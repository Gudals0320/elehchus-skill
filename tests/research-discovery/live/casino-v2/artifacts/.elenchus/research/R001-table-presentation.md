## 질문·목적·범위

중립 질문: 읽기 쉬운 테이블 중심의 3D 카지노 경험을 어떤 표현·조작·제작 접근으로 만들 수 있는가?

- 입력: 세 게임의 규칙 상태와 사용자 베팅·행동. 초기 가상 자금, 각 카드 게임 독립 6덱 등 확정 제약은 Idea를 참조한다.
- 출력: 실제 화면·조작 사례 비교와 제작 방법의 적용 조건, 사용자가 정할 열린 선택.
- 사용자 경험: Windows PC의 터미널부터 시작해 데스크톱 Chrome에서 혼자 플레이한다. 주변 공간이 보이는 테이블, 카드와 숫자의 가독성, 실사보다 애니메이션에 가까운 3D 느낌이 목표다.
- 성공 조건: 주요 표현·조작 접근을 실제 공개 자료로 비교하고, 관찰·자료 설명·추론·미확인을 분리해 제작 부담과 열린 선택을 제시한다. 최종 취향·구체적 성능 수치는 아직 사용자 미결정이다.
- 실패 조건: 소개 문구만으로 화면·동작을 보았다고 처리하거나, 특정 엔진·카메라·색을 사용자 선택으로 확정한다. 구현을 수행하거나 규칙 세칙 조사로 범위를 넓힌다.
- 확정 제약: Idea의 사용자 결정·제외를 따른다. 새 계정·유료 서비스 사용 금지. 제품 구현 금지.
- Repository 기준선: 현재 질문은 새 디자인·제작 접근 조사다. 운영상 제품 파일과 다른 저장소를 읽지 않는 범위이므로 기존 코드 연결·실행을 관찰하지 않았다. 사용 환경은 사용자 답변의 Windows PC/데스크톱 Chrome이며 하드웨어·버전은 미검증이다.
- 기술 언급 분류: Windows와 데스크톱 Chrome은 사용자 환경, 3D 느낌은 표현 요구다. 특정 엔진·라이브러리는 필수 제약이 아니며 조사에서 발견하는 후보로만 취급한다.
- 열린 질문: 카메라 높이와 이동, 구도·색·재질, 2D UI와 3D의 역할, 연출 속도·입력 시점, 자산 제작 방법과 부담.

## 탐색·검증 계획

초기 범주: 직접 카지노의 테이블·칩/버튼 조작, 인접 탁상 게임의 3D 공간·카드 가독성, 평면 카드 UI의 명료한 정보·빠른 조작. 3D 요구를 삭제하지 않고 작은 표현 방식과 3D 중심 방식의 교환 관계를 비교한다.

초기 검색은 `3D blackjack roulette baccarat game tabletop demo animated browser`, `Tabletop Club casino blackjack cards 3D official`, `Balatro card game interface play hand official`로 시작했다. 카지노 계정·현금 게임에 들어가지 않고 공개 원 제작자 페이지·영상·데모를 우선한다. 공개 접근 실패 시 공식 이미지·영상·공개 코드 등 같은 주장을 확인하는 경로를 찾는다.

| 검증할 주장 | 영향·반증 조건 | 필요한 원문·관찰 |
|---|---|---|
| 테이블 주변을 보이면서 카드·숫자와 베팅 영역을 읽기 쉽게 분리할 수 있다. | 낮은 시점에서 작은 카드/숫자가 가려지거나 포인터 대상이 모호하면 적용 범위를 제한한다. | 실제 테이블 화면, 해당 카드·베팅 장면 |
| 3D 공간 직접 조작과 별도 화면 버튼은 서로 다른 제작·조작 부담을 만든다. | 이미지의 배치만으로 실제 클릭·딜링·대기를 단정하지 않는다. | 동작하는 공개 데모/영상, 원 제작자 설명 |

관련 실패·한계는 홍보 자료와 별도로 확인했다. [bgio-effects 원 작성자 튜토리얼](https://delucis.github.io/bgio-effects/tutorial/)의 `Spot the difference`는 결과 값만 감시하면 같은 주사위 값이 연속 나올 때 두 번째 연출을 놓치는 예제를, `Wait a second…`는 점수 즉시 갱신이 연출 중 결과를 알려 버리는 문제를 설명한다. 메인이 해당 본문·코드를 읽었다. 이것을 우리 6덱의 같은 카드 반복·룰렛 같은 숫자 반복과 결과 공개 시점에 적용하는 것은 **추론**이다. 패키지 사용을 제안한 것은 아니다.

[MDN requestAnimationFrame](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)의 서두는 백그라운드 탭에서 콜백이 정지할 수 있고 프레임 수 대신 시간에 맞춰 진행해야 한다고 명시한다. 따라서 탭 복귀 시 연출을 이어갈지 결과로 이동할지는 **미정 사용자 경험**으로 남긴다. 현재 제품에서 오류를 재현했다는 뜻은 아니다.

### 검색·접근 공백 처리

- 실제 공개 검색은 직접 카지노/탁상/카드 UI로 시작한 뒤 Nintendo 공식 블랙잭, 룰렛 원 제작자 공개 코드·데모, 카드 평면 연출, 웹 3D 자산 작업·내보내기 제약으로 갱신했다. 동일 원본의 React/vanilla 프로젝트와 소개/데모는 독립 출처 수로 중복 계산하지 않았다.
- Neon 홈페이지 웹 본문 읽기는 Internal Error, 블랙잭 페이지는 0줄, 바카라는 non-retryable tool error였다. 별도 공개 Chrome 경로에서 실제 화면·조작을 확보했다. 도구의 빈 응답을 게임이 없거나 작동하지 않는 근거로 쓰지 않았다.
- Nintendo 웹 추출에서 게임 모달·영상이 빠져 공식 게임 목록을 공개 Chrome에서 열었다. 임베드 재생은 썸네일에 머물러 같은 공식 영상의 공개 YouTube 경로로 이동했고 0:02·0:42 프레임을 확인했다. 전 영상을 연속으로 보았다고 기록하지 않는다.
- Evolution의 연령 확인 경로는 terminal이다. 개인 정보나 나이를 대신 입력하지 않았다. 공개 소개 본문만 사용하고 다른 작성자의 공개 사례로 일부 보완했다.
- Deck of Cards 웹 추출은 0줄이어서 작성자 GitHub와 공개 Chrome 데모로 보완했다.
- Balatro 공식 홈페이지는 열었지만 게임플레이·영상은 관찰하지 않았다. 최종 비교 근거에서 제외했다. 계정·현금 기반 카지노 사이트, 유료 구매·다운로드 경로는 조사 목표에 필요하지 않아 진입하지 않았다.
- subagent가 전달한 추가 Babylon 회전 문제, Royal Roulette 정적 오류 의심, R3F 성능 문서, Rapier 결정성, Godot CLI는 메인이 결정적 원문 재확인을 하지 않았다. 본 Verdict의 확정 근거로 쓰지 않으며 세부 주장을 결론으로 옮기지 않는다.

## 결론과 다음 행동

판정: **결론 보류**. 화면 배치·직접 조작 선택지·제작 접근의 제한된 비교 결과는 제공할 수 있다. 최종 3D 연출 방향과 제작 방식 확정까지 조사 완료한 상태는 아니다.

- 근거: 직접 유사한 블랙잭·바카라·룰렛 사례와 인접 탁상/카드 연출을 비교했고, 원 제작자 코드·공식 문서에서 구현 경계·자산 부담·웹 제약을 확인했다.
- 반대 근거: 넓은 원근 장면은 카드가 작아지고, 작은 평면 접근은 공간·조명 표현이 제한된다. 직접 카드 공개는 클릭 수를 늘린다. 공개 룰렛 예제도 유지보수·규칙 차이·미검증 정확성 문제가 있다.
- 신뢰도: 관찰한 화면·버튼 상태·읽은 원문 사실은 높음. 우리 조건의 제작 부담 추론은 중간. 최종 3D 연속 동작·성능·취향 적합성은 낮음/미검증.
- 미승인 제안: 규칙 상태와 일시적인 배부·뒤집기·회전 이벤트를 분리하고 터미널은 즉시 출력, 웹은 선택한 방식으로 재생한다. 이는 결과를 두 번 계산하지 않고 같은 결과도 매번 연출하기 위한 설계 제안이다. 이벤트 보관·통계·멀티 서버 같은 새 기능을 추가하지 않는다.
- 미승인 제안: 웹 3D 장면과 별도 읽기 쉬운 UI를 우선 비교 후보로 둔다. 공간감과 숫자 가독성을 각각 조정할 수 있다는 근거이며, 카드 평면 중심의 작은 버전과 편집기 중심 3D도 선택 가능하다. 특정 엔진을 채택한 결정은 아니다.
- 채택·제외: 사용자 확정 제약은 유지. 사례의 색·재질·캐릭터·여러 좌석·로드·통계·00은 가져오지 않는다. 코드/에셋은 채택하지 않았다.
- Idea 영향: 미정 선택을 구체화한다. 카메라 높이·이동, 공간과 숫자의 화면 비중, 직접 공개와 자동 공개, 연출 중 조작·결과 표시, 탭 복귀, 자산 제작 방법을 열린 상태로 보존한다. 규칙 세칙·베팅 단위는 후속 합의다.
- Execution 영향: 전체 Build 계획과 번호는 만들지 않았다. 후속 계획에서 시각·동작 선택 및 필요한 관찰을 최종 에셋 제작보다 앞에 둬야 한다는 제안만 남긴다.

남은 중요한 공개 관찰은 카드가 배부·뒤집히는 연속 구간, 블랙잭 스플릿의 겹침·패 구분, 3D 룰렛이 결과 포켓에 멈추는 연속 구간이다. 같은 카메라 계열의 공개 영상/데모로 비교하고, 접근 가능한 원문 경로가 남아 있는 상태로 보존한다. 관찰하지 않은 부분을 구현 중 검증으로 대체하여 탐색 완료로 처리하지 않는다.

우리 제품에만 필요한 검증은 그 이후 별도다: 대상 Windows Chrome에서 화면 크기별 숫자 가독성, 같은 카드/결과 반복과 연출 누락, 스플릿 이동 경로, 탭 복귀·연출 종료와 정산의 일치, 로딩·GPU 비용. 현재 Lab은 실행하지 않았으며 이 목록도 승인된 Build가 아니다.

사용자 확인 전이므로 문서 상태는 `작성 중`이다. 다음 질문은 이 중간 비교 결과의 기록 방식과 남은 3D 연속 동작 조사를 후속 과제로 유지하는 데 관한 확인이다. 전체 Build 계획으로 이동하지 않는다.
