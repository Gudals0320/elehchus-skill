# Idea: 룰렛·바카라·블랙잭 싱글 카지노

- 상태: 작성 중
- 시작 요청: 룰렛·바카라·블랙잭을 플레이하는 터미널 카지노를 먼저 만들고, 이후 3D 애니메이션 웹앱으로 구현한다. 시작 자금을 정하고 파산할 때까지 계속 플레이한다. 저장은 필요 없다. 카드게임은 향후 멀티를 고려해 6덱으로 생각한다. 디자인 고찰과 레퍼런스 탐색이 필요하다.

## Topology

사용자가 원래 요청의 세 게임·세션 자금·터미널·웹 표현을 확인했다. 디자인·상호작용 사례와 제작 방법의 Research도 명시적으로 요청했다. 멀티플레이는 미래 맥락이며 이번 설계·구현 범위가 아니다.

| 구성요소 | 상태 | 초기 의도·산출물 | 근거 |
|---|---|---|---|
| 터미널 카지노 | 활성 | 세 게임의 규칙·진행·자금·파산을 확인하는 터미널 실행판 | 사용자: “터미널 기반 작동하는 카지노 로직”, 초기 자금·파산·계속 진행 |
| 3D 디자인·레퍼런스 탐색 | 활성 | 실제 사례를 비교해 시각·애니메이션 방향과 제작 부담을 판단할 근거 | 사용자: “디자인에 대한 고찰 및 레퍼런스 탐색이 많이 필요” |
| 애니메이션 웹게임 | 활성 | 터미널 단계 다음에 플레이할 싱글 웹앱 | 사용자: “터미널 기반 구현 -> 애니메이션 구현된 웹앱 게임 구현” |
| 멀티플레이 | 보류 | 미래 맥락으로만 보존 | 사용자 추가 답변: “멀티는 미래 맥락으로만” |

## 명료도

| 활성 구성요소 | 목표 | 제약 | 성공 기준 | 맥락 |
|---|---|---|---|---|
| 터미널 카지노 | 확정 | 부분확정 | 부분확정 | 부분확정 |
| 3D 디자인·레퍼런스 탐색 | 확정 | 확정 | 부분확정 | 확정 |
| 애니메이션 웹게임 | 부분확정 | 부분확정 | 미확인 | 미확인 |

## 확인된 사실

- 요청 파일에서 사용자 의도를 확인했다. 현재 제품의 코드·동작·디자인은 조사하지 않았다.
- 세션 설정상 최초 Release 확인이 완료되었고 업데이트가 필요 없다. 이 세션에서 재실행하지 않았다.

## 사용자 결정

- 출처: 사용자 요청. 게임은 룰렛·바카라·블랙잭 3개다.
- 출처: 사용자 요청. 초기 자금 설정 → 플레이 → 파산 시 게임오버, 파산하지 않으면 계속 진행한다.
- 출처: 사용자 요청. 터미널 기반 구현이 웹앱 구현보다 먼저다.
- 출처: 사용자 요청. 현재는 싱글 구현이며 카드게임은 6덱을 고려한다.
- 출처: 사용자 요청. 디자인 고찰과 레퍼런스 탐색을 진행한다. 구체적인 조사 질문은 Topology 확인 뒤 정한다.
- 출처: 사용자 추가 답변. 혼자 Windows PC에서 사용하며 웹은 데스크톱 Chrome 우선이다. 실제 현금·결제 없이 사용자가 입력한 초기 자금을 세 게임에서 공동으로 사용하고, 세션 종료 후 보관하지 않는다.
- 출처: 사용자 추가 답변. 카지노 이동·캐릭터 조작은 필요 없다. 플레이어·딜러 캐릭터도 필수가 아니다. 테이블 주변 공간이 보이고 카드·숫자가 읽기 쉬우며 실사보다 애니메이션에 가까운 3D 느낌을 원한다.
- 출처: 사용자 추가 답변. 카드게임은 각각 독립된 6덱, 룰렛은 싱글 제로, 바카라는 플레이어/뱅커/타이와 뱅커 5% 커미션, 블랙잭은 더블·스플릿까지를 원한다. 세칙·베팅 단위는 구현 전에 별도 합의한다.
- 출처: 사용자 추가 답변. 현재 조사는 디자인·상호작용 사례와 제작 방법에 집중하며 그 범위 안 역할 분담을 허용한다. 기술 구조는 조사 근거 이후에 제안한다.
- 출처: 사용자 추가 답변. 이번 대화는 Research 결론까지 확인하고 전체 Build 계획은 다음에 이어간다.

## 에이전트 제안

- 승인된 문서 구분. 활성 구성요소 3개와 보류 맥락 1개로 정리한다. 원래 요청 밖 기능은 추가하지 않는다.
- 대체됨. 응답 1에서 제안한 멀티 확장 제약 검토는 사용자 추가 답변에 따라 미래 맥락 보존으로 축소했다. 현재 서버·동기화 구조 선택으로 확대하지 않는다.
- 아직 미승인. 카메라·구도·색·재질·웹 텍스트/버튼과 3D의 역할·제작 도구는 Research 이후 사용자 선택으로 남긴다.
- 아직 미승인. R001의 비교 결과에 따라 테이블·카드·휠의 3D 표현과 정면 정보/행동 UI를 조합하는 안을 비교 기준안으로 제안한다. 가독성을 따로 조정할 수 있지만 UI·3D 상태 연결 부담이 있다. CSS/2.5D와 테이블 직접 조작 대안도 유지한다.

## 미확인·충돌

- Topology 질문은 사용자 추가 답변으로 해결됐다.
- 현재 Research: [R001](research/R001-table-presentation.md). 화면·조작·제작 접근 비교를 먼저 진행한다.
- 카메라·구도·색·재질, 텍스트/버튼과 3D 역할, 애니메이션 범위·시간·생략 여부, 자산 제작·재사용 방식과 품질 기준은 미확인이다.
- 규칙 세칙·베팅 단위·초기 자금 범위·게임 전환·중도 종료·재시작·입력 오류·성공 판정은 이후 Idea 인터뷰에서 구현 전에 합의한다.
- 기존 코드·도구는 현재 디자인 탐색에 필요하지 않아 확인하지 않았다. 특정 엔진·라이브러리 제약은 없다.
- R001에서 정지 배치·공개 데모 상태 변화·제작 접근은 비교했다. 카드/룰렛 공의 연속 움직임·타이밍 체감 비교는 미완료이며 완료로 계산하지 않는다. 이번 Research 확인과 미완료 부분의 처리에 대한 사용자 답을 기다린다.
