# Research R002: 게임 결과와 웹 연출의 연결

- 상태: 작성 중
- 기준: [idea.md](../idea.md)
- 확인 날짜: 2026-09-07
- 영향: Phase 후보 — 터미널 로직과 웹 표현의 연결 및 연출 검증. 전체 Execution 계획은 다음 논의 대상이다.
- 증거 경계: 가상 제품의 합성 문서 분석이며 실제 API·제품·성능 추천 근거가 아니다.

## Repository 기준선과 Neutral brief

관찰: `app.txt`는 `UNIMPLEMENTED PRODUCT STUB`이다. 현재 읽은 제품 기준선에는 재사용할 규칙 모듈이나 렌더러가 없다. `.elenchus/idea.md`의 확정 사용자 범위를 입력으로 사용한다. 실제 설치 라이브러리·사용자 설정·인증정보는 탐색하지 않았다. 문서 속 코드 조각은 실행하지 않았다.

| 항목 | 내용 |
|---|---|
| 중립 질문 | 터미널에서 웹으로 이어질 게임 결과와 3D 연출을 어떤 방식으로 연결할 수 있는가? |
| 입력 | 초기 자금, 게임 선택, 베팅과 게임별 행동, 각 카드게임의 독립 6덱 및 룰렛 싱글 제로 조건 |
| 출력 | 세 게임이 공유하는 세션 자금·상태·결과와, 그 결과에 일치하는 터미널 표시 및 웹 연출의 제작 방법 비교 |
| 사용자 경험 | 초기 자금을 입력해 플레이하고 파산하면 게임오버, 그 외 계속 진행. 먼저 터미널, 이후 애니메이션 웹앱. 블랙잭에는 더블·스플릿 선택이 있다. |
| 성공 조건 | 표현 타이밍 때문에 게임 결과·잔액이 달라지지 않도록 제안할 수 있고 카드·휠 연출의 작업 범위와 미검증 부분을 구분한다. |
| 실패 조건 | 애니메이션 샘플을 완성된 게임으로 취급하거나 구버전 API를 현행 계약으로 추천한다. 단일 화면·수식·seed만으로 공 착지·성능·복귀 동작을 검증했다고 주장한다. |
| 확정 제약 | Windows 싱글, 데스크톱 Chrome 우선, 실제 현금·결제 없음. 세션 공용 자금이며 보관하지 않음. 저장·계정·공유·통계 제외. 멀티는 미래 맥락. 새 계정·유료 서비스·제품 구현 미요청. |
| 객관적인 환경 사실 | 로컬 텍스트 증거만 제공. 네트워크·Browser·subagent 미지원. GPU·브라우저 버전·실행 자산과 성능 목표는 미확인. |
| 미해결 질문 | 렌더링 도구와 자산 제작 방식, 실제 휠 궤적·결과 일치, 화면 성능, 입력/연출 경계. 세칙·베팅 단위는 구현 전에 별도 합의. |

사용자 기술 언급 분류: 터미널→웹과 Chrome 우선은 필수 제약, Windows는 환경이다. 3D는 표현 목표이고 특정 엔진 지정은 아니다. 멀티는 미래 맥락이다. 사용자 지정 라이브러리·언어·서비스는 없다. Wheelkit과 아래 구조는 에이전트가 평가하는 후보·제안이지 사용자 선택이 아니다.

### 제안하는 최소 책임 구분

출처: 에이전트 제안. S2의 방법을 사용자의 터미널→웹 요구에 적용한 추론이며 확정 구조가 아니다.

1. 사용자 명령을 규칙 로직이 받아 허용 여부를 확인하고 상태·자금 변화와 표시할 사건을 만든다.
2. 터미널은 이를 텍스트로, 웹은 카드·칩·휠 움직임과 화면 정보로 표현한다. 잔액·점수·승패를 3D 좌표에서 계산하지 않는 방향을 권한다.
3. 블랙잭은 다음 사용자 결정 지점까지의 상태 전이를 확정한다. 히트·더블·스플릿 선택을 받기 전에 라운드 전체의 결과를 잠그는 방식은 사용자 요구를 충족하지 못한다. 이 적용 범위는 원문을 그대로 복제한 사실이 아니라 사용자 조건에 맞춘 제안이다.
4. 바카라와 블랙잭의 독립 6덱 및 공용 세션 자금은 규칙 상태의 관심사다. 화면에 312장의 모델을 항상 만들 필요가 있다는 근거는 없다. 보이는 소품과 논리 덱을 나누는 것은 제작 단순화 제안이다.

이는 저장·계정·통계·영속 이벤트 로그·네트워크·서버·멀티 기능을 추가하지 않는다. 미래 멀티를 고려한 상태/표현 경계의 가치는 있지만 이 분리만으로 멀티가 준비되었다고 주장하지 않는다. 언어와 모듈 공유 방식은 미정이다.

### 카드·칩·휠 연출의 제작 범위

카드와 칩은 상태에서 필요한 소품을 식별하고 이동·회전·공개를 표현하는 방식이 후보가 된다. 시간 진행으로 화면을 계산하는 S2의 방법은 프레임/콜백 지연에 규칙을 묶지 않을 단서를 준다. 실제 모션 곡선·공개 시간·효과·복귀 시 이어보기 또는 최종 상태 표시·연출 중 입력 허용은 UX 선택이므로 확정하지 않는다. 건너뛰기 기능도 선택된 경우에만 그 경계를 검증한다.

룰렛의 최종 착지에는 번호→포켓 배열 인덱스, 모델의 원점·정면·방향, 휠 회전과 공의 상대 위치가 일치해야 한다는 검증 가설이 필요하다. S2의 수식은 회전판 각도 보간만 다룬다. 그 식의 끝 각도가 맞아도 공의 궤도·감속·림에서 포켓으로 내려오는 구간·최종 착지는 증명되지 않는다. 한 장의 이미지나 숫자 하나 일치만으로 전체 연출을 채택하지 않는다.

### 렌더링·자산 도구의 선택 범위

R001의 3D+HTML 후보를 만들 때는 웹 렌더러에서 소품과 움직임을 구성하는 방식, 외부 제작 도구에서 만든 모델·애니메이션을 웹으로 가져오는 방식, 두 방식을 섞는 접근을 비교할 수 있다. 이는 에이전트가 제시하는 제작 범주다. 전자는 표현을 조정하는 코드 부담, 후자는 자산 제작·내보내기·좌표 일치 확인 부담을 검토해야 한다. HTML/CSS 2.5D는 더 작은 대안이지만 입체 공간 표현을 줄인다.

제공 자료에는 이 범주들의 실제 도구별 기능·라이선스·가격·파일 형식·로딩 성능 비교가 없다. 따라서 특정 현실 엔진·라이브러리·모델 제작 도구의 우열이나 무료 여부를 확정하지 않는다. 재료·색·조명 취향도 근거 없이 추가하지 않는다.

## Web closure와 Verdict

API 계약·버전 충돌·문서상의 구조 및 반례는 본문 확인을 마쳤다. 중요한 주장마다 적용 범위·확인 날짜·공백이 연결되어 있다. 그러나 C4·C5가 남아 있어 도구 채택과 실제 구현 가능성에 대한 전체 Research closure는 완료로 표시하지 않는다. 다음 행동은 실행 대상·실제 도구 근거 확보와 검증을 다음 논의로 연기하는 제안이다.

- 판정: 결론 보류 — 완성 연출·실행 성능·최종 도구 채택. 방법 비교와 조건부 구조 제안은 가능하다.
- 근거: S2의 동일 규칙 모듈/표현 분리, S5의 다른 환경 사례, S2·S7의 목표 결과 연출 계약.
- 반대 근거: S2의 콜백·원점 오류와 빠른 전환 경계, S8의 물리 결과 계약과 구버전 제거, 실행 자산 부재.
- 권고: 규칙 상태/이벤트와 표현의 분리를 우선 구조 후보로, 목표 포켓에 맞춘 연출을 룰렛의 우선 검증 후보로 둔다. 사용자가 엔진을 지정하거나 전체 물리 결과 방식을 승인한 것으로 기록하지 않는다.
- 채택·제외: 구현 구조는 아직 채택하지 않았다. Wheelkit 2.0을 목표 결과·37포켓 즉시 충족 후보에서 제외하며 1.4 유지보수 종료를 숨기지 않는다. 물리 방식은 대안으로 비교했으나 현재 우선안으로 권하지 않는다.
- 한계: 합성 자료만 분석했고 수식·데모를 실행하지 않았다. 실제 라이브러리 유지 상태·자산 권리·가격·Chrome 성능·전체 연출은 미확인이다.
- 신뢰도: 중간 — 사용자 조건에 대한 구조 제안. 문서 내부 API 충돌 판정은 높음, 실제 화면·성능·도구 적합성은 낮음.
- 출처와 변화: 에이전트 제안. 요구된 터미널/웹 연결의 내부 책임 구분을 추가 제안하며 새로운 사용자 기능·유료 의존성·멀티 범위는 추가하지 않는다. 사용자 확인 전 확정 계약으로 바꾸지 않는다.

## Idea 영향·Execution 연결·보류

Idea의 확정 범위는 유지한다. 바카라의 플레이어/뱅커/타이·뱅커 5% 커미션, 블랙잭 더블·스플릿, 카드게임별 독립 6덱, 싱글 제로를 바꾸지 않는다. 세칙과 베팅 단위, 커미션의 금액 처리 등 구현 전 합의 항목은 이번에 정하지 않는다.

Execution에서 향후 논의할 영향은 터미널→웹에 공유할 상태 계약과 웹 연출 검증 필요성이다. 전체 Phase·Build, 일정, 언어·엔진·프레임워크, UI 옵션은 작성·합의하지 않았다. 사용자에게 제시할 다음 선택은 연구 요약의 확인이며 제품 선택은 미정으로 유지한다.
