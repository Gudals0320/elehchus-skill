# Research R002: 게임 상태와 애니메이션 제작

- 상태: 작성 중
- 기준: [idea.md](../idea.md)의 터미널 → 웹 순서, 싱글 우선, 독립 6덱 카드게임·싱글 제로 룰렛
- 확인 날짜: 2026-09-07
- 영향: Phase 후보. 기술 구조는 제안 대상이며 승인된 설계가 아니다.

## 질문·목적·범위

중립 질문: 규칙·정산을 터미널에서 먼저 다루고 같은 결과를 웹에서 연출하려면 어떤 제작 접근이 가능하며, 재사용 후보의 조건과 한계는 무엇인가?

입력은 Idea의 사용자 결정, 제품 기준선과 제공된 기술 문서다. 출력은 상태·연출 결합 방식, 휠 제작 방식, 재사용 조건의 비교와 검증 공백이다. 사용자 경험은 처음 터미널에서 세 게임·공유 자금을 사용하고 이후 웹에서 결과를 읽고 조작하는 흐름이다. 성공 조건은 확정된 결과와 표현 사이의 책임·비용·실패 조건을 설명할 근거를 확보하는 것이다. 실패 조건은 문서의 API·측정값을 우리 환경의 실행 성공으로 바꾸거나 미래 멀티를 현재 구현 범위로 확대하는 것이다.

확정 제약·제외는 Idea를 참조한다. 엔진·언어·라이브러리는 사용자 필수 조건이 아니다. 문서에서 발견하는 구현체는 모두 비교 후보이며 neutral brief의 제약으로 삼지 않는다. 세칙·금액 단위·연출 속도는 미정이다. R001의 저장소 기준선과 접근 경계를 함께 적용한다. 실행 가능한 제품은 확인되지 않았으므로 현재 코드에 맞춘 구조라고 주장하지 않는다.

## 탐색·검증 계획

제작 문서 원문으로 결과와 연출의 결합 여부를 먼저 검토하고, 대안과 실패 경험을 비교한다. 휠 문서는 같은 라이브러리의 구버전·현행 버전이므로 지원·라이선스·성능 주장의 조건이 달라지는지 확인한다. 실제 최신 배포 상태를 네트워크로 확인하는 조사는 수행하지 않는다.

| 확인할 주장 | 필요한 근거·반증 조건 | 최신성·적용 범위 |
|---|---|---|
| 게임 결과를 먼저 정하고 연출을 나누는 전략을 가져올 수 있는가? | 기술 설명·관련 코드 조각·실패 경험. 중복 정산·입력 잠금 문제가 남으면 추가 책임을 명시 | 문서 속 구현 조건 한정 |
| 룰렛 휠 후보가 싱글 제로와 원하는 연출을 지원하는가? | 버전별 공식 형식 문서. API 제거·물리 계산 미지원·표현 자산 조건이 반증 가능 | 버전별 주장을 분리하고 현행 후보에 구버전 값 전이 금지 |
| 코드와 자산을 재사용할 수 있고 목표 환경 성능이 충분한가? | 라이선스·벤치마크 조건·원작성자 제한. 권리 누락·재현 환경 불일치이면 범위 제한 또는 근거 부족 | 현재 PC와 Chrome에서 실행·측정하지 않음 |

초기 검색 대상은 02·07·08 본문이며, 후속 검색은 그 문서가 제시한 버전 차이·입력·누락 이벤트·물리·라이선스·성능 조건과 다른 사례의 반대 설명을 대상으로 한다. 공개 대체 경로는 프로젝트 제약과 예약 도메인 때문에 이용하지 않으며, 가능한 로컬 원문을 검토한 범위와 남은 검증을 구분한다.

### 접근 기록과 공백 갱신

E02·E07·E08 본문을 확보한 뒤 `콜백`, `경과시간`, `넘긴`, `물리`, `포켓`, `원점`, `spinTo`, `spin(seed)`, `유지보수`, `37`, `24`, `성능`, `GPU`, `라이선스`, `license`와 관련 제한을 `evidence/` 전체에서 후속 검색했다. 결정적인 본문 위치를 다시 확인했다. 라이선스 문구는 발견되지 않았다. E04~E06에서 단순화·가림·구분 실패·적용 범위 반례도 확인했다.

1.4만 보면 결과 우선 휠 후보처럼 보이지만 2.0 본문은 그 계약을 반박했다. 이 변경으로 ‘현행 후보 그대로 재사용’에서 ‘접근법만 비교, 구체적 채택 보류’로 판정했다. 오래된 검색 설명이나 재게시를 현재 지원의 증거로 삼지 않았다.

각 원문 주소는 해당 파일 3행에 보존되어 있다. 로컬 문서는 모두 읽을 수 있었고 원문 본문 접근 실패는 없었다. 외부 소스 저장소·라이선스·실행 예제·벤치마크는 묶음에 없으며, 네트워크·브라우저 이용 불가와 예약 도메인 조건 때문에 공개 API·archive·렌더링 경로는 미시도다. 로컬 개발 문서·버전 변경 기록으로 가능한 대체 확인을 마쳤지만 실제 라이브러리 검증과 동등하지 않다. 현재 묶음의 재검색으로 실행·사용 권리 공백을 메울 수 없어 자료 경로를 닫으며, 새로운 실제 후보 자료는 결론을 바꿀 수 있다.

## 결론과 다음 행동

**탐색 판정: 결론 가능 — 제공 문서에 기록된 제작 접근의 차이와 조건부 구조 제안 범위. 검증 판정: 결론 보류 — 실제 엔진·라이브러리·코드/자산 재사용, 목표 환경 성능·정확성.** 파일 상태는 사용자 결론 합의 전이고 적용 검증 공백이 남은 `작성 중`이다.

**에이전트 제안 P2, 미승인:** 세 게임의 규칙·공유 세션 자금이 명령을 처리해 상태와 표현용 이벤트를 만들고, 터미널은 이를 텍스트로, 웹은 UI와 소품 움직임으로 표현하는 구조를 검토한다. E02의 직접적인 기술 설명과 탭 복귀 실패 경험이 근거다. 얻는 것은 규칙과 연출을 각각 수정할 경계이며 부담은 입력 시점·이벤트 순서·화면 최종 상태 일치의 관리다. 사용자 요구 대비 내부 구조의 구체화 제안이며 제품 기능 추가는 아니다. 별도 서버·영속 이벤트 저장·멀티 프로토콜·범용 프레임워크까지 도입하는 제안은 하지 않는다.

이를 우리 조건으로 옮길 때의 다음 내용은 **문서 관찰이 아닌 에이전트의 적용 추론**이다.

- 블랙잭은 아직 받지 않은 히트·스탠드·더블·스플릿 선택을 넘어 라운드 전체를 미리 확정하지 않는다. 각 사용자 행동으로 확정 가능한 규칙 상태·이벤트를 먼저 만들고 그 구간을 표현하는 경계가 필요하다. 바카라의 자동 진행 구간과 룰렛의 결과 연출에는 서로 다른 의사결정 경계가 있다.
- 카드게임별 독립 6덱은 게임 상태의 조건이다. 카드 312장 전부를 화면에 모델로 펼치는 요구가 아니다. 카드 이동·뒤집기, 칩 이동을 개별 이벤트의 시간 변화로 표현하는 제작 방향을 검토할 수 있으나 구체적 경로·속도·재질은 아직 미정이다.
- 공개 건너뛰기를 나중에 선택한다면 표현을 최종 상태로 이동시키면서 추첨·정산을 중복하지 않는 조건이 필요하다. 건너뛰기 버튼 자체는 사례의 기능이며 사용자 승인 기능이 아니다. 다음 입력을 언제 받는지도 UX 선택으로 남긴다.

**에이전트 제안 P3, 미승인:** 결과 우선 구조를 선택한다면 룰렛도 정한 포켓에 도달하는 연출 경로를 우선 검토한다. 물리 결과 방식보다 규칙·정산과 표현의 책임을 나누기 쉽다는 조건부 판단이다. 자연스러운 충돌을 직접 얻는 대신 공의 경로·감속·착지와 번호 배열을 별도로 맞추는 부담이 있다. E02의 각도 함수는 이 작업의 일부뿐이며 개발기 코드·에셋 복사를 승인하거나 제품 출발점으로 지정하지 않는다. 1.4는 유지 종료, 2.0은 목표 결과 계약 불일치로 어느 버전도 즉시 도입 추천하지 않는다.

반대 근거는 물리 시제품의 자연스러운 충돌, 평면 표현의 단순화 가능성, 상태·이벤트 분리 뒤에도 남은 빠른 넘김 경계 오류, 휠 원점 오차다. 상태와 표현의 분리만으로 정확성·재현성·멀티 확장 비용이 해결된다고 주장하지 않는다. 실제 엔진·언어·라이브러리·자산 제작 도구는 자료상 비교 근거가 없어 권장안을 정하지 않는다. 자산의 제작·수정 부담은 존재하지만 시간·비용 수치로 산정할 근거가 없다.

**신뢰도:** 합성 문서 내부의 API 차이·누락·실패 조건은 높음, 구조 적용 제안은 중간, 실제 도입·시각 품질·성능은 낮음.

| Discovery 완료 조건 | 판정과 이유 |
|---|---|
| 접근법 비교 | 제공 문서의 상태·표현 분리, 결과 지향 보간, 물리 결과 생성, 이미지 중심 대안 비교는 충족 |
| 적합한 직접 근거 | 구현 전략은 기술 설명·원작성자 실패 기록·버전 원문을 직접 읽어 비교 가능. 코드 조각은 실행하지 않았고 구체적 후보 적용 검증은 미충족 |
| 적용 가능성 | 행동 경계·이벤트 처리·포켓 좌표·자산 권리·유지 상태의 변경 부담 제시. 실제 성능·정확성은 별도 공백 |
| 결정 영향 | P2·P3를 미승인 조건부 제안으로 분리. 구버전 기능 전이·미검증 라이브러리 채택을 배제 |
| 타당한 종료 | 제공 문서의 전략 비교 범위는 더 읽을 관련 로컬 원문이 없어 부분 결론 가능. 실제 제작 도구·자산 확보·적용 검증 전체가 충분히 탐색됐다는 판정은 하지 않음 |

Web closure는 제공 문서의 주장 검증 범위에서 출처·버전·반증·공백을 추적할 수 있다. 실제 도입·성능 판단에는 추가 근거가 필요하므로 그 범위까지 종료 통과로 기록하지 않는다.

| 남은 공백 | 다음 조사·검증 조건과 시점 | 현재 상태 |
|---|---|---|
| 실제 제작 도구·라이브러리·자산 재사용 조건 | 실제 후보의 코드·문서·라이선스가 확보된 환경에서 비교 후 선택. 자산 통합 전에 확인 | 후속 Research 필요. 후보 채택·유료 자산 구매 승인 없음 |
| 카드 입력·탭 복귀·빠른 넘김 경계의 상태 일치 | 사용자에게 보여 줄 동작 경계를 정한 뒤, 경과시간 변경·탭 복귀·입력 경계에서 중복 추첨·정산·표시 불일치가 없는지 검증. 건너뛰기는 선택 시만 포함 | 미실행. 검증 Build의 필요성을 다음 Execution 논의에 전달할 제안이며 Build 합의 아님 |
| 휠 포켓 매핑·공 최종 위치·회전 경로 | 싱글 제로 번호 배열과 실제 모델이 정해진 뒤 모든 목표 포켓, 특히 0 양옆·원점·회전 방향을 확인. 정확한 착지를 전제로 후속 작업하기 전에 검증 | 미실행. 단일 정지 이미지나 각도 함수 검사만으로 대체 불가 |
| 가독성·움직임·성능 | R001의 미완료 사례 관찰을 유지. 실제 목표 환경과 장면·자산, 사용자 품질 기준을 갖춘 뒤 자체 화면을 검증 | 미실행. 원본 탐색을 제품 구현으로 대체하지 않음 |

Idea에는 연구 연결과 열린 기술 선택을 유지한다. 기존 요구·제외와 충돌하는 확정 변경은 없다. 전체 Execution 계획, Phase·Build 번호·순서의 합의는 다음 대화에서 다룬다. 위 후속 조건을 등록했다는 이유로 검증이 수행되거나 시각 탐색이 완료된 것으로 계산하지 않는다.
