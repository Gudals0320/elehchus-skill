**문서 비교 결과, 3D 테이블과 화면 UI를 나누고 게임 상태와 애니메이션을 분리하는 방식을 우선 검토할 만합니다.** 이는 미승인 제안입니다. 제공 자료는 모두 가상 제품의 합성 문서이며, 화면·영상·데모가 없어 **실제 가독성·움직임에 대한 결론은 보류**합니다.

Tablehaven 소개를 재게시한 Arcade Weekly는 독립 검증으로 계산하지 않았습니다. Tablehaven의 ‘라운드 약 9초’와 Flatfelt의 ‘카드당 180ms’도 측정 구간이 다른 설정값이므로, 적정 속도나 사용자 선호로 채택할 수 없습니다.

3D 애니메이션 제작에서는 **규칙이 입력을 처리해 상태와 이벤트를 만들고, 터미널과 웹이 이를 각각 표현하는 구조**를 제안합니다. Tablehaven 개발 기록에는 애니메이션 종료 콜백에서 다음 카드를 추첨하다가 탭 복귀 시 표시가 멈춘 실패가 있습니다. 상태와 표현을 나눈 뒤에도 빠른 건너뛰기 직후 새 라운드의 경계 검사는 필요했습니다.

우리 게임에 적용한다면 카드 이동·뒤집기·칩 이동을 확정된 이벤트에 맞춰 표현하는 방향입니다. 다만 블랙잭은 **각 사용자 행동으로 확정되는 구간**을 기준으로 해야 합니다. 아직 받지 않은 히트·더블·스플릿 선택까지 라운드 전체를 미리 정하는 의미는 아닙니다. 독립 6덱 역시 게임 상태의 조건이며, 312장을 모두 화면에 표시할 요구는 아닙니다.

룰렛은 다음 차이가 중요했습니다.

- **목표 포켓에 맞춘 연출:** 규칙 결과와 표현을 분리하기 쉽지만 공의 경로·감속·착지·포켓 좌표를 직접 맞춰야 합니다. 자료의 각도 함수에는 공 궤도가 없고, 실제 개발 기록에도 0 부근에서 한 칸 어긋난 문제가 있습니다.
- **물리 시뮬레이션으로 결과 생성:** 충돌 표현을 얻는 대신 시뮬레이션이 결과 결정에 관여합니다. 목표 결과를 먼저 정하는 방식과 책임이 달라집니다.
- **Wheelkit 버전 차이:** 1.4는 지정 포켓 정지와 37포켓 모델을 설명하지만 유지보수가 종료됐습니다. 2.0은 해당 API를 제거했고 예제도 24포켓입니다. 두 버전의 장점을 합쳐 도입 추천할 수 없습니다.

따라서 결과 우선 구조를 선택한다면 룰렛도 목표 포켓에 도달하는 연출을 우선 검토하자는 조건부 제안입니다. 실제 엔진·라이브러리·자산의 라이선스와 Windows·Chrome 성능은 확인되지 않아 선택하지 않았습니다.

아직 열린 선택은 카메라·구도·색·재질, HTML과 3D의 역할, 룰렛 베팅 조작, 연출 속도·다음 입력 시점·건너뛰기 여부입니다. 실제 화면과 연속 동작의 비교가 필요하며, 이 공백을 ‘구현하면서 확인’으로 넘겨 탐색 완료로 기록하지 않았습니다.
