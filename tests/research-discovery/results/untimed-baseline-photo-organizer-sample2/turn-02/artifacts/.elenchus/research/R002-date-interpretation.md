## Repository 기준선과 Neutral brief

`app.txt`는 `UNIMPLEMENTED PRODUCT STUB`이며 날짜 처리 코드·선정 모듈을 확인하지 못했다. 사용자 요청과 `idea.md`의 확정 조건만 intake로 사용한다. 저장소·환경의 공통 확인은 [R001의 기준선과 증거 계획](R001-collection-access.md)에 기록했다.

| 항목 | 내용 |
|---|---|
| 중립 질문 | 촬영일이 없거나 틀린 사진을 원본 변경 없이 날짜로 탐색하도록 어떤 읽기·표시·보정 방식을 참고할 것인가? |
| 입력 | 두 드라이브와 외장 SSD의 JPEG·PNG·HEIC 약 5만 장. 날짜 누락·오류 있음. Windows 개인 사용. |
| 출력 | 날짜 근거 보존과 탐색 정책의 대안·한계·검증 조건. 특정 라이브러리·정렬 정책의 확정은 아님. |

| 실패 조건 | 수정일을 실제 촬영일로 단정, 시간대를 임의로 부여, 오류·누락 사진을 조용히 숨김, 파싱 성공을 날짜의 진실성으로 오인, 미승인 원본/sidecar 기록. |

| 객관적 환경 | 제품 stub, 제공 합성 자료만 사용. 네트워크·브라우저·subagent 경로 미제공. |

기술 언급 분류: digiKam은 예시이며 비교 전제에서 제외한다. Windows·입력 형식은 환경/지원 목표다. Chronofile·EXIF·sidecar·DB는 자료의 후보 또는 설명 용어로, 사용자 필수 선택이 아니다.

## 후보와 핵심 차이

아래는 모두 출처: 에이전트 제안, 미승인이다.

| 접근법 | 얻는 결과 | 부담·잃는 결과 | 현재 판단 |
|---|---|---|---|
| 촬영일 우선, 없으면 파일 날짜를 임시 표시 | 대부분의 사진을 날짜 축에 배치 가능; 04 참고 | 임시 값을 촬영일로 오해할 수 있고 잘못된 촬영일은 남음 | 출처 표시와 함께 검토할 대안, 기본값 확정 안 함 |
| 알 수 없는 날짜를 별도 묶음으로 유지 | 불확실한 사진을 정확한 날짜로 위장하지 않음 | 날짜 축 밖의 사진을 따로 검토해야 함 | 대안 유지, 사용자 선호 미정 |
| 날짜 기준을 사용자가 선택 | 촬영일·파일 날짜의 관점 차이를 직접 비교; 01 참고 | 선택·정렬 변화의 인지 부담, 원래 날짜 오류는 해결 안 됨 | 대안 유지 |
| 원문과 별도로 로컬 보정값을 관리 | 원본을 보존하며 사용자가 탐색 날짜를 정정 가능 | 별도 기록의 보관·갱신·되돌림 필요 | 저장 패턴 후보. 보정 UI·자동 저장·원본 쓰기 기능의 채택은 별도 |
| 작은 버전: 출처 표시·누락 구분만, 보정 기능 연기 | 날짜의 한계를 설명하면서 범위 감소 | 잘못된 날짜를 앱 안에서 고치지는 못함 | 축소 대안, 제외로 확정하지 않음 |

제작 방법으로 원문·파싱값·출처·시간대 유무를 보존하는 구조를 우선 제안한다. 실제로는 파싱 상태와 사용자 보정값을 구분할 수 있는지도 후속 검증한다. 이것은 출처 설명을 위한 제안이며 구체적 DB·schema·라이브러리 선택은 아니다. 폴더 sidecar 기록을 기본으로 채택하지 않으며, 별도 앱 기록도 저장 내용·시점의 UX 정책은 미정이다.

## Verdict

- 판정: **결론 가능** — 날짜의 출처와 불확실성을 보존할 필요 및 정책 대안의 비교에 한정. 기본 날짜 정책·Chronofile 채택·HEIC 지원은 **결론 보류**.
- 권장 방향: 날짜를 단일한 확정 촬영일로 축약하지 않고 근거를 보존·표시하는 방향. 보정 기능을 선택한다면 원본과 분리한 기록부터 검토한다. 출처: 에이전트 제안, 미승인.
- 근거: 08의 값·출처·시간대 반환과 읽기 전용 경계, 04의 출처 배지 사례.
- 반대 근거: 출처를 보존해도 잘못 설정된 촬영일을 자동 판별하지 못한다. 사용자에게 정보가 많아질 수 있고 별도 보정값은 재스캔과 보관 정책이 필요하다.
- 채택·제외 근거: 설명 가능한 날짜 모델을 참고한다. 수정일=촬영일, 파싱 성공=사실, 시간대 자동 확정은 채택하지 않는다. 모듈·sidecar·특정 정렬 정책을 필수로 두지 않는다.
- 한계: 모든 원문은 합성이다. 08의 코드 조각은 공개 구현 설명의 예시일 뿐 실제 저장소 분석·테스트가 아니다. HEIC·손상 입력·실제 날짜 오류는 미검증이다.
- 신뢰도: **중간** — 문서상 한계는 분명하지만 사용자 정책과 구현 지원의 근거는 부족하다.
- Idea에서 바꿀 내용: 출처 보존·보정 분리의 미승인 제안을 연결하고 날짜 우선순위·보관 정책은 미정으로 유지.
- Execution에서 바꿀 Phase·Build: 없음. 날짜/형식 검증이 정렬·보정 정책 확정보다 앞서야 할 수 있다는 의존성만 제안. 전체 단계·Build 합의는 다음 대화.

## 보류·후속 검증·closure

- V1: 개인 사진이 아닌 검증 데이터로 세 형식의 정상·누락·파싱 불가·파싱되지만 잘못된 값·시간대 없음·상충 값을 검토한다. 읽기 실패가 전체 탐색을 중단시키지 않고 원인·출처를 구별하는지가 관찰 기준 제안이다. 전후 원본·sidecar 비변경도 확인해야 한다. 실험은 미실행이다.
- V2: 보정 채택 시 재스캔 후 보정값 유지·원문 구별·적용 전 원본 불변·취소 경험을 확인한다. 보정 기능 자체, 자동 저장·보관량·원본 쓰기 정책은 미승인이다.
- 핵심 주장과 반대 근거·버전·접근 경계를 기록했다. 로컬 문서 비교는 끝냈으나 실제 Web·Browser·Lab 확인은 완료하지 않았다. 중요한 지원 공백은 검증 연기로 연결했고 Research closure와 제품 정책 합의는 선언하지 않는다.
