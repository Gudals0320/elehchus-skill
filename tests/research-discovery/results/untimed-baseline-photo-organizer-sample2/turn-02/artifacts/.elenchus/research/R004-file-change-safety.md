# Research R004: 파일 적용 전 검토와 실패 후 상태 확인

- 상태: 작성 중
- 기준: [idea.md](../idea.md), T4 및 T1·T2·T3와의 파일 변경 경계
- 확인 날짜: 2026-09-07
- 영향: Phase 후보
- 증거 범위: 가상 합성 문서의 안전 설계 비교. 실제 파일 이동·삭제·중단·복구 실험은 수행하지 않았다. 이동 채택·복구 정책·전체 실행 계획은 미승인이다.

## Repository 기준선과 Neutral brief

`app.txt`는 `UNIMPLEMENTED PRODUCT STUB`이다. 파일 작업 엔진·테스트·복구 코드는 확인되지 않았다. 관련 문서만 읽었으며 개인 사진과 두 드라이브·외장 SSD를 실제로 탐색하지 않았다. 환경·자료의 공통 기준선은 [R001](R001-collection-access.md)에 있다.

| 항목 | 내용 |
|---|---|
| 중립 질문 | 파일 변경을 선택한다면 적용 전 목록 검토와 실패 후 원본·작업 결과 확인을 어떤 경계와 기록으로 지원할 것인가? |
| 입력 | Windows에서 JPEG·PNG·HEIC 약 5만 장이 두 드라이브와 외장 SSD에 분산. 사용자가 고른 사진과 변경 후보. 실제 개인 사진 접근 금지. |
| 출력 | 파일 변경의 조건·복구 범위·실패 관찰 기준과 제작 패턴 비교. 파일 작업 구현·실제 적용 권한 부여는 아님. |
| 사용자 경험 | 날짜로 훑고 크게 비교한 뒤 명시적으로 적용. 이동 채택 시 원본·대상 목록을 먼저 보고 실패 후 원본 상태와 일어난 일을 알아야 함. 삭제 전 나란히 비교해 직접 선택. |
| 성공 조건 | 적용 전 원본·메타데이터 불변. 변경을 선택한 항목과 실제 결과를 연결해 설명. 중단 이후 확인 안 된 상태를 성공이나 안전한 삭제로 단정하지 않는 것은 에이전트 제안 기준. |
| 실패 조건 | 선택·드래그만으로 원본 변경, 검토하지 않은 삭제, 대상 덮어쓰기 정책의 무단 확정, 다른 드라이브 이동이나 일괄 작업의 원자성을 보장, 불확실한 중단 상태에서 원본 삭제 반복. |
| 확정 제약 | 로컬·인터넷 없는 개인 사용. SSD 분리 시 이전 정보 조회. 계정·클라우드 업로드·공유·얼굴 인식·사진 편집 제외. 유사성 자동 삭제 금지. 유료 호출·외부 계정·실제 개인 사진 접근 금지. 신규 기능·비용 미확정. 이동 기능 자체는 미정. |
| 객관적 환경 | 제품 stub·합성 개발 문서만 존재. 네트워크·브라우저·subagent 경로 미제공. 실제 파일시스템·권한·여유 공간·Windows 구성 미검증. |
| 미해결 질문 | 이동/이름 변경 채택, 충돌 선택, 취소·부분 성공·재시도, 삭제 방식·휴지통·보관 기간·되돌림, 기록 보관 정책. |

기술 언급 분류: digiKam은 예시다. 파일 이동은 조건부 기능 후보다. journal·rename·복사 보관함·휴지통은 조사에서 발견한 구현/UX 후보이지 필수 엔진이나 승인된 정책이 아니다.

## 후보와 핵심 차이

모두 출처: 에이전트 제안, 미승인이다. 사용자 요구인 적용 전 불변·목록 확인·실패 파악을 위한 대안 비교다.

| 접근법 | 얻는 결과 | 부담·잃는 결과 | 현재 판단 |
|---|---|---|---|
| 탐색·비교·선택까지만, 파일 적용 연기 | 원본 변경으로 인한 실패 범위를 크게 줄임 | 앱 안에서 물리적 폴더 정리가 끝나지 않음 | 더 작은 버전으로 동등 비교. 이동·삭제 제외 확정 아님 |
| 계획 목록을 확인한 항목만 명시적으로 적용하고 단계별 기록 | 어떤 원본을 어디로 바꾸는지 검토, 부분 성공·중단 후 결과 추적 | 충돌·재검증·재시도·기록 보관 등 구현과 UX 부담 | 이동 채택 시 우선 검토할 방향 |
| 복사 보관함을 중심으로 관리 | 원장치 분리 후에도 복사본 접근 가능 | 공간 중복·원래 폴더 정리 별도. 복사본 휴지통은 원본의 복구 보장 아님 | 관리 대안, 안전 문제를 자동 해결하지 않음 |
| 기존 파일 도구에서 적용하고 앱은 검토 결과만 제공 | 자체 파일 변경 엔진의 개발 부담 감소 | 다른 도구로 넘어가는 수고, 앱과 외부 결과의 연결이 약함 | 만들지 않기/기능 연기의 대안. 실제 도구 안전성은 별도 검증 |

참고할 제작 경계는 다음과 같다. 구현 코드나 승인된 실행 계획이 아니다.

1. **계획과 적용 구분:** 선택·드래그·보정 초안은 계획이다. 원본·대상·작업 종류·충돌·적용 범위를 확인한 뒤 명시적 적용으로 이어진다. 원본 삭제가 포함되는 이동은 그 사실도 목록에 드러내야 한다는 에이전트 제안이다.
2. **적용 시 재검증:** 02처럼 계획 당시와 실행 당시의 파일 정보가 다르면 해당 항목을 보류한다. 장치 연결·대상 충돌·공간도 다시 확인하는 방향을 검토한다. 변경 감지 방법과 덮어쓰기/이름 변경/건너뛰기 정책은 확정하지 않는다.
3. **드라이브 간 단계를 분리:** 02의 복사 → 확인 → 원본 제거를 참고한다. “확인”의 구체적 무결성 기준과 원본 제거 직전 재검증은 구현 검증이 필요하다. 복사 완료 표시 하나만으로 삭제 가능한 상태라고 보장하지 않는다.
4. **항목별 결과와 미확인 상태:** 기록은 원본·대상 및 완료된 단계와 실패/보류 이유를 사용자가 이해할 수 있게 연결하는 방향이다. 중단 후 기록과 실제 파일 상태를 대조하고 확인되지 않은 항목은 자동 삭제·덮어쓰기로 진행하지 않는 것을 제안한다. 완료 항목을 다시 삭제하지 않는 재개는 문서상 패턴이지 실제 입증된 기능이 아니다.
5. **복구와 되돌림 구별:** 어디까지 실행되었는지 알려 주는 것, 안전하게 재시도하는 것, 모든 파일을 이전 상태로 되돌리는 것은 서로 다른 결과다. 사용자 요구는 앞의 상태 파악을 포함하지만 전체 원상 복구·특정 휴지통·30일 보관은 아직 합의하지 않았다.

## Verdict

- 판정: **결론 가능** — 이동 채택 시 참고할 계획·재검증·단계 기록 패턴과 보장하지 못하는 경계를 구분하는 범위. 파일 작업 엔진의 안전 인증·완전 복구·삭제 정책은 **결론 보류**.
- 권장 방향: 파일 변경을 채택한다면 적용 전 계획과 실제 실행을 분리하고 항목별 진행·실패·미확인 상태를 남기는 방향. 출처: 에이전트 제안, 미승인. 이동 자체의 채택을 요구하지 않는다.
- 근거: 02의 즉시 작업 실패 경험, 계획·journal·복사/확인/제거·외부 변경 보류·재개 설명. 01의 경로 목록과 충돌 검토.
- 반대 근거: 02는 파일시스템별 완전 복구를 보장하지 않는다. 같은 드라이브 rename의 속도는 다른 드라이브나 전체 일괄 작업의 원자성 근거가 아니다. 기록이 있다고 디스크 오류·전원 중단 뒤 상태가 항상 확정되는 것도 입증되지 않았다.
- 채택·제외 근거: 명시적 적용·직접 선택이라는 사용자 조건을 유지한다. 즉시 변경, 미검토 삭제, 유사성 자동 삭제, 원자적 일괄 이동·무조건 자동 복구 보장은 채택하지 않는다. 보관함의 30일 휴지통을 사용자 원본에 대한 정책으로 옮기지 않는다.
- 한계: 소스·실제 API·파일시스템·정전/분리 실험 없음. 문서상 재개 패턴은 실행된 검증이 아니다. 원본 메타데이터 쓰기·삭제·복구는 각자 별도의 합의와 검증이 필요하다.
- 신뢰도: **중간** — 실패 경계와 참고 패턴은 명시적이나 구현 안전성의 신뢰도는 낮다.
- Idea에서 바꿀 내용: 이동 조건부·적용 전 불변·직접 삭제 선택을 유지. 단계 기록·재검증을 미승인 제안으로 추가하고 전체 되돌림·삭제 보관 기간은 미정으로 둔다.
- Execution에서 바꿀 Phase·Build: 없음. 이동/삭제를 채택할 경우 중단·재개 검증이 기능의 일반 적용보다 앞서야 한다는 의존성만 제안. 구체적 Phase·Build·일정·비용은 다음 합의로 남긴다.

## 보류·후속 검증·closure

V1은 향후 실제 파일 엔진 후보와 격리 조건이 마련될 때 수행할 검증 제안이다. 현재는 실험 코드·데이터·Lab을 만들지 않았다. 사용자 개인 사진과 실제 라이브러리는 사용하지 않는다.

| 검증 조건 제안 | 확인할 사용자 결과·채택 기준 제안 | 보류/실패 기준 |
|---|---|---|
| 목록 작성만, 선택만, 적용 전 취소 | 원본 사진·메타데이터·sidecar 불변 | 승인 전 원본 영역 변경 |
| 동일 드라이브와 드라이브 간 작업 구분 | 항목별 원본·대상과 실제 결과 추적 | 빠른 rename 결과를 전체 작업 보장으로 일반화 |
| 복사 중·확인 후·원본 제거 전후·기록 저장 전후에 중단 | 재시작 후 확인 가능한 단계와 확인 필요 상태 구분 | 불확실한 상태를 성공으로 표시·삭제 반복 |
| 외장 장치 분리·재연결, 대상 충돌·공간 부족·권한 거절 | 실패/보류 항목과 남아 있는 원본·대상 상태 설명 | 대상 덮어쓰기·원본 제거를 검토 없이 수행 |
| 계획 뒤 원본/대상 외부 변경, 적용 시점의 추가 변경 | 검토한 대상과 실제 작업 대상이 달라지면 보류·재검토 | 오래된 계획으로 다른 파일 변경 |

| 삭제 채택 시 복구 경계 | 사용자와 합의한 방식·보관 범위 안에서 복구 가능 여부 검증 | 문서의 30일 휴지통을 검증 없이 보장 |

위 조건을 못 충족하면 파일 적용을 연기하거나 범위를 좁히는 선택이 필요하다. 작은 검증이라도 격리·출력 위치를 확인한 뒤에만 실행해야 하며, 계획 합의는 실제 개인 파일 접근·삭제 권한이 아니다.
