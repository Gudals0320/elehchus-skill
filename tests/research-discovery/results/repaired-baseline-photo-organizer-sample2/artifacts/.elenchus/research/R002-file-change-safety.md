## Repository 기준선과 Neutral brief

기존 `.elenchus/idea.md`와 프로젝트 지침, `evidence/README.md`를 읽었다. 조사 시작 당시 다른 Research·Execution 문서는 없었다. 이번 질문은 기존 코드 수정과 무관하므로 제품 소스·설정·테스트는 조사하지 않는다. 파일 목록/문서 확인은 제품 동작 관찰이 아니다.

| 항목 | 내용 |
|---|---|
| 중립 질문 | 선택적인 파일 이동·삭제에서 적용 전 확인과 실패 후 원본 상태를 어떻게 보장할 것인가 |
| 입력 | 서로 다른 드라이브와 외장 SSD의 원본 사진·메타데이터, 사용자가 명시적으로 적용할 변경 후보. |

| 확정 제약 | Windows·개인·로컬·인터넷 없이 탐색. 명시적 적용 전 원본·메타데이터 불변. 계정·업로드·공유·얼굴 인식·편집 제외. 외부 계정·유료 호출·실제 개인 사진 접근 금지. 새 기능·비용 미확정. |

사용자 기술 언급 분류: Windows와 JPEG·PNG·HEIC는 필수 조건/현재 입력, 두 드라이브·외장 SSD·약 5만 장은 사용자 보고 환경, digiKam은 예시다. 특정 제품·엔진·DB는 필수 조건이 아니며 비교 전제에 넣지 않았다. 사용자 답의 Research 진행 허용을 적용하며 아직 미정인 Idea UX를 확정하지 않는다.

## Retrieval plan

S01 제품 안내의 move·undo·preview를 S02 개발 문서의 cross-volume·copy·verify·delete·failure·collision·journal과 대조한다. S03 가져오기·복구 의미, S07 수동 비교·삭제 경계를 추가 확인한다. 제품 설명과 개발 문서를 독립 원천 둘로 세지 않는다.

접근 경로: `evidence/`의 원문 파일을 직접 읽고 본문·작성 주체·버전·원천을 대조한다. S00은 README, S01–S08은 파일 번호다. 한 파일의 공백은 같은 주장에 관련된 다른 제공 문서로 보완한다. 공개 URL은 합성 문서의 출처 식별자이며 실제 접근 성공을 뜻하지 않는다. 실패 시 다른 로컬 제공본을 확인하고, 그 밖의 웹·API·feed·archive는 네트워크 미제공으로 미시도한다. 브라우저 관찰이 있어야 판정할 UX는 보류하고, 구현·성능·복구 주장은 검증 후보로 연결한다.
