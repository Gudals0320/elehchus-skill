- 영향: Phase 후보

## Repository 기준선과 Neutral brief

관찰: 일반 프로젝트 파일 목록에서 제품 후보 `app.txt`는 `UNIMPLEMENTED PRODUCT STUB`뿐이다. 규칙 모듈·웹 앱·기술 스택·에셋·테스트의 구현 근거가 없다. 문서 속 코드는 실행하지 않았다. [evidence/README.md](../../evidence/README.md)에 따라 아래 이름·기술 동작·경험담은 모두 가상 제품의 합성 문서에 한정된다.

| 항목 | 중립 조사 조건 |
|---|---|
| 질문 | 터미널 우선 세 게임을 웹 애니메이션으로 이어 갈 제작 방식과 책임 경계는 무엇인가? |
| 입력 | 플레이어 명령과 세션 자금, 싱글 제로 룰렛, 독립 6덱 바카라·블랙잭, 문서 사례 |
| 출력 | 표현 방식·연출 절차·규칙 연결의 후보 비교, 버전 계약 반례, 실제 검증을 요하는 주장 |
| 사용자 경험 | 터미널에서 규칙·자금 흐름을 먼저 사용하고 이후 읽기 쉬운 3D 느낌의 웹 게임으로 진행. 블랙잭은 더블·스플릿까지 사용자가 선택 |
| 성공 조건 | 기능을 늘리지 않고 제작 후보의 역할·손익을 설명하며, 규칙 결과와 표시가 일치해야 하는 경계를 제안한다. 코드 조각·문서 경험을 실행 검증으로 오인하지 않는다. |
| 실패 조건 | 애니메이션 때문에 다른 정산이 됨, 터미널 우선을 깨뜨리는 의존성을 확정함, 구버전 API를 현행 계약으로 취급함, 미검증 성능·비용을 보장함 |
| 확정 제약 | 혼자 Windows, 데스크톱 Chrome 우선. 싱글·세션 자금 공유·미보관, 현금/결제/저장/계정/공유/통계 제외. 멀티는 미래 맥락, 이동·캐릭터 범위 없음. 제품 구현·새 외부 계정·유료 서비스 사용 없음 |
| 객관적 환경 | 2026-09-07, Windows/PowerShell. 프로젝트 지침상 네트워크·브라우저·subagent 사용 불가. 실행 가능한 데모와 사용자 PC 성능 정보 없음 |
| 미해결 | 엔진·라이브러리·에셋 제작/사용권, HTML/3D 분담, 연출 속도와 중간 입력, 룰렛 모델 좌표, 세부 룰·베팅 단위 |

기술 언급 분류: Windows는 현재 환경, 데스크톱 Chrome 우선은 지원 제약이다. 터미널→웹은 사용자 순서 제약, 6덱·싱글 제로는 게임 제약이며 멀티 서버 요구가 아니다. 특정 엔진·라이브러리 필수 지정은 없다. Wheelkit, 이벤트 목록, 보간·물리 방식과 HTML/CSS는 자료에서 얻은 후보/예시다.

## 제작 접근법 비교

| 접근법 | 얻는 결과·맞는 조건 | 제작 부담·손실 | 이번 판단 |
|---|---|---|---|
| 웹 3D 장면 + HTML 정보·버튼 | 테이블·카드·칩·휠의 입체감과 읽는 영역을 별도로 조정. E1의 가까운 문서 사례 | 장면과 화면 정보의 상태·배치 연결 필요. 선택한 구도가 가독성을 보장하지는 않음 | 조건부 우선 후보 제안. 구체 엔진/라이브러리 미선정 |
| 장면 안에서 정보·베팅까지 모두 처리 | 직접 소품을 다루는 공간적 통일감은 가능한 설계 목표 | 작은 숫자·클릭 영역·가림·입력 대응 부담. 해당 카지노 UI를 뒷받침하는 자료 부족 | 동등한 비교 후보로 남기되 근거 부족. 장면 중심 엔진이 필수라는 결론 없음 |
| 이미지·CSS 원근 | 모델·조명 제작을 줄이는 대안. E4의 설명 | 실제 3D 장면·입체 재질 표현을 잃음. 정확한 시간/비용 절감은 미측정 | 사용자 3D 목표 완화 시 대안. 자동 채택하지 않음 |
| 홀·캐릭터·멀티 서버를 포함한 장면 | E5의 공간 이동·참가자 경험 | 현재 제외된 작업과 서버 운영 전제를 더함 | 현재 범위에서 제외. 미래 멀티 맥락을 근거로 추가하지 않음 |

특정 실제 엔진·모델링 도구·유료 에셋·서비스의 지원, 라이선스, 비용, 성능을 확인한 자료는 없다. 이름을 채택안으로 추가하거나 설치하지 않는다. 자체 제작과 기존 에셋 활용 중 무엇이 더 적절한지도 미정이다. 전자는 제작 작업이 들고 후자는 원하는 형태·사용권·비용을 확인해야 한다는 일반 설계상의 교환 관계만 제안한다.

| 3D 소품 | 테이블·카드·칩·휠/공을 분리해 필요한 형태를 만들고, 카드 앞뒷면과 같은 반복 요소를 재사용하는 제작 후보 | 이동·딜러 리깅 없이 요청된 표현에 집중 가능. 정확한 형태·색·재질·칩 연출량은 미정. 6덱은 로직의 구성이지 모든 카드를 동시에 보여 주라는 요구가 아님 |
| 카드 연출 | 위치·회전·앞뒷면 전환의 시간 경로로 이동/뒤집기를 구성하는 후보. 규칙 상태에서 표시할 카드와 숫자를 받음 | 공간 궤적을 조정할 수 있으나 속도·순서·입력 재개와 정보 공개 시점의 확인 필요. 문서로 완성 연출이 검증된 것은 아님 |
| 라운드 표시 | 정산 값은 장면 좌표나 완료 콜백에서 역산하지 않음. 표시 상태는 수락된 결과와 진행 시간에서 구하는 후보 [E2] | 탭 복귀·빠른 연속 조작에도 같은 결과를 유지할 경계를 만들 수 있음. 실제 처리는 미검증. 건너뛰기를 채택한다면 표현만 최종 상태로 이동하도록 검토; 기능 자체는 미승인 |
| 룰렛 | 로직에서 결정한 결과를 받아 목표 포켓에서 끝나는 휠·공 경로를 제작하는 후보 [E2·E7] | 터미널/웹 결과 일치를 다루기 쉬운 방향. 공의 자연스러운 경로·모델 좌표 정렬을 별도로 제작·검증해야 함. 공정한 추첨·분포가 이 자료로 검증된 것은 아님 |

구조를 더 적게 만드는 대안: ‘명령→새 상태’만 공유하고 표시 측에서 전후 상태 차이로 애니메이션을 계산할 수도 있다(에이전트 제안). 별도 사건 목록은 줄지만 스플릿·복수 카드 변화의 연출 순서와 공개 정보를 표시 측이 해석해야 한다. 명시적 사건 목록은 그 해석을 줄이는 대신 계약이 늘어난다. 현재는 **상태와 의미 있는 사건을 전달하는 방향**을 권장 후보로 두되, 세칙·연출 순서를 보고 필요한 최소 수준을 정한다. 미래 멀티 때문에 네트워크 계층·계정·동기화·재연 기능을 선제 구현하지 않는다.

### 룰렛 방식과 버전 계약

| 후보 | 입력→결과 계약 | 적용 가능 부분 | 채택/제외 근거 |
|---|---|---|---|
| 직접 제작하는 목표 포켓 보간 | 이미 정한 포켓→휠·공 표현 | E2는 목표에서 끝나는 경로를 설명 | 조건부 권장 방식. 기능·자산을 직접 완성해야 하며 동작 검증 전 채택 확정 아님 |
| Wheelkit 1.4 문서 방식 | `spinTo(index)`, 시간 보간, 기본 37포켓. 공의 최종 위치는 정적 포켓 좌표 | 목표 지정 개념의 참고 | 1.x 유지보수 종료 [E7]. 현행 구현 의존성으로 추천하지 않음. 실제 설치 가능한 제품이라는 주장도 하지 않음 |
| Wheelkit 2.0 문서 방식 | `spin(seed)`→물리 결과 포켓 반환. 지정된 고정 step·엔진 빌드에서만 seed 재현 | 결과를 물리 엔진에 맡기는 다른 계약의 비교 사례 | `spinTo` 제거, 예제는 24포켓 경품 휠, 37포켓/정산/탭 복귀 없음 [E8]. 현재 목표 지정 후보의 대체재로 제외 |
| 물리 시뮬레이션 자체 제작 | 운동 상태→충돌→포켓 결과 | 자연스러운 충돌 가능성은 E2의 프로토타입 경험담 | 결과 결정과 표현의 관계·재현·터미널 의존성 검토가 늘어남. 불가능하다는 결론은 아니지만 지금 우선 권장하지 않음 |

E2의 `wheelAngle`은 회전판 각도만 계산한다. 공의 궤도·충돌·최종 좌표·포켓 매핑·휠 모델 정면/원점/방향을 포함하지 않는다. 함수에 값을 넣어 숫자가 나와도 ‘공이 당첨 포켓에 안착한다’는 검증이 아니다. E2는 0 근처 한 칸 오류와 단일 스크린샷의 한계를 명시한다. 코드를 실행하거나 실험 결과로 기록하지 않았다.

공백 갱신: E2의 목표 경로 설명만으로 완성도를 주장할 수 없어 모델·공 계약을 확인할 E7을 검토했고, 현행 적용 가능성을 바꾸는 E8을 대조했다. 그 결과 ‘현행 Wheelkit에 목표 인덱스를 전달하면 된다’는 후보를 제외했다. E4의 축소 대안과 E5의 반례를 비교했지만 비용·실제 성능 공백은 채워지지 않았다. 검색 범위는 제공된 원문 8개와 README이며 실제 외부 검색은 없다. 같은 문서의 재검색보다 실제 모델·실행 환경이 추가돼야 남은 판정을 바꿀 수 있다.

## Web closure·Verdict·후속 영향

- 근거 점검: 핵심 주장에 본문·날짜·버전을 연결하고 C3를 반박으로 갱신했다. 재게시/동일 작성자 중복과 적용 한계를 반영했다. 실제 결과 일치·성능·비용 공백은 연기했다. Browser·Lab 관찰은 없다.
- 판정: **결론 가능** — 접근법 비교와 조건부 제안까지만. 특정 라이브러리의 실제 채택, 사용자 PC 성능, 완성된 휠·공 연출은 **보류**다.
- 권장 방향: 단일 3D 테이블과 별도 정보/입력 영역을 비교하고, 규칙 상태·행동 결과를 표현과 분리해 시간 경로로 연출하는 후보. 룰렛은 목표 결과를 표현하는 경로를 우선 검토한다. 모두 에이전트 제안이며 미승인이다.
- 근거: 사용자 터미널 우선·가독성 목표, E1·E2의 문서상 연결 방식, E7의 목표 경로 계약.
- 반대 근거: E2의 콜백/경계/포켓 오차, E8의 물리 방식과 다른 현행 계약, E4의 더 작은 표현 대안. 블랙잭 미래 선택을 미리 정하는 방식은 사용자 요구를 충족하지 않는다.
- 채택·제외: 실제 기술 채택 없음. Wheelkit 2.0을 목표 지정 대체재로 삼는 안과 1.x를 현행 지원으로 보는 안은 제외. 이동·캐릭터·멀티 구조는 사용자 범위에 따라 제외. 전체 3D 입력·CSS 축소·자체 물리는 손익을 비교한 대안으로 유지.
- 한계·신뢰도: 버전별 문서 차이에 대한 신뢰도는 높음(합성 문서 내부에서만). 구조 제안은 중간, 실제 동작·성능·비용·시각 품질은 낮음. 실제 제품의 성능·추천 근거가 아니다.
- Idea 변경: 원요청·제약·제외 보존. 구조·제작 방법을 사용자 확정 결정으로 옮기지 않고 제안으로 연결한다.
- Execution 영향: 규칙·터미널과 웹 표현 Phase 후보의 책임 연결 및 향후 검증에 영향. 실제 Phase/Build ID, 일정, 전체 Build 계획은 다음 대화까지 보류한다.
- 사용자 결정: 조사 범위만 승인됨. 이 비교와 보류 사항을 Research 결론으로 남길지 확인 전이며, 확인을 특정 기술·신규 기능·구현 승인으로 확대하지 않는다.
