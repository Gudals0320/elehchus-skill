# Idea: 룰렛·바카라·블랙잭 싱글 플레이 카지노

- 상태: 작성 중
- 현재 범위: 이번 대화는 Research 비교 결과와 보류 사항 확인까지다. 전체 Execution·Build 계획은 다음 대화로 미룬다. 제품 구현은 하지 않는다.
- 단계 처리: 상위 구성과 아래 명시적 사용자 답은 승인됐다. 세칙·UX가 남아 있으므로 Idea 전체 closure나 구현 가능한 계약의 확정을 선언하지 않는다. 사용자가 지금 디자인·제작 방법 조사를 명시했으므로 미결정을 보존한 채 Research를 진행하며, 진행 여부를 다시 묻지 않는다.
- 시작 요청: 룰렛·바카라·블랙잭을 할 수 있는 게임을 만든다. 룰을 적당히 합의한 뒤 터미널 기반 카지노 로직을 먼저 구현하고, 이후 3D 애니메이션이 구현된 웹앱 게임으로 이어 간다. 디자인 고찰과 레퍼런스 탐색이 중요하다. 게임 시작 시 초기 자금을 정하고 파산하면 게임 오버, 그렇지 않으면 계속 진행한다. 저장은 현재 필요 없다. 싱글 구현을 우선하며 미래 멀티플레이를 고려해 카드게임은 6덱 구성을 생각한다.

## Topology

원래 분해 제안은 사용자가 세 게임·세션 자금·터미널·웹 표현에 한해 승인했다. T3는 이 범위를 위한 조사이며 추가 제품 기능이 아니다. T5는 미래 맥락으로만 남긴다.

| 구성요소 | 상태 | 책임·사용 표면 | 출처·근거 |
|---|---|---|---|
| T1. 세 게임의 규칙·카지노 로직 | 활성 | 싱글 제로 룰렛, 각각 독립된 6덱 바카라·블랙잭의 진행과 정산 | 사용자 요청 및 현재 세부 답변 |
| T2. 세션 자금·터미널 싱글 플레이 | 활성 | 초기 자금 입력 → 세 게임에서 함께 사용 → 파산 시 게임 오버, 그 외 계속 진행 → 세션 종료 시 미보관 | 사용자 요청 및 현재 세부 답변 |
| T3. 디자인·3D 애니메이션 조사 | 활성 | 시각적 방향, 레퍼런스, 애니메이션 제작 방법과 터미널 로직 연결 검토 | 사용자 요청: “3D animation을 어떻게”, “디자인에 대한 고찰 및 레퍼런스 탐색” |
| T4. 애니메이션 웹앱 | 활성 | 터미널 단계 이후 세 게임을 웹앱으로 제공 | 사용자 요청: “터미널 기반 구현 -> 애니메이션 구현된 웹앱 게임 구현” |
| T5. 멀티플레이 | 보류 | 미래 맥락만 유지. 현재 서버·접속·좌석·동기화 기능과 별도 확장 계획은 만들지 않음 | 사용자 응답: “멀티는 미래 맥락으로만” |

## 명료도

| 활성 구성요소 | 목표 | 제약 | 성공 기준 | 맥락 |
|---|---|---|---|---|
| T1 | 확정 | 부분확정: 게임 종류·기본 룰 확정, 세칙 유보 | 부분확정: 정산·자금 흐름, 상세 판정 유보 | 확정: 싱글, 카드게임별 독립 6덱 |
| T2 | 확정 | 부분확정: 공유 자금·미보관 확정, 입력 단위 유보 | 부분확정: 파산 종료, 입력 실패·종료 세부 유보 | 확정: 혼자 Windows PC |
| T3 | 확정: 사례·상호작용·제작 방법 비교 | 확정: 합성 문서 한정, 구현·새 계정·유료 사용 없음 | 확정: 비교 결과와 미정 선택을 구분해 제시 | 확정: 문서만 있고 실제 화면·영상 없음 |
| T4 | 확정 | 부분확정: 데스크톱 Chrome 우선, 표현 역할 미정 | 부분확정: 카드·숫자 가독성, 관찰 기준 세부 유보 | 부분확정: 스택 없음, 제작 방식 미선택 |

목표 초안: 혼자 Windows PC에서 입력한 세션 자금을 세 게임에 함께 사용하고 파산하면 종료하는 싱글 카지노를 터미널로 먼저 만든 뒤, 테이블 주변 여유와 카드·숫자 가독성을 갖춘 애니메이션에 가까운 3D 느낌의 데스크톱 Chrome 웹앱으로 이어 간다. 사용자 진술을 묶은 문장이며 Idea 전체 확정은 아니다.

## 확인된 사실

- 프로젝트 지침에 따라 이번 세션은 계획만 작성한다. Release 확인은 이전 턴에 완료되었고 현재 버전 사용이 선택되어 반복하지 않는다.
- 네트워크·브라우저·subagent는 이번 실행에서 사용하지 않는다.
- `evidence/README.md`에 따르면 `evidence/` 자료는 가상 제품의 합성 문서다. 실제 제품의 사실·성능·추천 근거로 바꾸지 않는다. 스크린샷·영상·실행 가능한 데모는 없으며 문서 속 코드도 실행·측정 결과가 아니다.
- 2026-09-07 저장소 기준선: 일반 프로젝트 파일 목록에서 제품 후보는 `app.txt`였으며 본문은 `UNIMPLEMENTED PRODUCT STUB`뿐이다. 구현·의존성·테스트·기술 스택을 뒷받침하지 않는다. 인증정보·사용자 설정은 읽지 않았다.

## 사용자 결정

- 출처: 사용자 요청. 게임은 룰렛·바카라·블랙잭 3종이다.
- 출처: 사용자 요청. 터미널 싱글 구현을 먼저 하고 애니메이션 웹앱으로 이어 간다.
- 출처: 사용자 요청. 시작할 때 초기 자금을 정하며, 파산하면 게임 오버이고 그 외에는 계속 진행한다.
- 출처: 사용자 요청. 바카라와 블랙잭은 각각 독립된 6덱이다. 룰렛은 싱글 제로다. 바카라는 플레이어/뱅커/타이와 뱅커 5% 커미션, 블랙잭은 더블·스플릿까지 포함한다. 세칙·셔플 시점·베팅 단위는 구현 전에 별도로 합의한다.
- 출처: 사용자 요청. 혼자 Windows PC에서 쓰며 웹은 데스크톱 Chrome을 우선한다. 실제 현금·결제는 없고, 사용자가 초기 자금을 입력해 세 게임에서 함께 쓰며 세션 종료 후 보관하지 않는다.
- 출처: 사용자 요청. 카지노 이동·캐릭터 조작은 필요 없다. 플레이어·딜러 캐릭터도 필요 범위에 넣지 않는다. 테이블 주변 여유 공간과 카드·숫자 가독성, 실사보다 애니메이션에 가까운 3D 느낌을 원한다.
- 출처: 사용자 요청. 카메라·구도·색·재질과 텍스트/버튼·3D의 역할은 사례를 보고 선택한다. 특정 엔진·라이브러리는 필수가 아니다. 기술 구조는 조사 근거 뒤 제안한다.
- 출처: 사용자 요청. 조사와 그 범위의 역할 분담은 허용됐다. 다만 이번 환경에서는 subagent를 사용하지 않으며 메인 세션이 조사한다. 이번 응답에서 Research 결론과 미정 선택을 확인하고 전체 Build 계획은 다음에 이어 간다.
- 출처: 사용자 요청. 룰 합의보다 디자인·3D 애니메이션 접근과 레퍼런스 탐색에 더 많은 고찰이 필요하다.

## 에이전트 제안

- Topology의 승인 범위는 위와 같다. 조사는 [R001: 화면·상호작용](research/R001-table-interaction.md), [R002: 애니메이션 제작·연결](research/R002-animation-method.md)로 나눈다. 조사 문서 분리이며 제품 기능 추가가 아니다.
- 출처: 에이전트 제안, 미승인. 사례 비교로 얻은 표현·구조 후보와 채택/제외 이유는 각 Research에만 기록한다. 권장 후보를 사용자 취향이나 선택한 기술로 바꾸지 않는다.

## 구현 위임

- 조사 범위는 승인됐고 제품 구현 위임은 없다. 내부 구조도 현재는 근거를 가진 제안으로만 다룬다.

- 출처: 프로젝트 지침 및 elenchus 계획 경계. 이번 계획 인터뷰에서 제품을 구현하지 않는다.

## 미확인·충돌

- 다음 질문: 비교 결과와 미정 선택을 제시한 뒤, 그 범위를 이번 Research 결론으로 확인한다. 구체적 취향·기술 선택이나 전체 Build 승인을 함께 요구하지 않는다.
- 남은 제품 결정: 게임별 세칙·배당·커미션 반올림·셔플 시점·베팅 단위·초기 자금 입력 범위, 파산 판정 경계, 게임 전환 조작, 잘못된 입력과 종료·재시작 흐름. 사용자가 구현 전 합의로 유보했다.
- 남은 디자인 결정: 정확한 시점·구도·색·재질, 3D 표현 대상, HTML/3D 조작 분담, 애니메이션 중 입력·속도·건너뛰기 여부, 구체적 가독성 판정 조건. 건너뛰기·확대 등 사례 기능을 자동 추가하지 않는다.
- 남은 제작 결정: 실제 에셋 제작·조달 방법과 사용권·비용, 엔진/라이브러리, 사용자 PC 성능·목표 화면 크기. 자료 밖 스택·자산을 선정하거나 설치하지 않는다.
- 화면·영상·실행 데모가 없으므로 시각적 적합성과 실제 조작감·Chrome 성능은 보류한다. 후속 시각 검토·검증 필요 사항은 각 R###에 기록하며 이번에 Lab이나 제품을 만들지 않는다.
- 기존 미확인 중 게임 간 슈 공유 여부·자금 연속성·현금 연동 여부·지원 환경은 현재 사용자 답으로 대체됐다. 기존 Topology 재확인 질문도 해소됐다.
- 직접 충돌은 확인되지 않았다. Research 진행 승인은 특정 제안·취향·기술이나 Idea/Research 전체 확정 승인이 아니다.
