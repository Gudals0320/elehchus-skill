# Research R002: 불확실한 날짜와 중복·유사 사진을 어떻게 판단하게 도울 것인가?

- 상태: 작성 중
- 기준: [Idea](../idea.md)
- 확인 날짜: 2026-09-07
- 영향: Phase 후보. 전체 실행 계획과 화면 취향은 미합의다.

## Repository 기준선과 Neutral brief

관찰: 사용자가 날짜 탐색·큰 비교·직접 선택을 명시했으나 날짜 fallback이나 비교 조작은 정하지 않았다. 기존 Idea에 상세 구현 계약은 없었다. README는 문서 설명과 코드 조각이 실제 관찰·실험이 아님을 명시한다. 관련 제품 코드 분석은 이번 문서 조사와 무관하여 생략했다.

| 항목 | 중립 조건 |
|---|---|
| 입력 | Windows의 JPEG·PNG·HEIC 약 5만 장, 촬영일 누락·오류, 복수 로컬 드라이브·외장 SSD |
| 출력 | 날짜 해석·큰 비교·중복 후보 제시의 대안과 제작 방법, 오탐·지원 공백 |
| 사용자 경험 | 날짜로 훑고 사진을 나란히 크게 비교해 사용자가 정리·삭제 대상을 직접 판단 |
| 성공 조건 | 불확실한 날짜를 정확한 촬영일로 오인시키지 않고 비교에 필요한 차이를 보여 주는 방향을 설명 |
| 실패 조건 | 파일 날짜를 실제 촬영일로 확정, 유사도만으로 삭제, 중복 검출을 사용자 선택의 대체로 사용 |
| 확정 제약 | 적용 전 원본·메타데이터 변경 금지. 계정·클라우드·공유·얼굴 인식·사진 편집 제외. 개인 사진 접근·유료 호출 금지 |
| 객관적 환경 | 합성 문서만 제공. 네트워크·브라우저·subagent 없음 |
| 미해결 | 날짜 불명 그룹·임시 정렬·보정 저장 정책, 비교 조작, 유사도 기준, HEIC 렌더링·성능 |

사용자 기술 언급 분류: Windows·형식은 필수 지원 목표, 규모·날짜 오류는 현재 맥락, digiKam은 예시이므로 neutral brief의 기술 조건에서 제외한다. 특정 유사도 엔진·DB·메타데이터 도구는 지정되지 않았다.

## 후보와 핵심 차이: 날짜 경험

| 방식 | 참고 근거 | 얻는 결과 | 잃는 것·한계 | 권장 여부 |
|---|---|---|---|---|
| 사용자가 촬영일·파일 날짜를 선택 | S01 | 정렬 기준을 직접 바꿀 수 있음 | 날짜가 없는 파일과 잘못된 값의 해결을 별도로 정해야 함 | 선택지로 유지, 기본값 미정 |
| 촬영일 우선, 누락 시 파일 날짜를 임시 사용하고 출처 표시 | S04 | 날짜 자료가 부족해도 연속 탐색 가능 | 복사·편집 날짜가 사진의 실제 순서를 왜곡할 수 있음(S08) | 출처 표시는 참고하되 fallback 정책을 자동 채택하지 않음 |
| 날짜 불명·의심 항목을 따로 모음 | 에이전트 제안, S08의 불확실성에서 도출 | 잘못된 날짜를 확정하지 않음 | 한 타임라인에서 모두 자연스럽게 훑는 경험이 줄고 수동 판단 증가 | 동등한 대안, 사용자 취향 미정 |
| 사용자가 정한 날짜를 앱 내부 보정값으로 분리 저장 | S08은 별도 저장소 또는 sidecar 선택을 앱에 맡김. 내부 저장 우선은 에이전트 제안 | 원문을 유지하며 사용자가 정리 기준을 정할 여지 | 보정·되돌리기·원본 적용의 의미를 정해야 함 | 보정 기능 자체와 UX는 미승인. 채택 시 적용 전 원본 쓰기 금지 |

공통으로 권하는 것은 **원문 날짜·해석한 값·출처·시간대 유무와 사용자 보정값을 섞지 않는 것**이다. 출처: 에이전트 제안, S08의 반환 구조와 S04의 출처 배지 참고. 날짜가 존재한다는 사실은 정확하다는 증거가 아니며, 시간대가 없으면 임의 시간대를 사실로 확정하지 않는 방향이다. 자동 시계 보정·날짜 추정 기능은 추가하지 않는다.

## 후보와 핵심 차이: 중복·유사 사진 비교

| 방식 | 근거와 실제 차이 | 사용자 결과·한계 | 현재 판단 |
|---|---|---|---|
| byte 동일 후보 | S03은 byte hash로 중복 가져오기를 건너뜀. S07은 내용 hash로 byte 동일 파일을 묶음 | 파일 내용의 동일성 후보와 크롭·압축·메타데이터가 다른 파일을 구별 | 후보 분류의 참고. 사용자가 요구한 직접 비교·삭제 선택을 건너뛰지 않음 |
| perceptual hash 근처의 유사 후보 | S07은 별도 유사 후보로 제시 | 축소·크롭본도 들어오며 같은 색 배경의 다른 이미지도 가까운 점수 가능. 후보 제한으로 누락 가능 | 비교 대상을 줄이는 도구로만 제안. 동일 사진 판정·자동 삭제 근거로 사용 불가 |
| 수동 큰 비교부터 제공 | 에이전트의 축소 대안, S07의 비교 흐름 참고 | 유사도 계산·색인 부담을 줄이며 사용자의 직접 판단을 지원 | 대규모 후보 발견은 수동 부담 증가. 원요청의 유사 후보 발견을 약화할 수 있어 미승인 |
| 제품을 만들지 않고 비교 도구 활용 | S07형 문서 사례 | 별도 삭제 구현 없이 판단 보조 가능 | 해당 사례는 CSV만 내보내며 통합 폴더·날짜 탐색·원본 정리를 충족한다고 확인되지 않음 | 전체 대체안으로 확정할 근거 부족 |

S07의 **두 장 나란히 보기 + 해상도·용량·경로 + 동기 확대**는 큰 비교 경험의 유력한 참고다. 같은 크기로 축소한 화면만으로 원본 세부를 놓쳤다는 제작자의 문제 설명이 근거다. 직접 화면을 보거나 조작한 결과가 아니므로 편리함이 입증됐다고 말하지 않는다. 동기 확대·정보 항목의 구체적 배치는 에이전트 제안으로 남긴다.

S07의 CSV는 원문 제품의 산출물일 뿐, 사용자 앱의 CSV 내보내기 기능으로 추가하지 않는다. 얼굴 인식·편집·클라우드 분석은 후보로 넣지 않는다.

## 후속 검증과 Web closure

로컬 합성 원문 범위의 주장·반례·접근 경로 점검은 완료했다. 실제 웹·화면·실험 검증 완료는 아니다. 아래 고영향 공백을 연기했으므로 성능·기능 적합성의 무조건 결론으로 닫지 않는다.

| 미확인 주장 | 후속 검증 후보·의미 | 채택 불가·실패 조건 |
|---|---|---|
| 날짜 해석·출처가 정확히 보존됨 | 비개인 fixture로 날짜 누락·시간대 없음·파싱 실패·충돌하는 날짜를 점검 | 원문 유실, 임시 파일 날짜를 실제 촬영일로 표시, 읽기 중 원본 쓰기 |
| JPEG·PNG·HEIC를 큰 비교에 적절히 표시 | 형식·회전·색·축소본/원본을 구분해 디코더와 화면을 검증 | HEIC 누락, 방향·세부 정보 오류, 미리보기를 원본 품질로 오인 |
| 유사 후보의 품질과 탐색 부담이 허용 가능 | byte 동일·메타데이터 차이·축소·크롭·같은 배경의 다른 사진을 포함한 라벨 자료로 누락·오탐·시간·메모리를 확인 | 기준 미합의, 필요한 후보 누락·과다 오탐, 자동 삭제 경계 침범 |

수치 기준은 사용자가 정하지 않았으므로 만들지 않았다. 이번에 Lab을 실행하거나 fixture를 생성하지 않았고, 이 검증을 실행 계획에 확정 편입하지 않았다.

## Verdict

- **판정: 결론 가능 — 날짜의 근거를 보존하고 byte 동일 후보·시각 유사 후보·사용자 최종 선택을 분리하는 설계 원칙.** 출처: 에이전트 제안, 미승인. 사용자가 이미 확정한 자동 삭제 금지는 그대로 유지한다.
- 근거: S08의 날짜 출처·시간대 구조, S03·S07의 파일 동일성과 시각 유사성 차이, S07의 큰 비교 개선 이유.
- 반대 근거: 파일 날짜 fallback은 편하지만 실제 순서를 왜곡할 수 있다. 후보 축소는 계산을 줄이지만 누락·오탐을 남긴다. 큰 미리보기는 저장 공간이 들며 SSD 분리 때 원본 세부를 제공하지 못할 수 있다.
- 채택·제외 근거: 근거 표시·나란히 비교는 사용자 판단을 지원한다. 시각 유사도 자동 삭제는 확정 조건과 충돌하여 제외한다. CSV·얼굴 인식·편집은 기능으로 추가하지 않는다.
- **판정: 결론 보류 — 기본 날짜 정책·보정 UX·구체 비교 조작·유사도 엔진·HEIC와 5만 장 성능.** 후속 사용자 결정과 위 검증으로 연결한다.
- 한계·신뢰도: 설계 원칙 **중간**. 개발자의 합성 설명과 짧은 코드만 있고 실제 UX·정확도·지원 검증은 없다.
- Idea에서 바꿀 내용: 원래 날짜 탐색·큰 비교·직접 선택은 유지. 날짜의 출처 표시·후보 구분·동기 확대는 미승인 제안으로만 남긴다.
- Execution에서 바꿀 Phase·Build: 번호·전체 계획은 없음. 날짜/디코딩/후보 품질 검증이 관련 기능 확정에 선행한다는 의존성만 제안한다. 수동 비교부터 만드는 축소안은 미채택이다.
- 사용자 결정: 조사 허용만 확인됐다. 이 정책·기능 제안에 대한 합의가 없어 문서 상태를 작성 중으로 유지한다.
