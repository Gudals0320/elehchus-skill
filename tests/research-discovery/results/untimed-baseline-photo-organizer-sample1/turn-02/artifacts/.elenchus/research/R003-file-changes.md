## Repository 기준선과 Neutral brief

관찰: 사용자의 안전 조건은 이동 채택 시의 목록 검토·실패 설명까지 명시하지만 이동 자체나 삭제·복구 방식을 확정하지 않는다. 02는 파일 작업 개발 설명이며 README상 실행 실험이 아니다. 원본 사진·파일시스템·제품 코드는 조사하지 않았다.

| 항목 | 중립 조건 |
|---|---|
| 입력 | 복수 드라이브·외장 SSD의 선택된 로컬 사진, 사용자가 나중에 명시 적용할 수 있는 정리 작업 |
| 출력 | 변경 경계·미리보기·중단 기록의 참고 방식, 안전 보장의 한계와 작은 대안 |
| 사용자 경험 | 적용 전 원본·메타데이터 유지. 이동을 채택하면 목록 검토 후 적용, 실패 시 원본과 진행 결과 파악 |
| 성공 조건 | 비교·날짜 정리와 원본 쓰기를 분리하고 부분 완료·실패를 설명할 수 있는 제작 방향을 제안 |
| 실패 조건 | 다른 드라이브 이동을 원자적 rename으로 취급, journal을 무조건 복구 보장으로 취급, 검토하지 않은 삭제·변경 |
| 확정 제약 | 사용자 직접 중복 선택, 시각 유사성 자동 삭제 금지, 계정·클라우드·공유·얼굴 인식·편집 제외, 실사진 접근·유료 호출 금지 |

사용자 기술 언급 분류: Windows는 필수 환경, 드라이브 구성은 입력 맥락, digiKam은 예시로 기술 전제에서 제외한다. 원본 폴더 직접 관리·보관함은 후보이며 journal·DB·파일 API를 사용자가 지정하지 않았다.

## 제작 방법과 원본 변경 경계

출처: 에이전트 제안. 아래는 S01·S02·S04·S08에서 도출한 조건부 제작 방향이며, 이동·보정·삭제 기능을 새로 확정하는 내용이 아니다.

1. **읽기·판단과 적용을 분리한다.** 탐색·날짜 읽기·후보 계산·비교 선택은 원본 파일과 원본 sidecar의 변경을 일으키지 않는 방향이다. S01은 날짜를 폴더 sidecar에 쓰므로 그 정책을 그대로 복제하지 않는다. S08의 보정값 저장 위치는 앱 책임이며 별도 로컬 저장을 후보로 둘 수 있다.
2. **이동을 고르면 원본·대상·작업을 먼저 보여 준다.** S01은 충돌 시 덮어쓰기 대신 건너뛰기·이름 변경을 선택하게 한다. 이 충돌 처리 방식은 유력한 참고지만 기본 정책을 사용자 대신 확정하지 않는다. 대상을 아직 읽을 수 없거나 공간 확인이 안 되면 실행 가능하다고 표시하지 않는 제안을 남긴다.
3. **실행 시 계획을 다시 확인한다.** S02처럼 계획 당시와 다른 원본은 보류 대상으로 다룬다. 계획 이후 외부 변경·대상 충돌·SSD 분리·용량 변화를 확인해야 한다는 설계 제안이며, 단순 경로·크기만으로 동일 파일임을 완전히 보장한다고 주장하지 않는다.
4. **다른 드라이브 이동은 복사·확인·원본 제거를 각각 기록한다.** S02의 단계 분리가 직접 근거다. 사본을 확인하기 전 원본 제거로 진행하지 않고, 어느 단계가 끝났는지 항목별로 남기는 방향을 제안한다. 확인 방법·기록의 내구성·파일시스템별 보장은 별도 검증 대상이다.
5. **실패 결과를 경로와 상태로 설명한다.** 원본이 남았는지, 대상 사본이 확인됐는지, 무엇이 미완료·실패인지 보여 주는 것이 사용자가 요구한 결과다. 로그 파일만 남기는 것으로 충분한지는 확인되지 않았다. 결과 요약과 재시도/재검토 경계의 화면은 다음 계획에서 정한다.
6. **재개는 같은 삭제를 반복하지 않게 설계한다.** S02의 완료 항목 재삭제 방지 설명을 참고한다. 기록만 믿지 않고 현재 파일 상태를 대조해야 한다는 것은 에이전트 제안이다. 상태가 애매하면 성공·원상복구라고 단정하지 않아야 한다.

원본 제거가 포함된 이동 승인은 목록에 표시된 그 작업 범위에 한정된다. 일반 삭제·메타데이터 일괄 쓰기의 승인으로 확대하지 않는다. 중복 삭제는 사용자가 후보를 나란히 비교해 고른다는 조건을 유지한다.

동일 드라이브 rename의 속도·특성과 다른 드라이브 이동, 여러 항목 전체의 원자성을 구분한다. journal은 작업을 추적·재개하는 설계 재료이며 백업이나 무조건적인 rollback 보증이 아니다. S02도 완전 복구를 선언하지 않는다. 구체적인 기록 순서·디스크 반영·중단 지점 대응은 공개 구현 전체나 실제 실험 없이 확정할 수 없다.

2. 원본 쓰기 위험 때문에 04의 읽기 전용 경계와 08의 보정값 저장 책임을 대조했다. 별도 정보 저장이 가능하다는 방향은 얻었지만 특정 앱의 실제 무변경 증거는 얻지 못했다.
3. 03의 휴지통·중복 정책을 원래 폴더에 확대하지 않았다. 사용자에게 보이지 않은 삭제·보관 정책을 확정하지 않는 결론으로 제한했다.
4. 동일 팀 문서 두 개는 독립 실패 재현이 아니다. 실제 구현·파일시스템의 고영향 공백은 남아 있으므로 이동 안전 보장 자체는 보류한다.
5. 현재 제공된 관련 본문은 모두 확인했다. 재독·형식적인 mock으로 실제 파일 작업 보장을 얻을 수 없으며, 후속 구현 검증이 생기면 결론이 바뀔 수 있다.

## 후속 검증과 Web closure

합성 원문 범위의 본문·반례·출처 계보·접근 기록 점검은 완료했다. 실제 공개 구현 안전성·파일시스템 복구에 관한 Web closure나 Lab 검증이 끝났다는 뜻은 아니다. 다음 공백은 명시적으로 연기하고 무조건 결론에서 제외한다.

| 검증할 주장 | 이동을 채택할 경우의 후속 검증 후보 | 채택 불가·실패 조건 |
|---|---|---|
| 적용 전 원본·메타데이터 무변경 | 비개인 통제 파일로 등록·날짜 읽기·후보 계산·비교 중 파일 및 sidecar 변경 여부 확인 | 적용 전 원본 바이트·메타데이터·sidecar 변경 |
| 다른 드라이브 중단 상태를 설명 | 복사 중, 사본 확인 뒤, 원본 제거 전후, journal 갱신 경계에서 중단하고 원본·대상·기록 대조 | 원본 제거 후 사본 확인 불가, 실제와 다른 성공 표시, 상태 미상 은폐 |
| 재개가 이미 한 삭제를 반복하지 않음 | 각 중단 상태에서 다시 시작하고 현재 파일 상태·기록을 함께 점검 | 잘못된 재삭제·덮어쓰기·작업 중복 |
| 계획 이후 변경을 안전하게 다룸 | 외부 파일 변경·동일 이름 대상 생성·디스크 공간 부족·권한 오류·SSD 분리·경로 변경 | 오래된 계획을 그대로 적용하거나 다른 파일에 작업 |
| 취소·부분 성공·삭제·복구 정책이 이해 가능 | 사용자와 각 행동·보관 범위를 먼저 합의한 후 장래 화면과 실제 결과 대조 | 취소를 전체 되돌리기로 오인, 휴지통 정책 미합의, 기록과 원본 상태 불일치 |

이 항목은 향후 검증 주제이며 실행 명령이나 확정 Build가 아니다. 실제 개인 사진을 쓰지 않았고 Lab·파일 이동·삭제·원본 쓰기 실험은 하지 않았다. 실제 격리·도구 출력 경계와 시간·비용은 실행 가능한 단계에서 확인해야 한다.

## Verdict

- **판정: 결론 가능 — 원본 읽기·판단과 명시 적용을 분리하고, 이동 채택 시 계획 목록·실행 전 재확인·항목별 작업 기록을 참고하는 방향.** 출처: 에이전트 제안, 미승인. 적용 전 원본 보호와 사용자 직접 선택은 기존 사용자 조건이다.
- 근거: S01·S02의 검토·단계·중단 기록, S04·S08의 원본 쓰기와 앱 내부 정보 저장 분리.
- 반대 근거: 같은 제품의 초기 실패와 개발 문서 자체가 원자성·완전 복구의 한계를 인정한다. 기록이 있어도 파일시스템·외부 변경·원본 제거 시점 검증이 필요하다. S03의 보관함 정책은 기존 폴더 책임을 해결하지 않는다.
- 후보·제외: 이동을 제공하는 방향과 읽기·비교까지만 먼저 만드는 방향을 동등하게 남긴다. 즉시 변경·일괄 원자성 가정·무조건 rollback·시각 유사성 자동 삭제는 제외한다. 이동 연기나 휴지통 기간은 새로 확정하지 않는다.
- **판정: 결론 보류 — 실제 이동·삭제·메타데이터 쓰기의 안전성, 취소·재개·복구 보장과 정책.** 위 실패 검증과 사용자 결정으로 연결한다.
- 한계·신뢰도: 참고 패턴의 조건부 권고는 **중간**. 안전 보장의 실증 신뢰도는 낮음/미확인이다. 합성 설명만으로 실제 데이터를 맡길 수 있다고 결론내리지 않는다.
- Idea에서 바꿀 내용: 기존 적용·비교 조건을 유지한다. 이동·삭제·복구의 정책 미결정과 조건부 제안만 남긴다.
- Execution에서 바꿀 Phase·Build: 번호·전체 실행 계획은 없음. 이동을 채택하면 실제 원본 작업을 가능하다고 판단하기 전에 원본 무변경·중단·재개 검증이 필요하다는 의존성을 제안한다. 미채택 시 이 구현 범위를 연기하는 대안이 있다.
- 사용자 결정: 조사 진행과 기존 안전 조건은 확인됐다. 조건부 흐름·기능 채택·복구 범위는 아직 합의되지 않아 작성 중 상태를 유지한다.
