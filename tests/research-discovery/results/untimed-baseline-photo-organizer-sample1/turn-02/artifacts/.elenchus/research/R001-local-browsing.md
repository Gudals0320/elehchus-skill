# Research R001: 여러 위치의 사진을 어떻게 모아 보고 연결이 끊겨도 탐색할 것인가?

- 상태: 작성 중
- 기준: [Idea](../idea.md)
- 확인 날짜: 2026-09-07
- 영향: Phase 후보. 이번에는 전체 실행 계획을 만들지 않는다.

## Repository 기준선과 Neutral brief

관찰: 기존 `.elenchus/idea.md`에는 시작 요청과 빈 범위 항목이 있었다. 현재 사용자의 상세 응답을 반영했다. `evidence/README.md`는 전 자료가 합성이며 화면·영상·실행 데모가 없다고 명시한다. 제품 코드·설정은 이번 문서 비교와 무관하여 탐색하지 않았다. 기존 제품 구현 유무도 단정하지 않는다.

| 항목 | 중립 조건 |
|---|---|
| 입력 | Windows PC, 여러 로컬 폴더, 두 드라이브와 외장 SSD, JPEG·PNG·HEIC 약 5만 장 |
| 출력 | 모아 보기·저장 방식의 대안, 사용자 경험과 제작 방법의 차이, 조건부 권고와 근거 공백 |
| 사용자 경험 | 혼자 인터넷 없이 탐색, 날짜로 훑기와 큰 비교, SSD 분리 시 이전에 본 사진 정보 검색 |
| 성공 조건 | 위치가 달라도 함께 탐색하고 저장 정보가 SSD 분리 때문에 사라지지 않는 방향을 설명하며 원본 적용 경계를 지킴 |
| 실패 조건 | 분리된 파일을 검색에서 누락, 원본 복사·이동이나 계정·비용을 동의 없이 필수화, 합성 자료를 실제 제품 검증으로 제시 |
| 확정 제약 | 적용 전 원본·메타데이터 무변경. 계정·클라우드 업로드·공유·얼굴 인식·사진 편집 제외. 실제 개인 사진·유료 호출 불허 |
| 객관적 환경 | 로컬 문서 읽기와 계획 문서 쓰기 가능. 사용자 환경 지침상 네트워크·브라우저·subagent 미제공 |
| 미해결 | 화면 취향, 원본 복사 여부, 오프라인 미리보기 수준, 공간·성능 예산, 실제 코덱·배포 지원 |

사용자 기술 언급 분류: Windows는 필수 환경, 형식·규모·드라이브는 현재 입력 맥락, digiKam은 예시이며 후보 평가의 전제에서 제거했다. 폴더 직접 관리·별도 보관함은 비교 후보이지 필수 구조가 아니다. 엔진·DB·제품 필수 지정은 없다.

폴더 화면·날짜 타임라인은 탐색 방식이고, 원본 참조·원본 복사는 저장 방식이다. S01·S03·S04에서 서로 다른 조합이 기술되므로 둘을 하나의 양자택일로 묶을 근거가 없다. 초기 화면의 선호는 권장안 없이 미정으로 둔다.

## 제작 방법과 책임 경계

출처: 에이전트 제안. S04의 참조 패턴을 참고하여 **선택한 원본의 읽기 → 앱 내부 정보 저장 → 날짜·폴더 탐색과 비교**를 분리하는 방향을 우선 제안한다. 원본 변경은 [R003](R003-file-changes.md)의 별도 명시 적용 경계에서 다룬다. 제품 구조의 확정이나 구현 지시가 아니다.

- 원본 위치와 볼륨 식별·상대 경로, 저장 정보의 갱신 시각을 연결하는 방식은 S04에 기술되어 있다. 드라이브 문자만으로 위치를 판단하지 않는 설계의 참고가 된다. 재연결 정확성이 입증된 것은 아니다.
- 저장된 정보의 탐색과 원본 파일의 접근 가능성을 구별해야 한다. 원본 연결 상태와 저장 정보의 시점을 표시하는 제안은 정보가 최신이라는 오인을 줄이지만, 재연결·갱신 처리 부담이 생긴다.
- 작은 미리보기만 보관할지 큰 비교용 미리보기도 보관할지는 사용자 결정이다. SSD 분리 후 정보 조회 요구를 원본 크기 오프라인 열람 요구로 확대하지 않는다. 앱 캐시·카탈로그 쓰기는 원본·원본 sidecar 쓰기와 별도로 설명한다.
- S04에 SQLite가 등장하지만 이것만으로 특정 DB 채택을 정당화할 수 없다. DB·색인 엔진의 비교는 실제 쿼리·갱신·복구·배포 조건을 확인한 뒤 수행한다.
- S01의 OS 확장 의존 HEIC 처리와 S03의 디코더 동봉은 서로 다른 배포 전략이다. 코덱 설치가 필요한지, 인터넷 없이 준비 가능한지, 배포 권리·비용이 어떤지는 현재 확인하지 못했다. 무료 또는 무설치 지원을 약속하지 않는다.
- 약 5만 장의 등록·썸네일·스크롤·검색에는 지연·캐시·재검색 설계 검증이 필요하다. 점진적 등록·필요한 화면만 렌더링하는 방식은 검토할 내부 전략이며 이번 문서에서 측정된 결과가 아니다.

## Verdict

- **판정: 결론 가능 — 합성 자료에서 참고할 설계 방식에 한정.** 원본을 제자리에 두고 앱 내부에 사진 정보를 저장하는 참조 카탈로그를 우선 검토할 것을 제안한다. 출처: 에이전트 제안, 미승인.
- 근거: S04의 분리된 드라이브 정보 검색·읽기 전용 경계가 사용자 요구에 맞고, 원본 복사를 필수로 추가하지 않는다.
- 반대 근거: 외부 이동·정보 노후화·캐시 보관 부담이 있다. 원본 사본을 통한 오프라인 원본 열람이 필요하면 S03형 보관함이 유리해질 수 있다.
- 제외: S01형 순수 폴더 스캔을 그대로 채택하면 SSD 분리 검색 요구를 충족하지 못한다. S06의 3.0 서비스 검색은 확정 제외와 충돌한다. 2.x도 패치 종료 고지가 있어 실제 사용 권고로 바꾸지 않는다.
- **판정: 결론 보류 — 실제 제품·엔진·DB·HEIC 배포·5만 장 성능의 채택.** 상단 후속 검증으로 연결했다.
- 신뢰도: 설계 비교·조건부 권고는 **중간**. 문서 간 차이는 직접 확인했지만 자료가 합성이며 사용성·성능 실증이 없다. 실제 제품 적합성은 낮음/미확인이다.
- Idea에서 바꿀 내용: 사용자의 제약은 그대로 유지한다. 저장 방식 제안과 오프라인 보관 수준의 미결정만 연결한다. 초기 화면·공간·비용은 확정하지 않는다.
- Execution에서 바꿀 Phase·Build: 현재 번호·전체 계획 없음. 추후 선택 시 형식·오프라인 식별·성능 검증 결과가 탐색 구조 확정에 선행해야 한다는 의존성만 제안한다.
- 사용자 결정: 조사 진행은 승인됐다. 이 Verdict의 구조·취향·검증 범위는 아직 합의받지 않았다. 따라서 문서 상태는 작성 중이며 전체 계획 합의로 넘어가지 않는다.
