## Repository 기준선

루트 목록, `app.txt`, 기존 `.elenchus/idea.md`, `evidence/README.md`를 읽기 전용으로 확인했다. `app.txt`는 미구현 표시뿐이며 확인한 루트에는 제품 소스·manifest·lockfile이 없다. 기존 화면·엔진을 재사용할 근거는 없다. 기존 Research와 Execution은 없다. 인증정보·사용자 설정·프로젝트 밖 설치본은 조사하지 않았다.

## 사용자 기술 언급 분류

- 현재 환경: Windows PC, 데스크톱 Chrome 우선. 모든 플랫폼 지원 또는 특정 버전을 확정한 뜻은 아니다.
- 필수 제약: 터미널 → 웹의 순서, 카드게임별 독립 6덱, 싱글 제로 등 게임 범위. 엔진·라이브러리 필수 지정은 없다.
- 후보/예시: HTML과 3D의 역할은 열린 선택이다. 조사에서 발견한 사례·도구는 후보일 뿐 neutral brief의 전제가 아니다.

| Pileplay (S06) | 테이블 전체와 주변 선반 일부. 화면 하단 행동 띠에 텍스트. 확대 중 게임 입력 잠금과 닫기 버튼. 토큰 색·높이를 과장하고 변경된 토큰만 움직임 | 주변 공간과 별도 정보 영역, 소품 식별 강조를 검토할 단서 | 주사위·토큰 비동기 보드게임이다. 작은 숫자가 많은 룰렛·동시 베팅·스플릿 패에 대한 증거가 없다. 선반·확대 기능·입력 잠금을 우리 기능으로 추가하지 않는다 |
| Orbitroom (S05) | 아바타로 홀 이동 후 테이블 가까운 카메라. 참가자·딜러 캐릭터. 가림 때문에 외곽선과 상단 패널 추가 | 공간을 넓히면 카드게임 외 제작과 가림 대응이 생기는 반대 사례 | 멀티 중심이고 로컬 싱글 미제공. 홀·좌석·캐릭터 제작은 현재 요청과 맞지 않아 현 범위에서 제외한다. 개월 수를 단일 테이블 개발 일정으로 환산하지 않는다 |

Tablehaven의 약 9초는 **베팅 클릭부터 다음 베팅 가능 상태까지의 기본 카드 라운드**이고 Flatfelt의 180ms는 **카드 한 장 공개**의 운영자 설정이다. 측정 단위·상황이 다르므로 속도 순위·권장 시간을 계산하지 않는다. 공개 생략, 다음 입력까지 결과 유지, 즉시 다음 베팅, 확대 중 입력 잠금은 각각 사례의 동작이며 사용자 확정 기능이 아니다. Tablehaven이 키보드만으로 전 과정 플레이를 지원하지 않는다는 사실은 혼합 HTML 구성만으로 접근성이 보장되지 않는 반례다. 사용자에게 새 접근성 지원 범위를 추가하거나 제외하지 않는다.

## Evidence matrix와 gap loop

Browser 관찰은 모든 Claim에서 없었다.

| Claim | 지지 근거 | 반대 근거 | Browser 관찰 | 적용 범위 | 상태 | 남은 공백·다음 처리 |
|---|---|---|---|---|---|---|
| U1 | S01의 3D+HTML, S06의 장면과 별도 행동 띠 | S04도 정보와 조작을 제공하므로 3D가 필수 해결책이라는 근거는 아님 | 없음 | 문서상의 서로 다른 두 사례에서 역할 분리 확인 | 확인 | 우리 화면의 구체 분담은 선택 보류 |
| U2 | S06의 주변 공간·소품 강조 | S06은 숫자/다중 베팅 미검증, S05는 캐릭터 가림 발생, 실제 이미지 없음 | 없음 | 토큰 식별 문제를 의식할 근거만 있음 | 근거 부족 | 세 게임의 실제 화면·조작 검증까지 구도/가독성 확정 연기 |
| U3 | S04의 CSS 구조와 개발자 제작량 설명 | 전체 3D 재질 없음, 동일 조건 제작비 측정 없음 | 없음 | 더 작은 제작 범주의 존재만 확인 | 범위 제한 | 3D 느낌을 줄일지 사용자 선택 필요. 비용 수치·일정은 미정 |
| U4 | S01·S04에 설정과 동작 설명은 있음 | S03은 재게시, S04는 선호 조사 아님. 9초/180ms의 측정 단위 다름 | 없음 | 사례 설정만 확인, 우리 선호로의 전환 불가 | 근거 부족 | 시간·생략·결과 유지·입력 잠금 선택을 실제 조작 비교 뒤로 연기 |
| U5 | S05에 공간 몰입 경험 설명 | 로컬 싱글 미지원, 별도 공간 작업·가림 발생, 사용자가 해당 기능 불필요라 명시 | 없음 | 현재 요청에 대한 적합성 | 반박 | 공간 이동·멀티 제작은 현재 제외, 미래 맥락만 보존 |

쟁점별 재검증 기록:

1. 사례 본문 검토 후 가장 가까운 Tablehaven의 설명을 S03과 대조했다. S03은 독립 관찰이 없으므로 근거를 늘리지 않았다. S02에서 탭 복귀와 빠른 생략 경계를 확인해 연출 생략이 공짜로 안전해진다는 해석을 배제했다.
2. 공간감과 가독성의 연결이 가장 큰 UX 공백이라 S05·S06의 `가릴`, `구분하기 어려워`, `작은 숫자` 부분을 재확인했다. 주변 공간·소품 강조는 단서지만 카지노 화면에서의 성공 증거는 없었다.
3. 제작 축소와 리듬을 S04 및 S01의 단위·작성 주체와 대조했다. 비용 우위와 선호를 측정 결과로 바꾸지 않았다.
4. 관련 로컬 원문은 모두 확보했다. 필요한 다음 증거는 같은 문서의 재검색이 아니라 실제 화면·조작 또는 후속 후보 검증이다. 누락된 시각 자산과 미지원 연결 때문에 현재 실행할 추가 관련 경로가 없다. 미검증 사실을 확정하지 않고 아래에 보류한다.

## 후보와 핵심 차이

모든 추천은 출처가 에이전트 제안이며 미승인이다. 문서상 비교만으로 취향을 대신 결정하지 않는다.

| 대안 | 사용자가 얻는 것 | 부담·줄어드는 결과 | 맞는 조건·판정 |
|---|---|---|---|
| 작은 3D 테이블/소품 + 별도 정보·조작 영역 | 3D 공간과 카드·숫자/행동 표시를 각각 조정할 수 있는 후보 | 장면과 UI의 면적·상태를 함께 설계해야 함. 가독성·제작 우위 미측정 | 3D 느낌을 유지하면서 숫자·버튼을 또렷하게 비교하고 싶을 때. 현재 범위에 가장 가까운 **우선 비교 제안** (S01·S06). 구체 카메라·우측/하단 배치는 미정 |
| 같은 작은 3D 장면에서 베팅 대상을 직접 선택 | 소품과 조작 위치를 맞추는 후보 | 작은 숫자의 클릭 영역·가림·각도·스플릿 확장 등을 검증해야 함 | 공간에서 직접 조작하는 느낌이 더 중요할 때. **미검증 에이전트 대안**이며 이를 입증한 카지노 사례는 묶음에 없음. R001 종료를 위해 임의 채택하지 않음 |
| HTML 이미지 + CSS 원근감으로 축소 | 모델·조명 없이 카드와 숫자 흐름을 비교할 수 있는 더 작은 제작 범주 | 완전한 3D 공간·재질 표현을 잃음. 실제로 더 빠른 제작인지 수치 근거 없음 | 입체감의 일부를 줄여도 좋다고 사용자가 선택할 때. 원목표를 바꾸므로 자동 채택하지 않음 (S04) |
| 카메라·재질·조작 분담의 결정을 연기 | 실제 사례/검증 화면을 보고 취향을 고를 수 있음 | 전체 실행 계획의 화면 세부를 지금 확정할 수 없음 | 자료에 시각 자산이 없는 현재 조건에 권장. 제품 기능 추가 없음 |
| 홀·아바타·멀티 공간까지 제작 | 공간 이동·다른 사람과의 경험 | 현재 필요 없는 제작과 조작·가림 문제 | 사용자 제외와 충돌하여 현 범위에서 제외 (S05). 미래 멀티 맥락을 제거하는 뜻은 아님 |

카메라의 탑뷰/사선 각도, 구체 여백 비율, 색 팔레트, 목재·펠트·금속 등 재질에는 **권장안 없음**. 문서의 목재·선반을 선호 근거로 쓰지 않는다. 애니메이션풍 3D라는 사용자 목표만 유지한다.

## 보류 선택과 후속 확인

| 미정 선택 | 바뀌는 사용자 경험 | 필요한 다음 근거·검증 제안 |
|---|---|---|
| 카메라·구도·주변 여백 | 공간을 보는 양과 카드/숫자 크기 | 같은 게임 상태의 복수 구도를 실제 화면으로 비교. 룰렛 번호, 바카라 합계, 블랙잭 스플릿 패가 읽히는지 확인. 이미지/화면 확보 전 확정 연기 |
| 색·재질·소품 크기 | 애니메이션풍 느낌과 패/칩 식별 | 실사/과장 정도를 보여 주는 실제 시각 비교. 합성 문서만으로 취향 추천 금지 |
| HTML과 3D의 정보·입력 분담 | 베팅과 더블/스플릿 등을 고르는 위치·방법 | 같은 행동을 UI 영역/장면에서 수행하는 조작 비교. 클릭 가림·작은 대상·입력 중 상태 혼동 점검 |
| 연출 속도·생략·결과 유지·입력 시점 | 기다림과 결과 이해, 다음 라운드 시작 | 게임별 조작 흐름 확인 후 선택. 9초/180ms를 기본값으로 옮기지 않음. 생략 기능 자체도 미확정 |
| 지원 창 크기·성능 기준 | 좁은 창에서 정보 누락·프레임 지연 | 대상 PC·Chrome과 사용 창 크기를 후속 합의하고 후보 화면에서 확인. 1600×900·1024px를 요구사항으로 복사하지 않음 |

위 검증은 **후속 검증 제안**이며 현재 Lab 실행이나 검증 Build의 확정이 아니다. 화면을 확보할 수 없으면 해당 UX 선택을 계속 연기한다. 자료 없는 부분을 구현 위임으로 넘기지 않는다.

## Web closure와 Verdict

- 판정: **결론 보류** — 최종 화면·조작 채택에는 U2·U4의 직접 UX 근거가 부족하다. 필요한 Browser Evidence가 미지원이므로 전체 Web closure 및 UX 확정을 완료했다고 보고하지 않는다.
- 지금 제시할 수 있는 비교 결론: 가상 자료에서는 작은 3D 테이블과 별도 정보/조작 영역의 결합이 사용자 조건에 가장 가깝다. CSS 원근 표현은 축소 대안이고 공간 이동형 제작은 현재 제외와 충돌한다. 이는 문서상 대안 정리이며 디자인 채택이 아니다.
- 근거: S01·S06의 공간/정보 분리, S04의 더 작은 표현 범주, S05의 불필요한 공간 작업과 가림. 모든 핵심 주장에 본문·날짜·범위 또는 근거 부족 상태를 연결했다.
- 반대 근거: 혼합 UI도 접근성·가독성을 자동 보장하지 않음. Pileplay는 카지노의 작은 숫자·여러 베팅을 검증하지 않음. Tablehaven과 재게시를 독립 검증으로 셀 수 없음.
- 한계: 합성 문서만 읽었고 화면·영상·조작·사용성·성능을 직접 관찰하지 않았다. 실제 제품의 도입·품질을 평가한 조사가 아니다.
- 신뢰도: **중간** — 문서에 적힌 후보 차이의 해석 기준. 최종 심미성·가독성·사용자 선호에는 **낮음/미검증**.
- 문서 증거 루프: Claim map·접근 기록·Evidence matrix·반대 근거·출처 계보 점검 완료. 본문 접근 실패는 없다. 누락 미디어와 예약 도메인의 접근 한계를 기록했다. 같은 문서 재검색은 핵심 UX 공백을 줄이지 못하므로 중단한다.
- 다음 행동: 실제 화면·조작 확인까지 미정 선택을 연기하는 Research 결과로 사용자에게 제시한다. 해당 보류를 받아들였다고 미리 기록하지 않는다. 현재 상태는 작성 중이다.

## Idea 변경과 Execution 영향

출처: 사용자 요청. 합의한 범위·제외·시각 목표·미정 선택을 Idea에 반영했다. 출처: 에이전트 제안. 위 비교와 보류 처리에는 아직 사용자 확인이 없다. 새 기능 추가나 기존 요구 삭제는 제안하지 않는다. CSS 축소를 선택한다면 줄어드는 3D 표현을 따로 합의해야 한다.

영향은 웹 표현·디자인의 Phase 후보에만 연결한다. 전체 Phase·Build·일정·승인 기준은 이번에 만들지 않는다. 후속 Execution은 실제 화면의 가독성·조작 검증을 처리하기 전 이를 완료된 근거로 참조할 수 없다. Lab은 실행하지 않았으며 보존/삭제할 실험 산출물도 없다.
