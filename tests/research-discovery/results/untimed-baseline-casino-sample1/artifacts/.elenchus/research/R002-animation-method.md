## 사용자 기술 언급 분류

현재 환경은 Windows PC와 데스크톱 Chrome 우선이다. 터미널에서 웹으로 진행하는 순서와 게임 범위는 사용자 제약이며 특정 언어·엔진·라이브러리 제약은 없다. 조사에서 등장한 보간·물리 엔진·Wheelkit·HTML은 후보 또는 사례다. 결과를 먼저 정하는 구조도 사용자 필수 제약이 아닌 검토할 에이전트 제안이다.

| 애니메이션 종료 콜백에서 다음 추첨·규칙 진행 | S02 초기 방식에서 탭 복귀 후 타이머·콜백 순서 변화로 표시 정지 | 초기 연결은 직접적일 수 있으나 표현 지연이 게임 진행에 전파된 사례 | 우선안에서 제외. 현재 제품에서도 반드시 실패한다는 보편 법칙은 아님 |
| 명령 → 규칙 상태와 이벤트 → 표현 | S02는 터미널/웹이 같은 규칙 모듈 사용, S05도 상태 결정과 소품 재생 분리 | 표시 좌표·연출 속도와 점수/잔액의 기준을 분리할 수 있음. 새 명령·빠른 생략·복귀 경계 처리는 별도 필요 | 우선 검토 제안. 현재 제품에서 작동 검증한 구조는 아님 |
| 서버가 규칙을 결정하고 클라이언트가 표현 | S05의 멀티 사례 | 미래 멀티와 관련된 분리 개념이지만 서버 구현 부담이 생김 | 현재 사용자 범위에서 제외. 로컬 메모리 상태와 모듈 경계만 검토 |

추천 구조는 `사용자 명령 → 로컬 규칙·세션 상태 갱신 및 이벤트 → 터미널 출력 또는 웹 연출`이다. 출처: **에이전트 제안, 미승인**. 원요청 대비 기능 추가는 없으며 터미널 다음 웹이라는 순서에서 규칙을 중복 작성하지 않기 위한 후보다. 실제 동일 모듈 공유 방식은 언어·실행 환경을 고른 뒤 검증해야 한다.

- 세션 자금과 두 카드게임의 독립 6덱 상태는 규칙 쪽에서 다루고, 화면의 위치나 애니메이션 완료 횟수로 금액·카드를 결정하지 않는 방향을 제안한다. 금액 정밀도·셔플 세칙은 사용자가 다음에 합의한다.
- **블랙잭은 사용자 행동마다 상태를 진행한다.** 자료의 “라운드 결과를 먼저 만든다”를 미래 히트·더블·스플릿까지 사용자 대신 선택한다는 뜻으로 적용하지 않는다. 아직 받지 않은 행동을 미리 정하거나 그 정보를 화면에 노출하지 않는다. 각 합법적 명령이 만든 결과를 그다음 연출하는 의미다.
- 카드는 이동·뒤집기·정렬 등의 표현 단위, 휠은 회전판·공·포켓 매핑의 별도 검증 단위로 다루는 방안을 제안한다. 모델·키프레임·보간 도구는 미정이며 제작 시간·완성도를 추정하지 않는다.
- 카드게임별 6덱은 게임 데이터 요구다. 312장 전체를 항상 화면에 그리거나 별도 모델 파일로 만들어야 한다는 요구는 없다. 보이는 카드 위주 표현은 에이전트의 단순화 제안이며 성능 향상 수치가 검증된 것은 아니다.
- 생략 기능을 선택한다면 결과를 다시 추첨하지 않고 해당 명령의 최종 표현 상태로 맞추는 방향이 S02에 부합한다. **생략 버튼 자체, 연출 중 입력 허용, 결과 유지 시간은 미승인 UX 선택**이다. 빠른 생략 직후 새 명령을 받을 경계는 별도 검증이 필요하다.
- 이벤트는 연출에 전달할 일시적 정보라는 제안이다. 영구 이벤트 저장·통계·재생 기록·계정·서버를 추가하는 뜻이 아니다. 세션 종료 후 보관하지 않는 사용자 제약을 유지한다.

### 룰렛: 목표 지정 보간과 물리 결과 관찰

| 접근 | 실제 문서 계약 | 얻는 것 | 부담·빠진 것 | 판정 |
|---|---|---|---|---|
| 규칙이 목표 포켓을 정하고 보간으로 표현 | S02의 최종 제품 설명. S07은 `spinTo(index)`로 목표 지정 | 터미널에서 정한 결과와 웹에서 보여 줄 포켓을 맞추는 구조와 잘 연결됨 | 공 궤도·착지·모델 원점·방향·포켓 순서를 직접 맞춰야 함. 자연스러움은 물리 방식보다 나을 근거 없음 | **우선 검토 제안**, 완성품 채택이나 정확성 입증 아님 |
| 물리 시뮬레이션 결과를 받아 규칙에 사용 | S02는 벽면 충돌이 자연스러웠으나 목표 선결정과 병용 어려움. S08은 `spin(seed)` 뒤 포켓 반환 | 충돌이 만들어 내는 움직임을 표현할 수 있음 | 결과 결정 책임이 달라짐. 고정 step·엔진 빌드 조건과 터미널 연결·37포켓 모델 검증 필요 | 배제 가능한 취향 문제가 아닌 구조 대안. 물리 결과를 원할 때 재검토하며 지금 확정 안 함 |

“물리 엔진이면 원래 틀린다” 또는 “보간이면 반드시 정확하다”는 결론은 없다. 선택에 따라 결과의 기준과 검증 의무가 달라진다. 물리 기반 결과를 먼저 계산해 연출하는 또 다른 설계도 개념상 가능하지만 제공 자료에 검증 사례가 없어 채택 근거로 쓰지 않는다.

### 버전 판정

| 항목 | Wheelkit 1.4 (S07) | Wheelkit 2.0 (S08) | 현재 요구에 대한 의미 |
|---|---|---|---|
| API·결과 방향 | `spinTo(index)`: 지정한 포켓에서 정지 | `spin(seed)`: 물리 결과의 포켓 인덱스를 반환. `spinTo` 제거 | 이름·검색 설명만으로 동일 API 계약을 가정할 수 없음 |
| 모델/공 | 기본 37포켓. 공 최종 좌표는 정적 포켓 좌표, 회전 중 충돌은 시각 효과 | 배포 예제는 24포켓 경품 휠. 37포켓 모델 미포함 | 2.0이 싱글 제로 요구를 바로 충족한다고 말할 수 없음. 24포켓 전용이라고 단정하는 뜻은 아님 |
| 재현·모델 범위 | 사용자 모델은 원점·방향을 맞춰야 함 | 같은 seed 재현은 지정 고정 step·엔진 빌드에서만 검증 | 임의 모델·다른 PC/브라우저에서 재현된다는 근거 없음 |
| 유지·누락 | 1.x 유지보수 종료, 2.x 계약은 설명 범위 밖 | 목표 결과 선결정 후 임의 모델 적용용 아님. 금전 정산·탭 복귀 처리 미포함 | 1.x 고정 사용도 자동 해결책이 아님. 현재 세션 자금 정산은 별도 규칙 문제 |

**Wheelkit 2.0을 목표 포켓 지정용으로 그대로 채택하자는 제안은 반박된다.** 1.4의 종료된 유지 상태와 2.0의 다른 계약을 함께 고려해 즉시 도입 후보에서 제외한다. 이는 합성 라이브러리의 문서 판정이며 실제 제품 구매·설치 권고가 아니다.

재검증 순서와 결과:

1. T1의 근거와 반례를 S02의 명령/이벤트와 콜백 실패 본문에서 함께 확인했다. S05를 대조해 분리 개념은 추가로 참고하되 서버를 현재 범위에 끌어오지 않았다. 블랙잭의 미래 행동까지 선결정하는 과도한 전이는 구조 제안에서 명시적으로 막았다.
2. 도구 채택을 크게 바꾸는 T3의 버전 경로를 S07·S08에서 직접 대조했다. 1.4 목표 지정 지원을 2.0에 적용할 수 없으므로 현행 즉시 채택 주장을 반박으로 갱신했다. 오래된 설명이나 동일 함수명을 찾는 추가 검색은 이 계약을 대체할 수 없다.
3. 남은 핵심 공백 T4를 S02의 코드 전후 본문으로 재확인했다. 각도 함수 자체보다 누락된 공 궤도·포켓 좌표와 0 근처 오차가 판정에 중요했다. 각도 종점 계산만 실행하는 Lab은 핵심 반증 조건을 시험하지 못하므로 만들지 않았다.
4. 비용·성능 일반화 여부를 S04·S05·S02에서 재확인했다. 실제 수치·비교 측정·자산 정보가 없어 T5는 근거 부족으로 유지했다. 묶음 밖 연결이 없으므로 필요한 실행/실재 후보 조사를 연기한다.

## Lab 검증 제안과 실행 보류

아래는 미검증 주장을 다음 대화에서 처리할 제안이다. Lab을 실행했거나 Build로 합의했다는 뜻이 아니다. 정확한 도구·자산·시간·출력 경계가 정해지면 실행 전 계약을 다시 작성한다.

| 시험할 주장·예상 방향 | 채택 판단에 필요한 관찰 | 폐기·실패 조건 | 현재 미실행 이유·다음 행동 |
|---|---|---|---|
| 명령 처리와 연출 분리로 결과 일관성을 유지할 수 있다 | 동일 명령의 카드·잔액이 연출 속도/일시 중단에 따라 바뀌지 않음. 블랙잭이 미입력 행동을 기다리고 승인된 행동만 한 번 반영 | 중복 추첨·중복 정산·미래 행동 자동 선택, 복귀 후 화면과 상태 불일치 | 제품 모듈·브라우저 없음. 구조 타당성은 후보 수준, 후속 검증까지 실제 성공 주장 보류 |
| 목표 포켓 보간으로 공·회전판·표시 번호·정산이 일치한다 | 사용할 모델의 37포켓 전체에서 목표와 착지 번호를 비교하고 0 인접 경계·시작 각도·회전 방향을 포함. 연속 동작과 최종 상태 모두 확인 | 한 칸 오차·역방향 배열·원점 불일치·공이 다른 포켓에 착지. 회전판 각도만 맞거나 공 좌표가 없으면 검증 실패 | 전체 모델·공 궤도·실행 데모 미제공. 각도 조각의 정적 계산을 대체 증거로 쓰지 않음 |
| 탭 복귀와 연출/다음 입력 경계에서 한 번만 진행한다 | 탭을 가렸다 복귀해도 상태·화면이 맞고 중복 처리 없음. 생략을 채택한 경우에만 생략 직후 새 입력도 확인 | 영구 대기·중복 라운드·잔액 차이·이전 이벤트가 새 라운드 표시를 바꿈 | 브라우저 미지원. UX 경계부터 후속 합의 후 검증 |
| 작은 장면으로 대상 PC에서 충분한 가독성·반응을 얻는다 | 합의한 창 크기에서 룰렛 번호·바카라 합계·스플릿 패가 읽히고 합의할 성능 기준을 충족 | 정보 가림·대상 클릭 불가·합의 기준 미달 | PC/GPU·Chrome 버전·창 크기·합격 수치 미정. 현재 프레임 수·시간 측정 없음 |

실행 상태: 검증 연기로 **미실행**이다. `채택`·`검증 실패` 같은 실제 실험 결과를 붙이지 않는다. 향후 실행 시 모든 코드·의존성·캐시·임시 출력은 해당 Lab 경계 안에 있어야 하고 제품·외부 상태를 바꾸지 않아야 한다. 현재 일반 프로젝트 쓰기 권한만으로 이 격리를 입증하지 않았으므로 도구 설치나 코드 실행을 시도하지 않았다.

## Web closure와 Verdict

- 판정: **결론 가능** — 문서상 제작 접근의 비교와 조건부 구조 제안에 한정한다. 실제 작동하는 휠·최종 엔진·비용·성능의 채택 판정은 **결론 보류**다.
- 근거: S02의 터미널/웹 규칙 공유와 상태·이벤트 분리, S02·S07·S08의 보간/물리 계약 차이. T3·T4의 과도한 주장에는 명시적 반박이 있다.
- 추천: 로컬 규칙·세션 상태를 명령 단위로 갱신하고 표현에 전달하는 방식과, 목표 포켓을 표현하는 보간 방식을 우선 검토한다. 실제 라이브러리는 고르지 않는다. 블랙잭의 다음 선택을 미리 확정하지 않는다.
- 반대 근거: 물리 방식의 자연스러운 충돌 장점, 보간의 모델 원점·포켓 오차, 분리 후에도 남는 복귀/생략 경계, 더 작은 CSS 방식의 가능성. 단일 구조나 엔진만이 답이라는 결론은 없다.
- 채택·제외 의미: 추천은 **미승인 에이전트 제안**이다. 콜백 종속 규칙 진행과 Wheelkit 2.0의 목표 지정용 즉시 도입은 우선안에서 제외한다. 홀/멀티/저장 등 사용자 제외를 유지한다. CSS 축소는 사용자 목표 변경을 별도 확인하기 전 채택하지 않는다.
- 한계: 합성 문서·코드 조각만 읽었다. Lab·Browser·실재 라이브러리·성능·공 궤도·37포켓 동작·사용권을 검증하지 않았다. 문서 작성자 PC의 경험을 사용자 Windows/Chrome에 일반화하지 않는다.
- 신뢰도: **중간** — 현재 범위에 대한 구조 제안. 합성 문서 내부의 API 변경 판정은 높지만 실재 도구 적합성의 증거가 아니다. 최종 휠 정확성·성능·제작비는 낮음/미검증이다.
- Web closure: 본문 확보·버전/대상 확인·출처 역할/중복 제거·반대 검색·Claim 연결·공백 처리를 완료했다. 문서 기반 비교 루프를 종료할 수 있다. 접근 실패 원문은 없고 외부 `.example` 경로는 예약 도메인/연결 미제공으로 시도하지 않았다. 필요한 다음 증거는 실제 모델/브라우저 실행 또는 실재 도구 자료이므로 같은 로컬 문서 재검색으로는 판정을 바꾸기 어렵다.
- 남은 높은 영향 공백: T4의 실제 정합성은 Lab 제안과 검증 연기, T5의 스택·비용·성능은 선택 연기로 연결했다. 향후 구현 검증을 통과하기 전 성공을 주장하거나 확정 계획의 기정사실로 쓰지 않는다.
- 사용자 결정: 현재 사용자는 Research 수행과 근거 기반 제안을 요청했으며 위 구조·검증·제외 제안 자체는 아직 확인하지 않았다. 파일 상태는 작성 중이다.

## Idea 변경과 Execution 영향

출처: 사용자 요청. 게임 세칙·베팅 단위는 다음 합의로 유지하고 저장·멀티·계정 등 제외를 그대로 보존했다. 출처: 에이전트 제안. 기술 선택은 본 R002에 후보로만 남겼으며 Idea의 사용자 확정 사실로 복사하지 않는다. 원요청 대비 새로운 제품 기능 추가·삭제는 없다. 공유 규칙/표현 분리는 중복 구현을 줄일 가능성과 명령/연출 경계를 관리하는 부담이 있다.

터미널 → 웹의 사용자 지정 순서를 유지한다. 영향은 규칙·세션 및 웹 애니메이션의 Phase 후보이며, 실제 Phase·Build ID·전체 실행 계획·일정은 만들지 않는다. 후속 Execution에서는 세칙·UX 합의와 위 검증을 처리해야 하며, 지금 이 문서를 완성된 휠 구현 근거로 인용할 수 없다. 별도 Lab·제품 산출물은 생성하지 않았다.
