# Research R002: 파일 변경의 사전 검토와 실패 상태 설명

- 상태: 작성 중
- 기준: [idea.md](../idea.md)
- 확인 날짜: 2026-09-07
- 영향: Phase 후보
- 범위: 합성 개발 문서의 설계 비교. 파일 변경 기능의 채택이나 복구 보장에 대한 사용자 합의가 아니다.

## Repository 기준선과 Neutral brief

관찰: `app.txt`는 제품 미구현 stub이며 파일 작업 코드·테스트는 확인되지 않았다. 원자료 S01·S02·S03을 읽기 전용으로 확인했다. 해석: 동작하는 트랜잭션 엔진이나 복구 기능을 전제로 삼을 수 없다.

| 항목 | 내용 |
|---|---|
| 중립 질문 | 이동·삭제를 채택할 경우, 사전 목록과 실패 후 원본 상태·작업 경위를 어떻게 연결할 것인가? |
| 입력 | 두 드라이브와 외장 SSD에 있는 사용자가 선택한 사진; 아직 적용하지 않은 변경 의도 |
| 출력 | 적용 전 원본·대상·작업 목록, 실패·부분 성공 후 항목별 현재 상태를 이해할 수 있는 설계 후보 |
| 사용자 경험 | 명시적 적용 전 원본·메타데이터 불변; 이동은 목록 확인 후 실행; 삭제는 나란히 비교해 직접 선택 |
| 성공 조건 | 무엇을 검토·적용했고 어느 단계까지 끝났는지, 원본과 대상이 어떤 상태인지 설명 가능 |
| 실패 조건 | 미검토 삭제·덮어쓰기, 재개 중 중복 삭제, 연결 끊김을 전체 성공으로 표시, 완전 복구를 근거 없이 약속 |
| 확정 제약 | 오프라인·개인 Windows 사용, 자동 유사 삭제 금지, 외부 계정·유료 호출·개인 사진 접근·제품 구현 금지 |
| 객관적 환경 | PowerShell 문서 분석만 가능; 네트워크·브라우저·subagent 없음; 실제 작업 엔진·파일시스템 조건과 실험 자료 없음 |
| 미해결 질문 | 이동·삭제의 포함 시점, 휴지통·복구 보관, 이름 충돌 선택, 중간 취소·재개·되돌리기의 보장과 공간 비용 |

사용자 기술 언급 분류: Windows·복수 볼륨은 환경 및 제약이다. 폴더 직접 관리·보관함은 후보이고 digiKam은 예시다. 특정 파일 API·엔진·DB는 요구하지 않았다. 이동은 조건부 기능이지 무조건 구현할 확정 항목이 아니다.

## 후보·더 작은 대안과 제작 제안

모든 채택안은 **출처: 에이전트 제안 · 미승인**이다. 안전 제약 자체는 사용자 요청에서 왔다.

| 방향 | 얻는 것 | 부담·사라지는 결과 | 판정 |
|---|---|---|---|
| 사용 동작 즉시 이름 변경·이동 | 조작 수 감소 가능 | 적용 전 검토를 건너뛰면 확정 요구 위반; 실패 중간 상태 추적 어려움 | 사전 확인 없는 형태 제외 |
| 계획 검토 후 기록을 남기며 적용 | 경로·충돌 확인, 부분 성공·실패를 항목별로 설명할 기반 | 상태 기록·재개·공간·복사 검증 필요, 모든 작업이 한 번에 되돌아간다는 보장은 없음 | 이동 채택 시 참고할 방향 |
| 조회·후보 선택까지만 만들고 원본 정리는 수동 | 파일 변경 기능과 복구 구현 부담을 줄임 | 도구 안에서 실제 정리가 끝나지 않음 | 동등한 축소·연기 대안; 기능 제외 확정 아님 |
| 복사 보관함 안에서만 변경 | 보관함 복사본과 기존 원본을 구별할 수 있음 | 추가 공간, 원래 폴더 중복·정리는 그대로 남음 | R001의 저장 방식 선택에 의존 |
| 기존 도구를 사용하고 새 변경 엔진을 만들지 않음 | 자체 파괴적 작업 구현 부담 감소 | 실제 제품의 조건·유지·복구 검증 필요; 합성 자료로 추천 불가 | 실제 후보 조사 보류 |

이동을 선택할 때 참고할 절차는 다음과 같다. S02가 설명하는 **계획 → 사전 확인 → 드라이브 간 복사 → 확인 → 원본 제거 → 기록에 따른 재개**를 기본 근거로 삼는다. 복사의 확인 알고리즘과 기록의 내구성은 원자료에 없다.

이에 대한 추가 설계 제안은 적용 대상·원본/대상 경로·계획 시점 정보를 보관하고, 실행 직전 변화를 재확인하며, 복사 확인에 실패하면 원본 제거로 넘어가지 않도록 하는 것이다. 상태 표시는 예를 들어 `대기·복사 중·확인 완료·원본 제거 완료·실패·보류`로 나눌 수 있다. 이 상태명·저장 구조·UI는 에이전트 제안이지 검증된 소스나 확정 요구가 아니다. 드라이브가 빠지면 확인할 수 없는 상태를 성공·손실로 추정하지 않아야 한다는 제안도 남긴다.

실행 이력은 백업이 아니다. 복사 완료·원본 제거·앱 종료의 어느 시점에서 중단됐는지, 외부에서 파일이 바뀌었는지에 따라 재시도·복구가 달라진다. 이는 무조건 자동 롤백을 약속하지 않아야 한다는 문서 해석이다. 사용자 검토 없는 원본 삭제는 허용하지 않는다.

## Web closure·Lab 관찰 의미

제공 자료에 대한 본문·버전·출처 연결과 반대 자료 검토를 마쳤다. 실제 Web·Browser·Lab 관찰은 없다. 실제 안전성 검증까지 완료한 closure로 보고하지 않는다. journal이 모든 파일시스템에서 안전하다는 주장과 원본 복구 보장은 보류한다.

파일 변경을 채택하기 전 검증 과제는 연결 끊김, 공간 부족, 대상 충돌, 계획 이후 원본 변경, 재시작 중복 실행, 복사 확인 실패, 일부 성공 후 취소, journal 손상이다. 이는 합성 fixture와 실제 채택 엔진을 이용할 미래 검증 후보이며 이번 실행에서 만들거나 돌리지 않았다. 먼저 원본·대상의 허용 결과와 사용자에게 보여 줄 실패 상태를 합의해야 한다. 파일시스템 종류·백업·휴지통 정책을 가정하지 않는다.

## Verdict

- 판정: **결론 가능 — 사전 계획과 실행 기록을 분리하는 설계 방향. 실제 복구 보장과 파일 변경 기능 채택은 결론 보류.**
- 근거: S01·S02는 사용자 검토와 드라이브 간 복사·확인·제거, 외부 변경 보류, 중단 기록 재개를 설명한다. 사용자의 실패 경위 확인 요구에 대응한다.
- 반대 근거: S02 자체가 완전한 복구를 보장하지 않는다. S03의 보관함 휴지통은 외부 원본 정리를 대신하지 않는다.
- 권장 방향: 이동을 채택한다면 계획과 적용을 분리하고 항목별 경위를 남기는 방식을 검토한다. 조회·비교까지만 우선 다루는 작은 대안도 같은 지위로 유지한다.
- 한계·신뢰도: **중간** — 문서상 경계에 대한 판단. 실행 가능한 소스·실제 파일시스템 장애 관찰이 없으므로 복구 안전성의 신뢰도는 낮다. 추가 저장 공간·개발 비용·복구 기간은 미확정이다.
- Idea 변경: 사용자 안전 제약 유지. P2는 기능 분리·축소 제안으로만 남김. 이동·삭제의 채택 시점과 복구 범위를 사용자 대신 결정하지 않음.
- Execution 영향: Phase 후보에 조회/선택과 파괴적 작업의 책임 분리, 파괴적 작업 채택 전 장애 검증 필요성을 남긴다. 전체 Phase·Build 번호·순서·계획은 다음 대화로 미룬다.
- 사용자 결정: 사전 목록과 실패 경위 확인 조건만 확정. 이동 채택, 휴지통·복구·자동 재개 정책은 미승인이다.

## 보류

이동·삭제의 포함 시점과 부분 성공·취소·복구의 구체적 결과는 다음 계획 합의 대상이다. 더 높은 영향의 분리 조회 범위(R001)부터 결정한 뒤 돌아온다. 낮은 우선순위라는 이유로 안전 조건을 완료·제외 처리하지 않는다.
