# Research R001: 여러 볼륨의 사진 정보를 오프라인에서 모아 보는 관리 방식

- 상태: 작성 중
- 기준: [idea.md](../idea.md)
- 확인 날짜: 2026-09-07
- 영향: Phase 후보
- 이번 산출물: 제공된 합성 문서에 한정한 비교와 조건부 권고. 사용자 채택·Idea closure·전체 실행 계획 합의는 하지 않았다.

## Repository 기준선

관찰: `app.txt`는 `UNIMPLEMENTED PRODUCT STUB`다. 현재 질문에 사용할 구현·DB·테스트 동작을 확인할 근거가 없다. `.elenchus/idea.md`의 기존 초안과 최신 사용자 답을 대조했다. `evidence/README.md`는 모든 제품·측정값·코드가 합성임을 명시한다. 관련 자료의 본문을 읽었으며 제품 파일·원자료는 변경하지 않았다.

해석: 기존 엔진에 맞출 제약이 없으므로 사용자 결과에서 관리 방식을 비교한다. 제공 설명을 실제 제품의 동작으로 간주하거나 존재하지 않는 코드 구조를 추정하지 않는다.

## 사용자 기술 언급 분류

Windows·로컬 사용·입력 형식·규모는 현재 환경 및 필수 제약이다. digiKam은 예시이며 neutral brief의 채택 조건에 넣지 않았다. 폴더 직접 관리와 별도 보관함은 비교할 후보이며 선택된 구조가 아니다. SQLite 등 DB·엔진은 필수 조건이 아니다.

| 온라인 검색 전환 · Indexlens 3.0 | 자료상 계정 서비스가 검색 담당 | 로컬 원본과 로컬 처리를 구별하는 반례 | 로그인·연결 필수, 썸네일·메타데이터 업로드 | 확정 제외 조건에 불일치 |
| 더 작은 자체 도구 | 연결된 폴더를 읽고 정보만 지속 보관, 원본 정리는 수동 | 카탈로그와 조회·비교로 범위를 줄일 수 있음 | 복잡한 파일 변경이 줄지만 사용자가 원한 실제 정리의 일부는 별도 수작업 | 단순화 제안; 기능 축소 승인 아님 |
| 만들지 않고 기존 도구 사용 | 제작 부담을 줄일 가능성 | 실제 제품의 오프라인·형식·유지 상태를 먼저 확인 | 이번 자료는 모두 합성이므로 조건을 만족하는 실제 대체 제품을 검증하지 못함 | 동등한 대안으로 유지; 실제 후보 선정 보류 |

원본의 저장 방식과 화면 방식은 별개의 선택이라는 것이 이 비교의 해석이다. 카탈로그를 쓴다고 보관함 중심 화면을 강제할 이유는 없지만, 폴더·타임라인 중 어느 화면이 사용자에게 더 좋은지는 자료만으로 정하지 않는다. SQLite는 S04에 나온 구현 예일 뿐, 엔진·DB·스키마 채택의 근거가 충분하지 않다.

## Web closure와 검증 경계

핵심 Claim의 본문·날짜·버전·반대 근거·중복 출처를 대조했고, 비교에 필요한 제공 자료 경로를 모두 확인했다. 이 범위의 문서 검토는 마쳤다. 실제 Web/Browser 조사는 수행하지 않았으며 실제 제품의 외부 검증까지 완료한 Web closure로 보고하지 않는다. 표의 `근거 부족` C4와 직접 UX·현재 지원·공개 코드·라이선스 공백은 검증 연기에 연결한다. 브라우저가 없다는 이유로 제품 화면을 관찰했다고 바꾸지 않는다.

실행하지 않은 검증 후보: 실제 채택 후보의 Windows·HEIC 오프라인 디코딩과 배포 조건, 통제된 자료에서 규모에 따른 초기·재검색 시간과 저장량, SSD 분리·재연결과 외부 이동, 캐시 소실과 부분 읽기 실패, 큰 비교의 실용성. 개인 사진 접근 없이 가능한 데이터 확보와 관찰 기준부터 다음 계획에서 정한다. Lab 결과·벤치마크·예산은 없다.

## Verdict

- 판정: **결론 가능 — 합성 사례의 구조 비교와 조건부 설계 권고에 한정.** 실제 제품 채택·HEIC 배포·5만 장 사용성·화면 선호는 **결론 보류**다.
- 권장 방향: 원본을 그대로 두고 위치·정보를 PC의 별도 로컬 저장소에 기억하는 참조 카탈로그를 우선 검토한다. 원본 이동 없이 분리 조회를 지원할 수 있다는 S04의 구조 설명과 사용자 요구의 대응에 근거한다. 미리보기 보관 범위는 다음 사용자 결정이다.
- 반대 근거: S04 방식에도 재연결·정보 노후화·캐시 비용이 있다. 분리된 상태에서 원본 수준의 큰 비교가 필요하고 저장 공간을 수용한다면 S03의 복사 보관함이 더 맞을 수 있다. 단순 폴더 도구에 지속 색인을 추가하는 안도 비교 가능하다.
- 채택·제외 근거: 특정 제품·DB를 채택하지 않는다. S06의 3.0은 확정 제약과 충돌하고 2.x는 자료상 보안 패치가 종료돼 구버전 설치 대안으로 권하지 않는다. S01 그대로의 분리 동작은 요구에 부족하다.
- 한계: 합성 문서 설명만 있으며 사용자 PC, 실제 UX, 성능, 라이선스·배포 비용을 검증하지 않았다. 금액과 공간을 확정하지 않는다.
- 신뢰도: **중간** — 요구와 문서상 구조의 대응에 대한 판단. 실제 제품 적용·성능에 대한 신뢰도는 낮다.
- Idea에서 바꿀 내용: P1을 미승인 대안으로 추가; 분리 중 정보·미리보기 범위와 저장 교환 관계를 미정으로 유지한다.
- Execution에서 바꿀 Phase·Build: 전체 계획은 만들지 않는다. Phase 후보로 원본 읽기와 로컬 정보 보관의 경계, 형식·규모·분리 상황의 검증 필요성을 넘긴다. 특정 번호·순서·비용을 합의하지 않는다.
- 사용자 결정: 조사 범위만 승인됨. 카탈로그·복사 보관함·DB·화면·캐시 용량은 미승인이다.

## 보류와 다음 질문

외장 SSD가 빠져 있을 때 이전 사진의 날짜·경로 같은 텍스트 정보만 찾으면 되는가, 저장된 미리보기로 사진을 알아보고 비교하는 것까지 필요한가? 이 답은 원본 복사 필요성·미리보기 해상도·저장 비용을 바꾸므로 다음 대화의 첫 결정으로 제안한다. 오늘 Research 결과를 제시하기 위해 답을 가정하지 않는다.
