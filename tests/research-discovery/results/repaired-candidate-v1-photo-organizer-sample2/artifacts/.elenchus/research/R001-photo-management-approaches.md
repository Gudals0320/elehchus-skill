## Repository 기준선

- 직접 확인: 프로젝트의 `AGENTS.md`, `skill/SKILL.md`, 현재 단계 지침, `evidence/README.md`, 현재 `idea.md`. 기존 `.elenchus/`는 없어 이번 요청의 초안부터 작성했다.

## 조사한 접근 범주

자료 목록과 본문에서 폴더 직접 스캔, 복사형 보관함, 참조 카탈로그의 직접 유사 사례를 발견했다. 인접 사례로 유사 이미지 후보 검토와 날짜 출처 보존 모듈을 발견했다. 관리 방식 외에 ‘선택 결과만 내보내고 파일 변경을 줄이는 범위’도 비교한다.

같은 원문의 재게시, 참조 카탈로그의 버전 변화, 파일 이동의 복구 한계, hash의 적용 범위, 날짜 API가 보장하지 않는 사항을 원문에서 집중 재확인했다. 후보 발견 뒤 Claim을 만들고 관련 구절을 다시 대조했으며, 채택 방향은 정하지 않았다.

자료에 없는 관련 범주는 여러 관리 모드를 함께 제공하는 혼합형 제품, 다른 유사 이미지 검색 전략, 실제 Windows 사진 앱의 공개 구현·사용 후기다. 유효한 대안일 가능성이 남아 있어 탐색 완료로 계산하지 않는다. 클라우드 전용·다중 사용자 협업은 현재 개인용 로컬 목적의 주된 비교 대상이 아니며 범위를 넓히지 않았다. 구현하지 않고 기존 도구만 쓰는 대안도 유지하지만 실제 제품 선택을 뒷받침할 자료는 없다.

## 비교 자료: 관리 방식과 작은 대안

모든 사례의 화면·행동은 **자료의 설명**이다. 장면을 직접 보거나 동작시킨 것은 아니다. ‘우리 조건’의 판단과 아래 조건부 권장은 **에이전트 추론·제안**이며 미승인이다.

| 접근법·대표 합성 사례 | 실제 근거·차이 | 우리 조건에서 가져올 요소·필요한 변경·부담 | 채택·제외·보류 및 선택 조건 |
|---|---|---|---|
| 폴더 직접 관리 — Pathframe 1.7 | E01: 선택 폴더 스캔·실제 폴더 트리·날짜 선택, 원본 복사 없음. 즐겨찾기·보정 날짜는 폴더 JSON sidecar에 기록. 분리된 폴더는 사진 보기·검색에서 빠짐. | 경로가 눈에 보이는 조작, 적용 전 원본·대상 목록, 충돌 시 덮어쓰지 않는 흐름을 참고. 원본 무변경을 원하면 sidecar 위치 정책을 달리해야 함. 분리된 저장장치 정보 유지와 대량 탐색 성능은 별도 설계 부담. | 보류. 탐색기에서 다루는 폴더가 정리의 중심이고 연결된 파일만 보면 되는 경우에 적합할 가능성. 원본 폴더 안 쓰기가 괜찮다는 동의는 없음. |
| 복사형 보관함 — Albumvault 4.0 | E03: 사진을 전용 공간으로 복사, DB에 정보·미리보기 보관. 원래 폴더가 없어져도 가져온 사진 열람. 참조 전용 모드 없음. 복사본·미리보기만큼 추가 공간, 원래 폴더 정리는 남음. | 원본 경로·이름의 가져오기 기록, 동일 파일 재가져오기 처리, 제거 후 유예 흐름을 참고. 파일 복사·검증·용량 부족·부분 가져오기와 보관함 복구 정책이 필요. 자료의 30일 휴지통을 우리 정책으로 자동 채택하지 않음. | 보류. 한곳의 관리된 복사본으로 계속 보고 싶고 저장 공간·이중 관리 부담을 감수할 때 적합할 가능성. 별도 보관함이 백업을 보장한다는 근거는 없음. |
| 참조 카탈로그 — Indexlens 2.8의 구조 | E04: 원본 위치·메타데이터·미리보기만 로컬 DB에 기록. 볼륨 식별자·상대 경로, 분리 중 정보 검색, 원본 동작 비활성화. 외부 이동 시 재연결, 내용 변경 시 정보가 낡을 수 있음. | 사진 복제 없이 폴더를 가로질러 보는 구조, 연결 상태·정보 갱신 시각·날짜 출처 표시를 참고. DB·캐시 저장 공간, 재스캔·재연결·카탈로그 복구가 부담. ‘읽기 전용’도 DB·캐시는 쓰며 원본·sidecar 무쓰기를 별도로 구분. | 구조 비교는 유지, 채택은 보류. 원본 위치를 유지하며 통합 정보·미리보기를 원할 때 유력한 중간안. E06 때문에 Indexlens 3.0을 독립 로컬 구현의 근거로 쓰지 않고, 패치가 중단된 2.x 사용도 추천하지 않음. |
| 후보 검토·결과 내보내기로 축소 — Pairboard | E07: 디자인 이미지에서 byte 동일 그룹과 perceptual hash 유사 후보 분리. 두 장·해상도·용량·경로·동기 확대를 설명. 선택 결과 CSV 출력, 원본 수정·삭제 없음. | 유사 후보의 이유·원본 경로와 품질 정보를 보고 사용자가 판단하는 흐름을 참고. 전체 보관함을 만들지 않는 작은 대안이나 유사 사진 기능에 적용 가능. 실제 사진 데이터에서 오탐·누락과 화면 사용성을 확인해야 함. | 보류. 우선 어떤 사진을 남길지 판단하는 게 목표라면 범위를 줄일 수 있음. 실제 폴더 정리와 날짜 통합 보기까지 해결하는 대안은 아니며 별도 작업이 남음. |
| 현재 방식 유지·새로 만들지 않기 | 사용자에게 현재 세부 작업 방식은 아직 묻지 않았음. 실제 대체 제품 비교 근거도 없음. | 새 구현·유지보수와 파일 작업 코드를 줄일 수 있음. 여러 폴더를 모아 보고 날짜·유사도로 정리하려는 원문 목표가 충족되는지 확인 필요. | 동등하게 열린 대안. 합성 제품 목록만으로 특정 기존 앱 사용을 추천할 수 없음. |

폴더 트리를 화면에 보여 주는 것과 내부에 카탈로그를 쓰는 것은 별개의 선택일 수 있다(에이전트 추론). 따라서 ‘탐색기 같은 화면’만으로 저장 구조를 정하지 않는다. 혼합형의 실제 사례는 미탐색이므로 제공 사례에서 이미 검증된 구성처럼 제시하지 않는다.

## 참고 구현과 파일 안전 경계

| 참고 전략 | 자료의 설명 또는 코드에서 확인한 점 | 반례·한계와 우리 계획에 미치는 영향 |
|---|---|---|
| 계획 → 검사 → 항목별 작업 기록 → 재개 | E01·E02: 경로 목록을 먼저 보여 주고 충돌·공간을 확인. 외부에서 바뀐 원본은 해당 항목 보류. 드라이브 간 이동은 복사·확인·원본 제거로 분리. | 같은 드라이브 rename의 특성을 드라이브 간·일괄 작업에 일반화할 수 없음. 저널은 완전 복구·모든 항목의 일괄 원자성 보장이 아님. 향후 파일 변경을 선택하면 전원 중단·분리·권한 오류·충돌·외부 변경·재시작의 관찰 기준부터 정해야 함. |
| 원본 쓰기와 정리 정보 쓰기 분리 | E01은 폴더 sidecar에 쓰고, E04 읽기 전용 모드는 원본·sidecar에 쓰지 않지만 DB·캐시에 씀. E08은 사용자 보정값 저장소를 앱이 정하게 함. | ‘사진 파일을 안 옮김’만으로 쓰기 없음·안전함이 보장되지 않음. 원본 바이트·경로·sidecar·앱 DB·캐시 각각의 변경 범위를 구분해 사용자 경험과 복구 대상을 정해야 함. |
| 완전 동일 그룹과 유사 후보 분리 | E03은 byte hash로 중복 가져오기만 건너뜀. E07은 내용 hash와 perceptual hash를 별도로 쓰며 유사 후보를 사용자에게 제시. | 크롭·압축·메타데이터 차이는 byte 동일성이 아님. 같은 배경의 다른 이미지가 가깝게 나오거나 후보 축소로 놓칠 수 있음. hash 일치만으로 원본 삭제의 충분조건이 검증된 것도 아님. 후보를 곧바로 삭제 대상으로 바꾸지 않는 흐름을 제안. |
| 후보 수를 줄이고 비교 정보 제공 | E07은 hash 근처만 후보로 만들고 해상도·용량·경로·동기 확대를 설명. | 5만 장에 대한 속도 측정·사진 정확도·완전 탐색 대비 누락률은 없음. 해상도·용량이 ‘남길 사진’의 유일 기준도 아님. 읽기 전용 검토만 만들면 변경 위험과 개발 범위가 줄지만 실제 파일 정리는 남음. |
| 날짜 원문·파싱값·출처·시간대 유무 보존 | E08의 `date_record`는 해당 필드를 딕셔너리로 반환하는 코드 조각. E04는 EXIF 우선·없으면 파일 날짜 임시 사용·출처 배지를 설명. | 코드 조각은 전체 EXIF 파서·오류 처리·입출력 구현이 아님. 시간대 없는 촬영일·다른 기기 시계·바뀐 수정일을 한 정확한 시간으로 취급할 수 없음. 날짜 우선순위·누락·보정 저장 방식은 사용자에게 남은 선택. |
| 형식 지원·재사용 조건 확인 | E01 HEIC는 OS 확장 상태에 의존. E03은 디코더 동봉을 서술. E08 fixture는 JPEG·PNG뿐이라고 서술. | 우리 PC의 HEIC 지원·손상 파일·대량 처리 성능은 미확인. 전체 코드·라이선스·의존성·빌드 조건은 자료에 없어 코드 복사·배포 가능성을 확정하지 않음. 실제 소스 조사 뒤 재사용 여부 판단 필요. |

지원되는 전략의 개념을 참고하는 것과 코드·에셋을 그대로 재사용하는 것은 구분한다. 현재 재사용 승인이나 라이선스 적합성 판정은 없다. 지원되는지 알 수 없는 수치 목표·속도·정확도·완전 복구 약속을 계획에 넣지 않는다.

근거 공백에 따른 조사 갱신:

1. 최초 발견: E01·E03·E04로 세 관리 방식, E07·E08로 검토·날짜 전략을 확보했다. 단일 선호 제품 검증에 범위를 가두지 않았다.
2. 가장 큰 전제인 로컬 처리·원본 안전을 집중 확인: E04·E05의 원천을 합치고 E06으로 2.8/3.0 적용 범위를 분리했다. E02로 저널의 복구 보장 추정을 반박했다. 따라서 특정 구버전 제품 사용 추천·원자적 일괄 작업 주장은 채택하지 않는다.
3. 구현·실패 근거 보완: E03·E07의 hash 의미, E04·E08의 날짜 의미, E01·E07·E08의 성능·형식·화면 제한을 재확인했다. 사용자 사진에 대한 정밀도나 5만 장 처리 속도는 숫자로 만들지 않는다.
4. 제공 묶음의 관련 8개 본문을 읽고 중요한 구절을 재대조했다. 같은 묶음을 반복해서 읽어도 빠진 실제 소스·라이선스·실행·화면을 얻을 수 없어 이 환경의 추가 로컬 검색 효용은 낮다. 그러나 실제 대안 탐색과 사용자 환경 검증은 선택을 바꿀 가능성이 있어 전체 조사를 충분하다고 닫지 않는다.

## 발견 완료 판정과 Web closure

| Discovery 완료 조건 | 판정과 근거 |
|---|---|
| 접근법 비교 | 제공 묶음 범위에서 충족: 세 관리 방식과 검토만 하는 축소안, 유지·만들지 않기의 편익·부담을 비교. 실제 생태계 전체의 충분성은 미확인. |
| 적합한 직접 근거 | 부분 충족: 원문 설명·짧은 코드는 직접 읽음. 화면·영상·데모·실제 공개 저장소는 확인하지 못함. 문서 설명을 실제 UX로 일반화하지 않음. |
| 적용 가능성 | 부분 충족: 가져올 흐름·필요 변경·공간·갱신·복구 부담을 정리. 코드 재사용 조건·우리 입력 성능은 부족. |
| 결정 영향 | 비교 근거와 조건부 제안 마련. 사용자 승인 대기이며 저장 방식·쓰기 경계를 확정하지 않음. |
| 타당한 종료 | 미충족: 실제 제품·구현·화면과 다른 유력 범주가 미탐색. 자료 접근 한계로 멈춘 것이며 충분한 탐색 완료가 아님. |

Web closure는 **미통과**다. 전체 Claim·본문 위치·출처 관계·버전·반대 근거·접근 기록·공백은 기록했지만 실제 외부 탐색을 대체하지 못한다. 문서별 설명에는 원 작성자 본문을 사용했고 원문 재게시를 독립 증거로 세지 않았다. 중요한 일반 주장의 실제 독립 교차 검증은 없다. 사용자 Browser는 사용하지 않았으며 승인·관찰 성공을 주장하지 않는다. 추가 공개 조사가 결론을 바꾸지 않을 것이라는 근거도 없다.

## Verdict

- 판정: **결론 보류**. 제공 합성 묶음 안의 접근법 비교와 핵심 문구 재검증은 수행했다. 사용자가 요청한 실제 제품·공개 구현의 폭넓은 탐색, 우리 제품의 성공 검증, 사용자 선택 합의는 완료하지 않았다.
- 근거: 폴더 직접 스캔·복사형 보관함·참조 카탈로그는 원본 위치·추가 공간·분리 시 사용·재연결 부담이 다르다. 유사 후보 검토와 날짜 출처 보존은 관리 방식과 별도로 참고할 수 있는 전략이다(E01–E04·E07·E08).
- 반대 근거: 폴더 기반도 sidecar를 쓸 수 있다. 복사형은 원래 폴더 정리를 끝내지 않는다. 참조 카탈로그는 낡은 인덱스·재연결 문제가 있고, 가상 Indexlens의 3.0은 2.8과 달리 온라인 서비스에 의존한다. 저널·hash·날짜 API 어느 것도 자동 안전·정확도·복구를 보장하지 않는다.
- 후보와 핵심 차이: 실제 폴더를 정리할지, 관리된 복사본을 만들지, 원본은 그대로 두고 목록·미리보기를 관리할지가 중심 선택이다. 먼저 후보 검토·목록 출력으로 범위를 줄이거나 새 도구를 만들지 않는 대안도 유지한다.
- 채택·제외 근거: 채택 확정 없음. Indexlens 3.0의 독립 로컬 검색 주장, E05를 독립 증거로 세는 방식, 완전 복구 보장, 유사 점수만으로 같은 사진 판정, 검증된 UX·성능이라는 해석은 근거에서 제외한다. 구조 패턴은 제품의 특정 버전 사용과 분리해 비교한다.
- 조건부 권장: 사용자가 원본 위치 보존과 통합 열람을 우선하면 참조 카탈로그가 검토할 중간안이다. 실제 폴더 변경이 목적이면 직접 관리의 편익이 커지고, 원래 위치와 무관한 열람이 목적이면 복사형의 편익이 커진다. 현재는 우선순위 미정이므로 단일 관리 방식을 추천·확정하지 않는다.
- 안전 관련 초안: 원본을 읽으며 후보·정리 계획부터 검토하고 실제 변경은 별도 결정으로 두는 범위 축소안을 제안한다. 이점은 되돌리기 어려운 작업을 줄이는 것, 부담은 실제 폴더 정리가 아직 남는 것이다. 출처: 에이전트 제안, 미승인. 사용자 요구에 ‘원본 변경 금지’가 이미 포함됐다고 기록하지 않는다.
- 한계: 합성 자료, 네트워크·브라우저·subagent 미사용, 실제 코드·라이선스·화면·실행·사진 입력 정보 부족. 외부 탐색의 생략·연기 및 새 제품 선택에 대한 사용자 동의 없음.
- 신뢰도: **중간** — 합성 본문의 의미·버전·출처 구분에 한정. 실제 제품 추천·코드 재사용·성능·사용성·복구 보장에 대한 신뢰도는 **낮음(근거 부족)**.
- Idea에서 바꿀 내용: 세 관리 방식과 더 작은 범위를 열린 비교 후보로 연결. 사용자 원문·로컬·Windows·개인 사용·구현 전 계획·digiKam 예시 분류를 유지. 날짜·유사도·쓰기·복구·지원 범위의 미확인을 보존.
- Execution에서 바꿀 Phase·Build: 아직 없음. Topology·Idea·Verdict 합의가 남아 `execution.md`를 만들지 않는다. 향후 검증은 그 결과를 전제하는 기능 작업보다 앞서도록 제안했으며 사용자 승인 전 순서·범위를 확정하지 않는다.

현재 사용자 질문은 `idea.md`의 큰 범위 확인 하나다. 답변 부재를 저장 방식·안전 정책·조사 축소 승인으로 해석하지 않는다.
