# Research R002: 게임 애니메이션 제작 방법

- 상태: 작성 중
- 기준: [Idea](../idea.md)의 사용자 결정·제외·미확인
- 확인 날짜: 2026-09-07
- 영향: Phase 후보

## 질문·목적·범위

탐색·벤치마킹 및 발견한 기술 주장 검증: 터미널에서 웹으로 이어지는 세 게임의 애니메이션을 어떤 방법으로 제작할 수 있는가?

- 입력: 사용자 범위, 미구현 저장소 기준선, 제공된 합성 기술 문서·제작기·버전 설명.
- 출력: 제작 방식과 필요한 작업·제약·실패 조건 비교, 근거에 따른 미승인 구조 제안, 실제 환경에서 남은 검증.
- 사용자 경험: 같은 세션 자금과 게임 결과가 터미널 이후 웹 표현으로 이어지는 개발 순서. 사용자 경험·비용을 바꾸는 선택은 승인 없이 확정하지 않는다.
- 성공 조건: 적용 요소와 수정 부담을 기술 설명·코드 문맥·버전에 연결한다. 우리 PC에서의 정확성·성능은 실측 전 미확인이다.
- 실패 조건: API·벤치마크 문구를 현재 실행 결과로 오인하거나 구버전을 현재 API에 섞는 것, 미래 멀티를 현재 기능으로 확대하는 것.
- 확정 제약·저장소 사실: Idea 참조. 기존 제품 구조·실행 환경의 근거가 없으며 특정 엔진·라이브러리를 필수로 지정하지 않았다.
- 기술 분류: Windows·Chrome은 환경. 자료에서 발견할 엔진·라이브러리는 비교 후보 또는 구현 예시이며 채택 제약이 아니다.
- 미해결: 표현 계층 분담, 애니메이션 제작·결과 연결 방식, 코드·에셋 재사용 가능성, 대상 PC의 성능·정확성.

증거원 계획과 실행 한계는 [R001의 질문·목적·범위](R001-table-presentation.md#질문목적범위)와 같다. 이 질문의 Repository는 기존 구현 제약 확인, External evidence는 로컬 기술 원문·작성자 제작기·버전·사용 조건 검증에 필요하다. Lab은 현재 후보 비교에 필수적이지 않아 생략하며 제공 코드 실행·성능 측정을 하지 않는다. 구현 관점의 실제 검증은 후보와 반증 조건이 정리된 뒤 후속 필요 사항으로 연결한다.

먼저 접근 범주를 발견하고 기술 설명·실패 경험·현행/구버전 원문을 대조한다. 비용·지원·API는 묶음의 명시된 버전 범위로만 판정한다. 원문 수와 독립 작성 주체 수를 구분한다.

## 발견 후 검증할 주장과 자료 경로

Tablehaven의 기술 설명, Flatfelt의 축소 방식, Pileplay의 움직임 조정, Orbitroom의 실패 경험, Wheelkit의 버전 차이를 발견했다. 이 이름들은 가상 비교 사례이며 실제 설치·채택 후보로 전환하지 않는다. 복수 주장과 버전 충돌이 있어 전체 Evidence 의미를 사용한다.

|---|---|---|---|
| C5. 게임 상태·이벤트와 표현을 분리하는 방식이 터미널→웹 제작에 참고가 된다 | 구조 제안. 원 개발 기록·실패 경계 | Tablehaven 0.8. Orbitroom은 별개 맥락의 참고만 가능 | 애니메이션 콜백·탭 복귀가 추첨·정산을 변경하거나 다음 행동 전환을 깨뜨리면 설계 실패 |

후속 로컬 검색은 `spinTo`, `spin(seed)`, 37/24포켓, 원점·콜백·건너뛰기·고정 step, 제작 비용·라이선스·성능·누락 자료를 대상으로 한다. 성공 경로는 로컬 본문 확인이며 `.example` 웹 검증·코드 실행을 수행한 것으로 쓰지 않는다.

## 우리 조건의 제작 제안

아래는 모두 **출처: 에이전트 제안 / 미승인**이다. 특정 엔진이나 새 기능·서버·계정·저장소를 확정하지 않는다.

1. **P3 — 입력에 따른 게임 상태와 표현 진행을 분리한다.** 입력 → 규칙 처리 → 상태와 표현할 사건 → 터미널 출력 또는 웹 애니메이션이라는 책임 분리를 검토한다. 근거는 S2다. 원계획 대비 구조를 구체화하는 제안이며 규칙 재사용과 표현 지연의 분리에 이점이 있지만, 사건의 순서와 최종 상태를 함께 맞추는 부담이 생긴다. 더 작은 대안은 확정 상태만 읽어 최소 이동을 표시하는 방식이다. 이 경우 중간 배분·칩 이동의 풍부한 연출은 줄 수 있다. 표현 목표가 정해지기 전 복잡한 이벤트 프레임워크를 필수로 만들지 않는다.
2. **블랙잭에는 S2의 “라운드 결과를 먼저 만든다”를 그대로 옮기지 않는다.** 사용자가 히트·더블·스플릿을 고르기 전에 그 선택 이후의 게임 결과를 확정할 수는 없다. 수락한 행동마다 다음 결정 지점까지 규칙 상태를 처리하고 그 전이를 표현하는 쪽이 현재 요구에 맞는 적용 추론이다. 바카라·룰렛도 합의한 베팅과 규칙에 따라 결과가 결정되는 시점을 정해야 한다. 애니메이션 종료 콜백 자체가 추첨·정산을 수행하게 하면 S2의 실패와 같은 경계 위험이 있다.
3. **P4 — 결과를 먼저 정하는 룰렛이라면 목표 포켓에 맞춘 연출을 먼저 검토한다.** 근거는 S2와 S7/S8 계약 차이다. 원계획 대비 룰렛 표현 방식을 구체화하는 제안이다. 논리 결과와 화면을 맞추기 쉬운 계약을 얻지만 자연스러운 공의 이동·정지 경로는 별도로 만들어야 한다. 물리는 충돌 움직임의 대안으로 유지하되 결과 결정 책임·재현 조건·검증 부담이 달라진다. 어느 방식도 현재 채택하지 않았고 Wheelkit을 설치 후보로 추천하지 않는다.
4. **자산·연출 작업량은 줄일 곳과 남는 작업을 구분한다.** 3D를 택하면 카드 표면, 칩, 테이블, 룰렛과 공, 조명·재질·카메라, 배분/공개/이동/회전 연출의 제작 또는 적법한 자산 확보가 필요하다. 캐릭터·복도는 제외한다. 독립된 6덱은 규칙 데이터의 조건이며 카드 312장을 매번 화면에 모두 모델로 늘어놓으라는 요구가 아니다. 재사용 카드 형태·표면과 실제 표시할 카드 수를 어떻게 다룰지는 구현 후보이며 배치·에셋 스타일은 미정이다.

엔진/라이브러리의 실명 비교·성능 순위는 현재 자료로 뒷받침할 수 없다. 지금 비교할 수 있는 것은 HTML/CSS의 축소 표현, 웹의 3D 장면과 별도 UI, 보간/물리의 결과 계약, 규칙과 표현의 책임 분리다. 합성 사례가 사용한 방식만으로 특정 실제 엔진이 적합하다고 결론 내리지 않는다.

## 결론과 다음 행동

- **판정(문서상 계약 검증): 결론 가능.** C6의 버전/API 차이와 C7의 코드 범위·원점 오류는 원문으로 판정할 수 있다. C5는 참고 가능한 구현 설명이며 실제 제품 구조 채택이나 우리 구현 성공의 증명이 아니다.
- **판정(우리 제작 방식·엔진 채택 및 작동 검증): 결론 보류.** 화면 역할이 열려 있고 실제 코드/자산/사용 조건·실행 자료·우리 PC 측정이 없다. 전체 제작 탐색 완료로 처리하지 않는다.
- **비교 후 제안:** 원 개발 순서와 가까운 P3를 설계 검토 후보로 제안한다. 3D와 별도 UI(P1)는 시각 비교 후보이고, 평면 축소(P2)와 최소 상태 기반 표현도 유지한다. 목표 결과를 정하는 룰렛 조건에서만 P4를 우선 검토한다. 지금 확정된 제품 선택은 없다.
- **반대 근거:** 상태/표현 분리 뒤에도 새 라운드 경계 검사가 필요했다. 물리 충돌의 자연스러움은 보간 방식이 자동으로 얻는 장점이 아니다. CSS 축소는 입체 표현을 잃을 수 있고 실제 비용 우열은 실측되지 않았다.
- **신뢰도:** 명시 버전/API와 코드 포함 범위 판정은 높음. 사용자 조건에 대한 구조 제안은 중간. 제작 기간·성능·연출 품질·실제 재사용은 낮음/미확인. 모두 합성 문서 범위의 신뢰도이며 실제 제품 검증이 아니다.
- **Idea 영향:** P3·P4를 미승인 제안으로 연결하고 기존 결정·제외를 유지한다. 멀티가 미래라는 이유로 서버·온라인 프로토콜·계정·영속 저장을 추가하지 않는다.
- **Execution 영향:** Phase 후보에만 연결한다. 전체 Build 계획은 다음 대화 범위이며 이번에는 문서를 만들지 않는다. 아래 미실행 검증 조건을 후속 계획에서 해당 전제를 쓰는 제작보다 앞서 다룰 필요가 있다.

Web Evidence의 좁은 문서 계약 검증은 핵심 Claim·반증·원문·버전·공백의 추적이 가능하다. 전체 제작 탐색 closure는 통과하지 않았다. Lab 실행이 없다는 이유만이 아니라 실제 제작 후보와 사용 조건의 근거가 부족하기 때문이다. 추가 자료에 따른 탐색·검증을 다음에 이어가거나 사용자와 그 범위의 연기를 확인해야 한다. 미실행 항목을 완료한 조사·승인된 검증 Build로 기록하지 않는다.

문서 상태는 작성 중이다. 문서 계약 결론 가능과 사용자 합의에 따른 문서 확정은 서로 다르다.
