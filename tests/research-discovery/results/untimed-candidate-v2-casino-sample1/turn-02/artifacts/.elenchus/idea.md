# Idea: 룰렛·바카라·블랙잭 싱글 카지노에서 3D 웹앱으로

- 상태: 작성 중
- 시작 요청: 룰렛·바카라·블랙잭 세 게임을 할 수 있는 게임을 만든다. 룰을 적당히 합의한 뒤 터미널 기반 카지노 로직을 먼저 구현하고, 이후 애니메이션이 구현된 웹앱 게임으로 발전시킨다. 핵심 고민은 3D 애니메이션을 어떻게 만들지이며, 디자인 고찰과 레퍼런스 탐색이 많이 필요하다. 현재는 싱글 구현이 먼저이고 멀티플레이는 추후 확장 계획이다. 미래 멀티플레이를 고려해 카드게임은 6덱 구성으로 생각한다. 게임 시작 시 초기 자금을 정하고 플레이하며, 파산하면 게임 오버이고 파산하지 않으면 계속 진행한다. 저장 등은 현재 필요 없다.

사용자가 이번 응답에서 원요청의 아래 활성 구성을 확인했다. 조사는 웹 표현과 제작 방법의 선택 근거를 마련하는 활동이며 새 제품 기능이 아니다.

| 구성요소 | 상태 | 목표·근거 |
|---|---|---|
| 세 게임의 로직 | 활성 | 룰렛·바카라·블랙잭을 플레이한다. 세칙은 구현 전에 합의한다. |
| 세션 자금·진행 | 활성 | 사용자가 입력한 초기 자금을 세 게임에서 함께 사용하며, 파산하면 게임 오버이고 그전에는 계속 플레이한다. 세션 종료 후 보관하지 않는다. |
| 터미널 사용 표면 | 활성·먼저 | Windows PC에서 혼자 게임 로직과 세션 흐름을 사용한다. |

- 2026-09-07 관련 저장소 확인: `app.txt`는 `UNIMPLEMENTED PRODUCT STUB`이며 구현 코드·실행 환경·기존 기술 구조의 근거가 아니다. 관련 파일 목록과 계획 문서만 확인했다.
- `evidence/README.md`에 따르면 자료 전체는 가상 제품의 합성 문서다. 화면·영상·실행 데모가 없고, `.example` 주소는 웹 접근 대상이 아니다. 실제 제품 사실·직접 UX 관찰·우리 PC의 측정으로 일반화하지 않는다.
- 현재 실행의 네트워크·브라우저 연결·subagent 제한은 프로젝트 지침에 따른다. 메인이 로컬 원자료로 조사하며 기술적 격리나 도구 실패를 관찰한 것으로 보고하지 않는다.

## 사용자 결정

모두 출처는 사용자 요청이며, 이번 답변은 새 의미를 추가하지 않고 반영했다.

- 혼자 Windows PC에서 사용하고 웹은 데스크톱 Chrome 우선이다. 실제 현금·결제는 없다.
- 사용자가 초기 자금을 입력한다. 세 게임이 세션 자금을 공유하고 세션 종료 후 보관하지 않는다. 파산하면 게임 오버, 그렇지 않으면 계속 진행한다.
- 터미널 기반 싱글 게임을 먼저 만들고 이후 애니메이션 웹앱으로 발전시킨다. 멀티플레이는 미래 맥락이다.
- 바카라와 블랙잭은 각각 독립된 6덱이다. 룰렛은 싱글 제로다. 바카라 베팅은 플레이어/뱅커/타이, 뱅커 5% 커미션이다. 블랙잭은 더블·스플릿을 포함한다. 세칙과 베팅 단위는 구현 전에 따로 합의한다.
- 카지노 이동·캐릭터 조작은 필요 없다. 플레이어·딜러 캐릭터도 필수 요소가 아니므로 현재 제작 범위에 추가하지 않는다.
- 테이블 주변 여유 공간과 카드·숫자 가독성을 원한다. 실사보다 애니메이션에 가까운 3D 느낌을 원하지만 정확한 카메라·구도·색·재질은 미정이며 사례를 보고 선택한다.
- 웹 텍스트/버튼과 3D의 역할은 열려 있다. 필수로 지정한 엔진·라이브러리는 없다.
- 이번에는 디자인·상호작용 사례와 제작 방법을 조사한다. 기술 구조는 조사 근거를 보고 제안한다. 조사 범위 안 역할 분담은 허용하지만 현 환경에서는 메인이 수행한다.

- Release 확인·설치·별도 업데이트는 현재 대화에서 반복하지 않는다.

## 미확인·충돌

- 현재 요청에서 확인한 직접 충돌은 없다. 위 세칙·베팅 단위와 터미널의 상세 UX는 후속 합의 대상으로 남긴다.
- 시작 입력이 잘못되거나 잔액이 부족한 경우, 취소·종료 시점, 웹 로딩·애니메이션 실패·중복 입력 시 사용자 반응은 아직 정하지 않았다. 이 공백을 새 기능 요구나 확정 구현으로 바꾸지 않는다.
- 정상 흐름은 초기 자금 입력 → 세 게임 중 플레이 → 베팅·진행·정산 → 잔액으로 계속 또는 파산 시 종료다. 상세 게임 전환·명시적 종료 조작은 미정이다. 금액·카드·정산 불일치는 실패이나 구체적 판정 시나리오는 세칙 합의 뒤 정한다.
- 단독 사용자 본인이 플레이와 결과 확인을 담당한다. 실금전 손실은 없지만 잘못된 정산·읽기 어려운 화면은 의도한 플레이를 방해한다. 계정·외부 데이터·영구 보관은 필요 없다. 부분 성공·빈 출력·복구의 구체적 의미는 관련 흐름이 정해질 때 분류한다.
- Research: [화면·조작 비교](research/R001-table-presentation.md), [제작 방법 비교](research/R002-animation-production.md). 시각 관찰·로컬 성능·취향을 문서만으로 확정하지 않는다.
- 이번 자료의 문서 비교 결과는 마련했다. 화면·조작의 직접 관찰은 미수행이고 전체 디자인·제작 채택 결론은 보류다. 좁은 버전/API 판정과 전체 탐색 완료를 구분한다. 비교 결론·보류 범위에 대한 사용자 확인은 아직 받지 않았다.
