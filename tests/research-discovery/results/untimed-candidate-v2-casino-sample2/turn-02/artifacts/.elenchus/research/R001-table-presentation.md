# Research R001: 테이블 표현·조작과 애니메이션 제작 접근

- 상태: 작성 중
- 기준: [Idea](../idea.md)의 사용자 결정·제외·미확인 항목
- 확인 날짜: 2026-09-07
- 영향: Phase 후보. 전체 Phase·Build 계획은 이번에 작성하지 않는다.
- 목적: 탐색·벤치마킹, 발견한 구현 주장의 문서 검증. 제품 구현·Lab 실험은 하지 않는다.

## 중립 질문과 기준선

| 항목 | 조사 조건 |
|---|---|
| 중립 질문 | 가독성과 주변 공간을 함께 살리는 테이블 표현·조작 및 애니메이션 제작 접근은 무엇이며, 각 접근은 어떤 조건에서 맞는가? |
| 입력 | Idea의 확정 의도와 열린 선택, 제공된 합성 원자료. 제품 입력은 초기자금·베팅·게임 행동이다. |
| 출력 | 직접 유사·인접·실패 사례의 비교, 제작 접근과 조건부 제안, 근거 공백·미정 선택. |
| 사용자 경험 | Windows 개인 싱글 플레이. 터미널 이후 데스크톱 Chrome 웹에서 테이블 주변 공간과 카드·숫자를 보며 세 게임을 진행한다. |
| 성공 조건 | 서로 다른 해결 방식의 얻는 것·부담을 근거와 함께 비교하고, 문서 설명·추론·직접 관찰을 구분해 사용자가 다음 선택을 할 수 있다. 제품의 가독성·동작·성능 임계값은 아직 미정이다. |
| 실패 조건 | 소개 문구를 실제 화면 관찰로 바꾸거나, 합성 수치를 우리 PC 성능으로 일반화하거나, 취향·새 기능·엔진을 대신 확정하는 것. |
| 확정 제약 | Idea 참조. 세 게임·공통 세션 자금·독립 6덱·싱글 제로 등은 유지한다. 세칙 합의와 전체 Build 계획은 후속 작업이다. |
| 저장소·환경 사실 | 관련 파일 목록과 `app.txt`의 미구현 표시를 읽기 전용으로 확인했다. 기존 제품 구조는 없다. Windows PowerShell 파일 읽기가 가능하다. 네트워크·브라우저·subagent는 이번 실행에서 사용할 수 없으며 자료 묶음에 이미지·영상·실행 데모가 없다. |
| 미해결 질문 | 화면 구성·카메라·색·재질, 버튼과 3D의 역할, 동작 속도·입력 타이밍, 제작 도구·자산 조건·성능. |

사용자가 언급한 터미널 → 웹 순서는 필수 제약, Windows·데스크톱 Chrome은 대상 환경이다. 특정 엔진·라이브러리 언급은 없으며 발견되는 기술은 모두 후보로 취급한다.

호스트의 허용 쓰기 범위는 프로젝트이며, 현재 작업은 `.elenchus/` 계획 문서에만 쓴다. 원자료는 읽기 전용으로 취급한다. 도구 호출을 통한 브라우저·subagent 격리 검증을 수행한 것은 아니며 이번 사용 불가는 프로젝트 지침·환경 맥락에 근거한다.

## 탐색·검증 순서

먼저 제품 설명·매뉴얼에서 화면과 조작의 접근 범주를 발견하고, 연결된 개발 문서·제작기에서 구현·실패 조건을 대조한다. 문서의 용어·참조가 드러나면 해당 원문·버전으로 후속 확인한다. 같은 원문 재게시는 독립 근거로 세지 않는다.

검색 범위는 제공된 01–08 문서와 README다. 초기 확인 대상은 테이블 배치·카메라·입력·카드/휠 동작이며, 반대 확인 대상은 가독성 저하·지연·물리 결과·실패·재사용 라이선스·버전 변경이다. 최신성은 합성 문서가 명시한 버전과 날짜 안에서 판단하며 실제 최신 제품 여부를 주장하지 않는다.

`.example` 주소는 원천 식별자로만 기록한다. 인터넷·공개 API·archive·브라우저 대체 경로는 현재 환경에서 사용할 수 없어 시도하지 않는다. 이는 HTTP 접근 실패나 원자료 자체가 사라졌다는 판정이 아니다. 로컬 원문·개발 문서·재게시·후속 버전을 가능한 대체 경로로 사용한다.

이 묶음으로 비교할 수 있는 것은 설명된 배치와 동작의 차이다. 실제 화면을 나란히 본 비교 자료는 만들 수 없다. Tablehaven의 목재를 사용자의 재질 선호로, Pileplay의 과장된 토큰을 애니메이션풍 미술이 검증됐다는 증거로 바꾸지 않는다. 카메라·색·재질에는 현재 권장안이 없다.

## 제작 접근과 핵심 주장 검증

발견 이후 결정을 바꿀 가능성이 큰 순서로 S02의 콜백 실패·포켓 오차, S07→S08의 API 계약 변경, S01→S03의 재인용, 원자료의 실행·재사용 근거를 대조했다. 후속 검색은 전체 `evidence/`에서 `spinTo`, `spin(seed)`, 37/24포켓, 원점, 콜백, 라운드, 재게시, 측정·실험, 라이선스·재사용, 이미지·영상 표현을 확인했다. 관련 새 문서나 라이선스는 발견되지 않았다.

| 주장·결정 영향 | 확인 근거·반대 근거·반증 조건 | 적용 범위·판정 | 남은 공백·다음 행동 |
|---|---|---|---|
| C05. 규칙 상태와 표현을 분리하면 터미널→웹의 일관성을 다룰 수 있다. | S02 6–8행: 명령→상태·이벤트, 같은 규칙 모듈을 터미널과 브라우저가 호출. 애니메이션 콜백 추첨은 탭 복귀 후 멈춤을 일으켰다고 설명한다. 반증 조건: 분리해도 상태·표시가 어긋나거나 표현 완료가 추첨·정산을 바꾸는 경우. | **범위 제한**. 문서의 전략과 실패 경험은 확인. 우리 제품에서 정확성·복귀 안정성을 보장한 것은 아니다. | 최소 상태·표현 경계의 제안 근거로 사용. 탭 복귀·빠른 연속 입력·다음 라운드 경계에서 정산 중복과 표시 불일치를 후속 검증한다. |

## 우리 조건의 제작 제안 — 모두 미승인

각 제안의 출처는 **에이전트 제안**이다. 아래는 비교 후 검토할 방향이며 사용자의 확정 취향·구조가 아니다.

| 제안 | 원요청 대비 변화·얻는 것 | 부담·사라지는 결과·맞는 조건 |
|---|---|---|
| P01. 3D 테이블·소품과 HTML 숫자·행동 버튼을 결합하는 안을 우선 비교한다. | 기능 추가 없이 웹 표현의 역할을 나누는 후보. S01·S06에서 공간과 행동 정보를 분리한 방법을 가져온다. | 장면·HTML 상태와 배치를 함께 맞춰야 한다. 3D 물체를 직접 집어 조작하는 느낌은 줄 수 있다. 시각 연출과 명확한 조작을 함께 원할 때 검토할 안이며 실제 가독성은 미검증이다. |
| P02. 더 작은 대안으로 카드 이미지·CSS 입체감 접근을 남긴다. | 제작할 3D 모델·조명을 줄일 여지가 있다. S04에서 설명한 작업 감소를 비교 기준으로 쓴다. | 전체 3D 공간·입체 재질 표현이 줄어들며 사용자의 3D 기대를 충족할지 불명확하다. 사용자 동의 없이 이 방향으로 단순화하지 않는다. |
| P03. 규칙·세션 상태를 터미널과 웹 표현에서 독립시키고, 웹 연출은 이미 확정된 변화만 재생한다. | 터미널→웹 순서를 유지하는 구조 제안. 추첨·정산을 화면 좌표나 콜백에 맡기지 않는다. S02가 근거이며 미래 멀티용 서버를 추가하는 제안이 아니다. | 상태와 표현의 경계를 다루는 작업이 필요하다. 전체 이벤트 프레임워크 대신 현재 상태와 필요한 변화 목록부터 검토할 수 있다. 언어·라이브러리·파일 계층은 아직 결정하지 않는다. |

P03은 **블랙잭 라운드 전체를 플레이어 선택 전에 확정하자는 뜻이 아니다.** 현재 유효한 행동으로 확정할 수 있는 상태 변화만 규칙이 계산하고 다음 선택 지점에서 멈춘다. 더블·스플릿 이후 변화는 해당 입력 이후 처리해야 한다는 적용 추론이다. 6덱의 논리적 카드 상태와 화면에 보여 줄 카드를 분리해 검토하되 숨은 정보를 언제 공개할지는 후속 합의·검증 대상이다. 변화 목록은 현재 세션 표현용 제안으로서 저장·통계·리플레이 기능을 추가하지 않는다.

자산 제작에서는 단순 테이블·칩 형태와 카드 면 자산을 직접 만드는 작은 안을 검토할 수 있으나, 이는 에이전트의 미승인 추론이며 원자료에 제작 공정·소요 시간의 근거가 없다. 기존 코드·모델 재사용은 C09가 막혀 있다. 외부 모델링 도구의 사전 제작 애니메이션, 특정 웹 3D 엔진·라이브러리별 개발 난이도·호환성·라이선스는 이 묶음에 비교 자료가 없어 판단하지 않는다. 정확한 스타일·자산 제작 방식·엔진을 지금 고정하지 않는다.

## Verdict와 완료 판정

**전체 판정: 결론 보류.** 제공 문서에 한정한 접근법 비교와 버전 계약 반박은 결론 가능하지만, 요청된 시각·상호작용 사례의 직접 관찰과 실제 제작 후보 검증까지 충분히 완료한 것은 아니다. 상태는 `작성 중`이며 사용자 결론 확인도 아직 받지 않았다.

- 근거: S01·S04·S05·S06에서 혼합 표현·작은 대안·범위 밖 공간·인접 입력 사례를 비교했다. S02에서 규칙/표현 분리·콜백 실패·물리 대비 보간·좌표 실패를 확인했고 S07/S08에서 버전 차이를 직접 대조했다.
- 반대 근거: 혼합 표현은 두 표현 영역을 맞춰야 하고, 작은 대안은 원하는 3D 표현을 줄일 수 있다. 물리는 충돌감에 장점이 있다는 설명이 있다. Pileplay는 작은 숫자·동시 베팅의 근거가 없으며 어떤 사례도 실제 미술·사용성을 관찰하지 못했다.
- 채택·제외·보류: 기존 사용자 범위는 유지한다. Orbitroom식 이동·캐릭터·현재 멀티는 범위상 제외한다. Wheelkit 2.0 즉시 적용 주장은 반박한다. P01·P03·P04는 후속 비교·검증의 우선 제안이며 채택 합의가 아니다. P02는 작은 대안으로 보존한다. 카메라·색·재질·엔진과 추가 UI 기능은 보류한다.
- 한계: 합성 문서의 서술 범위, 출처 의존성, 시각 자료·실행물·라이선스·측정 부재. 이번 조사로 실제 제품의 우열이나 우리 제품의 완성도·성능을 주장할 수 없다.
- 신뢰도: 문서 간 차이·버전 계약·원요청과의 범위 충돌 판독은 **높음**(합성 묶음 안에 한정), 우리 조건의 제작 접근 추론은 **중간**, 시각적 적합성·성능·실제 재사용 판단은 **낮음**.
- Idea 영향: 사용자 합의는 그대로 유지하고 P01–P04와 G01–G05를 미승인 제안·미정 선택으로 연결한다. 웹 명료도를 확정으로 올리지 않는다.
- Execution 영향: 이후 터미널/웹 관련 Phase 후보의 근거가 되지만 번호·Build 계획은 만들지 않는다. 사용자의 다음 대화 범위를 존중한다.

Web Evidence 검증 기준에 해당하는 핵심 주장·원문·버전·반대 근거·공백·대체 경로는 위에 연결했다. 로컬 문서 검증을 웹·브라우저 조사 수행으로 계산하지 않는다. 시각·동작의 필수 근거가 없고 추가 관찰의 효용이 크므로 Web/Research의 전체 closure를 통과했다고 보고하지 않는다. 사용자가 후속 검증이나 연기에 동의하더라도 미수행 사례 탐색을 완료로 바꾸지 않는다.

사용자에게 확인할 내용은 **“문서 비교에 근거한 조건부 제안까지만 Research 결과로 확인하고, 시각·조작의 최종 선택과 엔진 채택은 근거 확보 전까지 보류한다”**는 결론이다. 이 확인은 P01–P04의 제품 채택, 구현, 전체 Build 계획 승인과 구분된다. 해당 보류 처리에 대한 사용자 답은 아직 없다.
