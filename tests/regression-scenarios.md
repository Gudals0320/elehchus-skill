# Elenchus 회귀 시나리오

이 파일은 사례 목록이며 실제 실행·통과 기록이 아니다. 실행 입력·판정 절차는 [실제 동작 평가](evaluation.md), 실행 상태와 근거는 [평가 기록](evaluation-results.md)에 둔다.

이 문서는 Elenchus의 호출·지속·완료 계약을 입력과 기대 상태로 검토한다. 각 시나리오는 독립적으로 실행한다.

이슈 #12에서 Idea 확정 뒤에만 조사하는 순서, 탐색 전 Claim map 강제, subagent 호출별 승인·Research당 한 명 제한, 읽기 전용 강제 미확인만으로 위임을 미지원 처리하던 기대값을 아래 현재 계약으로 교체했다. [기존 평가 절차](evaluation.md)의 R06a·R06b와 [평가 기록](evaluation-results.md)의 해당 결과는 변경 전 계약을 실행한 역사적 기록이며 새 동작의 통과 근거로 사용하지 않는다.

## Lifecycle

### 명시적 최초 호출

- 사전 상태: Elenchus 상태 표식이 없는 새 작업
- 입력: `$ELENCHUS 를 사용해 아이디어를 구체화해 줘.`
- 기대 상태: `[Elenchus · 진행 중]`으로 시작한다.

### 대체 호출 토큰

- 사전 상태: Elenchus 상태 표식이 없는 새 작업
- 입력: `SKILL:Elenchus 로 이 계획을 검토해 줘.`
- 기대 상태: 토큰의 대소문자와 관계없이 `[Elenchus · 진행 중]`으로 시작한다.

### 일반 이름 언급

- 사전 상태: Elenchus 상태 표식이 없는 작업
- 입력: `Elenchus가 작성한 계획을 요약해 줘.`
- 기대 상태: Elenchus를 시작하지 않고 상태 표식 없이 일반 요청으로 처리한다.

### 프로젝트 문서와 계획 용어

- 사전 상태: 프로젝트에 `.elenchus/`와 확정된 `execution.md`가 있으며 Elenchus 상태 표식은 없다.
- 입력: `Build #4 닫고 Phase #2의 Build #5 얘기해보자.`
- 기대 상태: Elenchus를 시작하지 않고 상태 표식 없이 일반 요청으로 처리한다.

### 진행 중 세션 지속

- 사전 상태: 직전 응답이 `[Elenchus · 진행 중]`이다.
- 입력: `첫 번째 선택으로 할게.`
- 기대 상태: 호출 토큰이 없어도 `[Elenchus · 진행 중]`으로 현재 질문 흐름을 계속한다.

### 완료 후 일반 모드

- 사전 상태: 직전 응답이 `[Elenchus · 완료]`이며 계획이 확정되었다.
- 입력: `Build #1부터 구현해 줘.`
- 기대 상태: Elenchus를 재활성화하거나 상태 표식을 붙이지 않고 일반 구현 요청으로 처리한다.

### 완료 후 명시적 재진입

- 사전 상태: 이전 응답에 `[Elenchus · 완료]`가 있고 `.elenchus/` 문서가 존재한다.
- 입력: `$elenchus 로 기존 계획을 재검토해 줘.`
- 기대 상태: 기존 문서를 읽고 `[Elenchus · 진행 중]`으로 재진입한다.

### 진행 중 구현 요청

- 사전 상태: 직전 응답이 `[Elenchus · 진행 중]`이다.
- 입력: `지금 코드까지 구현해 줘.`
- 기대 상태: 제품 구현을 시작하지 않고 계획 closure 또는 명시적 종료를 먼저 처리한다.

## Phase와 Build

### 기존 평면 계획 호환

- 사전 상태: Phase 헤더 없이 `### Build #1`부터 `### Build #5`까지 있는 기존 `execution.md`
- 입력: `skill:elenchus 로 새로운 범위를 Phase로 추가해 줘.`
- 기대 상태: 기존 Build를 내용·순서·번호 변경 없이 Phase #1로 묶고 제목 깊이만 `####`로 조정한 뒤 Phase #2를 추가한다.

### Phase 간 전역 Build 번호

- 사전 상태: 진행 중인 Elenchus의 Phase #1에 Build #1부터 Build #5까지 있음
- 입력: Phase #2의 첫 Build를 작성
- 기대 상태: Build 번호를 초기화하지 않고 Build #6을 부여한다.

### 기존 Phase 수정 시 새 Build

- 사전 상태: 진행 중인 Elenchus의 Phase #1과 Phase #2에 Build #1부터 Build #8까지 있음
- 입력: Phase #1을 수정하면서 Build 하나를 추가
- 기대 상태: 새 Build를 Phase #1에 두되 전역 최댓값 다음인 Build #9를 부여한다.

### 삭제 번호 보존

- 사전 상태: 진행 중인 Elenchus에 Build #1부터 Build #6까지 있고 Build #6을 삭제함
- 입력: 새 Build를 추가
- 기대 상태: Build #6을 폐기 이력의 제목으로 보존하고 새 Build에 #7을 부여한다.

### Build 분리

- 사전 상태: 진행 중인 Elenchus에 Build #1부터 Build #7까지 있음
- 입력: Build #3을 두 Build로 분리
- 기대 상태: 원래 범위를 담당하는 Build는 #3을 유지하고 추가 Build에 #8을 부여한다.

### Build 병합

- 사전 상태: 진행 중인 Elenchus에서 Build #3과 Build #4를 병합하기로 합의함
- 입력: 병합 결과를 문서에 반영
- 기대 상태: 더 작은 Build #3을 유지하고 Build #4는 대표 Build와 이유를 적은 폐기 이력으로 이동한다.

### Feature 계층 제거

- 사전 상태: 진행 중인 Elenchus에서 사용자가 새 Feature를 추가하고 싶다고 표현함
- 입력: `결제 Feature를 다음 계획에 넣어 줘.`
- 기대 상태: Feature 번호·헤더·문서를 만들지 않고 범위에 따라 Phase 또는 Build의 이름과 범위에 반영한다.

### 기존 Feature 계층 축소

- 사전 상태: Phase #1 아래 Feature #1과 그 하위 Build #1·#2가 있는 기존 계획
- 입력: `$elenchus 로 기존 계획을 수정해 줘.`
- 기대 상태: Feature 헤더를 제거하고 Build #1·#2를 Phase #1 바로 아래로 옮긴다. Feature의 의미는 각 Build의 이름·범위·설계 근거에 보존하고 Build 번호와 순서는 바꾸지 않는다.

### Phase와 Build closure

- 사전 상태: 진행 중인 Elenchus에 여러 Phase와 활성·폐기 Build가 함께 있음
- 입력: Execution closure audit 수행
- 기대 상태: 모든 활성 Build의 합의와 Phase 경계, 전역 번호의 고유성, 폐기 번호 보존을 검사하며 폐기 Build에는 활성 Build의 전체 필드를 요구하지 않는다.

## Research 목적과 진입

### Idea 확정 전 명시적 레퍼런스 요청

- 사전 상태: 초기 목적·제약은 확인했지만 화면 구도와 사용 흐름은 아직 정하지 않음
- 입력: `비슷한 제품과 참고할 만한 사례부터 찾아보고 방향을 정하자.`
- 기대 상태: Idea 전체 확정이나 같은 Research 진행 승인을 다시 요구하지 않고, 열린 선택에 필요한 탐색·벤치마킹을 시작한다. 사례를 보기 전에 화면 구도와 사용 흐름을 확정하지 않는다.

### 사례가 필요한 선택에서 탐색 제안

- 사전 상태: 여러 접근이 가능한 신규 기획에서 시각·상호작용을 실제 사례 없이 정하려 하며 아직 조사 범위를 합의하지 않음
- 입력: 다음 인터뷰 단계 선택
- 기대 상태: 사례가 바꿀 사용자 선택과 조사 범위를 설명해 탐색을 제안한다. Idea closure를 선행 조건으로 삼거나 사용자가 모르는 사례를 먼저 지정하게 하지 않는다.

### 높은 재작업 비용과 선행 검증

- 사전 상태: 한 표현 방식의 실행 가능성이 불명확하고 실패하면 여러 Build의 설계를 다시 해야 함
- 입력: Research 결과를 Execution에 반영
- 기대 상태: 공개 구현·실패 경험에서 배울 수 있는 내용을 먼저 조사하고, 우리 환경에서 확인해야 할 핵심 전제의 검증을 그 전제에 의존하는 제작보다 앞에 둔다.

### 탐색과 검증의 완료 분리

- 사전 상태: 선택한 기술의 Lab 실험은 통과했지만 요청된 레퍼런스 비교는 수행하지 않음
- 입력: Research 완료 판단
- 기대 상태: 기술 검증 결과는 기록하되 탐색·벤치마킹까지 완료했다고 처리하지 않는다. 남은 사례 발견·비교를 수행하거나 사용자가 해당 조사 범위를 제외·연기한 사실을 구분한다.

### 웹 탐색만으로 가능한 결론

- 사전 상태: 실제 사례와 공개 구현에서 접근법·적용 조건·실패 경험을 확인했고 실행 환경 실험이 선택을 바꾸지 않음
- 입력: 탐색 종료 판단
- 기대 상태: 접근법 비교·적합한 직접 근거·적용 가능성·결정 영향·타당한 종료 이유를 검토해 탐색을 완료한다. 형식적으로 Lab이나 검증 Build를 만들지 않는다.

### 직접 분야와 인접 분야의 접근 발견

- 사전 상태: 사용자가 제품 방향만 제시했고 비교할 후보는 없으며 인접 분야에서 같은 상호작용 문제를 다룸
- 입력: 레퍼런스 탐색
- 기대 상태: 같은 분야의 유사 제품과 문제의 일부를 해결한 인접 분야 사례를 탐색해 서로 다른 접근법을 비교한다. 제품명 여러 개나 같은 방법의 변형만으로 탐색 범위를 충족했다고 하지 않는다.

### 유력한 대안이 하나뿐인 경우

- 사전 상태: 합의한 제약에 맞는 접근을 조사했지만 다른 접근은 구체적인 조건 때문에 모두 제외됨
- 입력: 접근법 비교와 종료 판단
- 기대 상태: 탐색한 범주와 제외 근거, 남은 접근의 적용 조건을 설명한다. 비교 개수 할당량을 채우기 위해 부적합한 대안을 동등한 후보로 만들지 않는다.

### 적용 판단과 기존 선택 유지

- 사전 상태: 서로 다른 사례를 직접 비교했고 현재 방향이 사용자 조건에 가장 잘 맞음
- 입력: 탐색 결과 제시
- 기대 상태: 가져올 요소·필요한 변경·어려운 부분·비용과 유지 이유를 근거에 연결한다. 조사의 성과를 보이기 위해 기능을 추가하거나 기존 결정을 억지로 바꾸지 않는다.

### 조사 결과가 기존 선택과 충돌

- 사전 상태: 사례 관찰에서 기존 Idea의 선택이 목표를 해칠 가능성과 유효한 대안을 발견함
- 입력: 조사 결론 반영
- 기대 상태: 기존 선택과 대안의 실제 결과·적용 조건을 보여 주고 사용자 결정을 받아 Idea와 의존하는 계획을 갱신한다. 발견한 대안을 자동으로 확정하거나 기존 합의를 이유로 숨기지 않는다.

### 미완료 탐색의 Build 이관 금지

- 사전 상태: 레퍼런스의 실제 화면·동작을 아직 비교하지 않았고 관련 공개 자료를 더 확인할 수 있음
- 입력: `나중에 만들면서 참고하면 되니 Research는 완료라고 적어 줘.`
- 기대 상태: 미수행 비교를 Build에 넘긴 사실만으로 탐색 완료를 기록하지 않는다. 조사 지속 또는 해당 탐색의 제외·연기를 구분하고 선택에 남는 근거 공백을 명시한다.

### 탐색 완료와 환경 실험의 연결

- 사전 상태: 접근법 비교와 적용 판단은 끝났고 선택한 접근의 사용자 장치 성능만 실측이 필요함
- 입력: Research 결과와 다음 행동 기록
- 기대 상태: 탐색에서 확인한 결론과 아직 검증하지 못한 성능을 구분한다. 실측 주장·채택 및 실패 기준·의존하는 선택을 Lab이나 선행 검증 Build에 연결하며 성능 검증까지 완료했다고 하지 않는다.

## Research 파일과 Lab

### 독립 Research 파일 생성

- 사전 상태: `.elenchus/research/`가 없고 새 결정 질문의 Research 진행이 승인됨
- 입력: 첫 Research 문서 생성
- 기대 상태: `research/index.md`와 중립 문제명으로 된 `research/R001-*.md`를 만들고 index에는 ID·중립 질문·상태·영향·파일만 기록한다.

### Research ID 재사용 금지

- 사전 상태: R001과 R003의 기록이 있고 R002 파일은 삭제됨
- 입력: 새 Research 시작
- 기대 상태: 삭제된 R002를 재사용하지 않고 최댓값 다음인 R004를 사용한다.

### Legacy Research 이전

- 사전 상태: `.elenchus/research.md`만 있는 기존 프로젝트
- 입력: 새 Research를 시작해 문서를 수정
- 기대 상태: 기존 내용을 `research/R001-legacy.md`로 보존하고 index를 만든 뒤 기존 참조를 새 경로로 바꾸며 새 Research에는 R002를 부여한다.

### 혼합 구조의 안전한 이전

- 사전 상태: `.elenchus/research.md`와 `research/R001-*.md`가 함께 있음
- 입력: 새 Research 시작
- 기대 상태: 어떤 파일도 덮어쓰지 않고 legacy 문서에 다음 빈 ID를 부여한 뒤 새 Research에 그다음 ID를 사용한다.

### 기존 Research 읽기의 호환

- 사전 상태: 단일 legacy `research.md` 또는 목적별 기록이 없는 기존 `R###` 파일이 있음
- 입력: 기존 계획과 Research를 읽어 요약
- 기대 상태: 읽기만 했다는 이유로 파일을 이전하거나 새 형식을 채워 다시 쓰지 않는다. 원문에 없는 탐색·검증 수행 사실을 추정하지 않는다.

### 모드 질문 제거

- 사전 상태: Research의 질문과 조사 범위가 합의됨
- 입력: Research 진행 선택
- 기대 상태: `web | mixed | data`를 묻지 않고 탐색·벤치마킹과 검증·실험 중 필요한 목적을 구분한다. 저장소·외부 근거·Browser·Lab·위임의 필요·생략을 질문에 맞춰 판단하며 사용자에게 조사 수단을 고르게 하지 않는다.

### 조건부 Lab 생략

## Web Evidence Loop

### Web 또는 Browser Evidence 필요 시 진입

### 단일 권위 Claim의 간소화 기록

- 사전 상태: 공식 원문 하나가 직접 통제하는 저위험 Claim 하나이며 후보 비교·출처 충돌·접근 실패·중요한 공백이 없음

### 복합 Claim의 전체 기록

- 사전 상태: 탐색·벤치마킹 질문에서 가능한 접근법과 비교 후보 자체가 아직 알려지지 않음
- 입력: 외부 조사 시작
- 기대 상태: 문제·제약·열린 선택과 탐색할 범주를 기준으로 접근법을 발견한 뒤 유력 후보의 결정 Claim과 근거 공백을 구체화한다. 미리 선택한 해법의 Claim 검증만으로 탐색을 제한하지 않는다.

### 선택한 접근의 검증 계획

### Claim 확인과 탐색 완료의 구분

- 사전 상태: 최초 후보에 대한 모든 Claim을 확인했지만 요청된 대안 접근법의 발견·비교는 수행하지 않음

### 이미지 URL과 시각 관찰의 구분

- 사전 상태: 제품 소개·이미지 URL·대체 텍스트는 읽었지만 이미지나 실제 화면은 보지 못함

### 정지 화면과 움직임의 증거 구분

- 사전 상태: 테이블 게임의 스크린샷만 확인했고 애니메이션 속도·착지·다음 판 전환은 보지 못함
- 입력: 반복 플레이의 속도감과 자연스러움 비교
- 기대 상태: 스크린샷은 구도·정보 배치에만 사용한다. 동작 주장은 영상·데모의 실제 장면과 구간을 관찰하거나 미확인으로 남기며 제품 설명을 재생 관찰로 바꾸지 않는다.

### 시각적 선택을 위한 비교 자료

- 사전 상태: 직접 확인한 여러 화면 사례가 카메라·정보 배치에서 서로 다른 선택을 보여 줌
- 입력: 사용자에게 시각 방향 선택 제시
- 기대 상태: 사용자가 실제 사례를 비교할 수 있게 화면이나 확인 가능한 장면을 제시하고 가져올 요소와 적용 조건을 연결한다. 링크·감상 목록만으로 비교를 대신하지 않으며 로그인 화면 자료의 저장·공유 권한을 확대하지 않는다.

### 구현 주장에 적합한 근거

- 사전 상태: 동작 데모는 봤지만 목표 위치에 도달하는 구현 방법은 아직 확인하지 않음
- 입력: 해당 알고리즘의 재사용 권고
- 기대 상태: 공개 코드·기술 설명에서 방법과 조건을 확인하고 실제 관찰·자료의 설명·추론을 구분한다. 화면 결과만으로 내부 알고리즘을 확인했다고 하지 않는다.

### 단일 경로 실패 확대 금지

- 사전 상태: 공식 문서 URL 하나가 403으로 막혔지만 같은 내용을 제공하는 공식 공개 API와 feed가 있음

- 기대 상태: Claim 전체를 `근거 없음`으로 닫지 않고 API·feed 같은 관련 공개 대체 경로를 시도한다.

### 미시도 공개 경로와 조기 종료

- 사전 상태: 직접 페이지와 archive는 실패했지만 구조화 데이터와 공개 브라우저 렌더링은 아직 시도하지 않음
- 입력: 공개 접근 실패 선언 시도
- 기대 상태: 남은 경로를 접근 기록에 표시하고 관련 경로가 남아 있는 동안 실패나 Web closure를 선언하지 않는다.

### Terminal condition

- 사전 상태: 대상 페이지가 로그인·paywall·인증·CAPTCHA 또는 404를 요구함
- 입력: 공개 접근 계속
- 기대 상태: 해당 경로의 terminal reason을 기록하고 우회를 시도하지 않으며, 같은 Claim의 독립 공개 출처 또는 승인형 Browser Evidence 필요성을 판단한다.

### 부분 메타데이터의 범위

- 입력: Claim 판정
- 기대 상태: 확보한 필드만 근거로 사용하고 제품 동작이나 전체 본문 내용을 추정하지 않는다.

### 중복 출처 제거

- 사전 상태: 세 기사와 블로그 하나가 모두 같은 보도자료를 재인용함
- 입력: 독립 출처 수와 Evidence matrix 갱신
- 기대 상태: 파생 페이지를 서로 독립적인 네 개 출처로 계산하지 않고 원문 하나의 계보로 묶는다.

### 사용자 후기 적용 범위

- 사전 상태: 특정 버전과 계정 유형의 사용자 후기 하나가 장애를 보고함
- 입력: 일반 서비스 동작 Claim에 반영
- 기대 상태: 실제 UX·실패 사례 증거로 사용하되 전체 사용자나 다른 버전·플랜으로 일반화하지 않는다.

### 교차 확인과 공식 원문 예외

- 사전 상태: 중요한 일반 주장 하나는 여러 독립 출처가 있고 다른 정책 주장은 유일한 권위 있는 공식 문서만 있음
- 입력: Web closure 검사
- 기대 상태: 첫 주장은 가능한 독립 출처 둘 이상으로 확인하고, 두 번째 주장은 불필요한 두 번째 자료 없이 공식 원문의 권위와 적용 범위를 기록한다.

### 반대 근거 탐색

- 사전 상태: 전체 기록이 필요한 복합 Claim에서 지지 자료만 수집했고 반대 사례나 실패 조건을 찾지 않음
- 입력: Web closure 시도
- 기대 상태: 반대 검색 범위와 결과가 기록되기 전에는 closure를 통과하지 않는다.

### Verdict 영향 기반 gap 선택

- 사전 상태: 자료가 적은 배경 Claim과 Verdict를 뒤집을 수 있는 미확인 핵심 Claim이 함께 있음
- 입력: 다음 검색 대상 선택
- 기대 상태: 검색량이 적은 배경 Claim이 아니라 Verdict 영향이 큰 핵심 Claim을 선택한다.

### 고정 검색 횟수 금지

### 반복 근거의 중단

- 입력: 다음 조사 가치 평가
- 기대 상태: 다음 검색이 Verdict를 바꿀 가능성이 낮은 이유를 기록하고 중단 후보로 처리한다.

### 남은 공백 연결

- 사전 상태: 필요한 접근법 비교는 마쳤지만 web과 Browser로 판정할 수 없는 우리 환경의 중요한 검증 Claim이 남음

## Browser Evidence

## Research subagent 운영

- 입력: 탐색용 brief 작성

- 입력: Research 계속
- 기대 상태: 기존 agent의 구체적인 후속 조사나 복구 가능한 재시도를 우선하고 필요하면 메인이 보완한다. 매번 재승인을 받거나 동일 질문으로 새 agent를 반복 생성하지 않으며 권한 거절·실제 미지원을 무한 재시도하지 않는다.

### 실제 위임 미지원 시 메인 조사

- 사전 상태: 현재 환경에 호출 가능한 subagent 도구가 없거나 위임 연결이 복구 불가능함
- 입력: 합의된 공개 Research 계속
- 기대 상태: 미지원 사실과 독립성 한계를 알리고 메인이 접근법 발견·근거 확인·비교를 수행한다. 없는 도구를 호출하거나 메인 조사를 독립 agent 수행으로 보고하지 않는다.

### 동일 원문의 중복과 agent 동의

- 사전 상태: 사례 탐색과 집중 검증 agent가 같은 원문을 각각 인용하며 같은 결론을 반환함
- 입력: 근거 수와 신뢰도 판단
- 기대 상태: 원문 계보 하나로 계산하고 agent 수·동의를 독립 근거의 수로 바꾸지 않는다. 결정에 필요한 추가 독립 근거가 있으면 따로 확인한다.

### 메인의 결정적 근거 재확인

- 사전 상태: agent의 권고를 좌우하는 출처를 메인이 아직 확인하지 않았거나 원문이 반환 요약과 다름
- 입력: Research Verdict 작성
- 기대 상태: 메인이 결정적 원문과 적용 범위를 직접 재확인해 차이·충돌·공백을 반영한다. agent 결론을 그대로 채택하거나 다수결로 완료 판정하지 않는다.

### Subagent와 Lab 역할 분리

- 사전 상태: research subagent가 실제 관찰이 필요한 주장을 제안함
- 입력: subagent 결과 수신
- 기대 상태: subagent는 실험하지 않고 Lab 후보만 반환하며 메인 세션이 필요성을 다시 판단하고 `.elenchus/lab/R###/`에서만 실험한다.

### 결과 의미만 보존

- 사전 상태: research subagent가 긴 후보 비교·직접 관찰·추론과 출처를 반환함
- 입력: Research 파일 갱신
- 기대 상태: agent 원문을 저장하지 않고 접근법 범주·직접 근거·자료 설명과 추론의 구분·핵심 차이·적용 조건·채택 및 제외 근거·결정 영향·공백과 다음 행동을 정제한다. 메인이 종합·사용자 선택·목적별 완료 판정을 책임진다.

## Release 확인 네트워크 권한

### Windows 네트워크 권한 감지

- 사전 상태: Windows Codex 샌드박스가 GitHub 네트워크 연결을 `WinError 10013`로 차단함
- 입력: `scripts/release_update.py --check` 실행
- 기대 상태: `status: permission_required`, `exit_code: 2`, 현재 버전과 오류 메시지를 JSON으로 출력하고 Python 종료코드 `2`를 반환한다.

### 권한 상승 1회 재시도

- 사전 상태: 첫 확인이 `permission_required`와 종료코드 `2`를 반환함
- 입력: Elenchus 최초 진입 계속
- 기대 상태: 셸 실행 도구가 바깥 종료코드를 일반 실패로 표시하더라도 JSON의 `permission_required`를 기준으로 동일한 `--check` 명령에 필요한 네트워크 권한 상승을 요청해 한 번만 재시도한다.

### 권한 요청 거절

- 사전 상태: 사용자가 네트워크 권한 상승을 거절함
- 입력: Elenchus 최초 진입 계속
- 기대 상태: 실패 이유를 한 줄로 알리고 현재 버전으로 인터뷰를 시작하며 같은 작업에서 확인이나 권한 요청을 반복하지 않는다.

### 권한 상승 재시도 실패

- 사전 상태: 권한 상승으로 재시도한 `--check`도 실패함
- 입력: Elenchus 최초 진입 계속
- 기대 상태: 실패 이유를 한 줄로 알리고 현재 버전으로 인터뷰를 시작하며 세 번째 확인을 실행하지 않는다.

### 일반 GitHub 확인 실패

- 사전 상태: GitHub HTTP 오류, DNS 실패 또는 기타 권한 외 오류가 발생함
- 입력: `scripts/release_update.py --check` 실행
- 기대 상태: `status: unavailable`, `exit_code: 1`과 Python 종료코드 `1`을 반환하고 권한 상승 재시도 없이 현재 버전으로 인터뷰를 계속한다.

### 정상 Release 확인

- 사전 상태: 샌드박스에서 GitHub 연결이 가능함
- 입력: `scripts/release_update.py --check` 실행
- 기대 상태: `up_to_date` 또는 `update_available`과 종료코드 `0`을 반환하고 권한 상승을 요청하지 않는다.
