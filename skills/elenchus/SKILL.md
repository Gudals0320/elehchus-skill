# Elenchus

사용자 목적에 필요한 기능적 재료를 설계하고 실제로 구현·연결·검증한다. 흐름은 **Topology ↔ Research → 재료와 결론 전달 → 일반 Codex 작업**이다. 연구의 질문과 달성 조건을 충분히 준비한 뒤 시행착오를 끝까지 진행한다.

확보할 것은 작동하는 재료와 그 의미다. 입력·출력·환경 제약·실패 조건·기능 연결은 설계할 수 있다. 종합 사용자 경험, 최종 화면·동선·제품 중심 개념과 전체 제품 개발 계획은 이후 제작자에게 남긴다. 사용 목적은 재료 선택과 검증의 기준으로 이해한다. 코드 양이나 CLI·GUI 여부로 이 경계를 판정하지 않는다.

## 세션 경계

| 현재 조건 | 처리 |
|---|---|
| 현재 사용자가 `$elenchus` 또는 `skill:elenchus`로 호출 | 시작 또는 기존 탐구 재개. 대소문자·뒤의 한국어 조사를 허용 |
| 최신 유효 상태가 `[Elenchus · 진행 중]` | 호출 없이 같은 세션 계속 |
| 최신 상태가 `[Elenchus · 완료]`이거나 활성 세션과 호출이 없음 | 일반 요청 처리. 스킬 이름·과거 표식·파일 존재로 재진입하지 않음 |

진행 중 응답 첫 줄은 `[Elenchus · 진행 중]`이다. Topology 정리나 개별 Research 결론은 세션 종료가 아니다. 사용자가 세션 자체의 중단·종료를 요청하면 현재 재료·결정·미해결을 남기고 완료 표식으로 끝낸다. 기능·후보의 취소는 해당 범위만 변경한다.

`좋아`, `진행`, `계속`은 제시된 내용에 대한 답이다. 보이지 않은 제품 선택이나 추가 권한의 승인으로 확대하지 않는다. 명시적으로 요청하거나 이미 합의한 조사·기능 실험·범위 내 위임은 다시 승인받지 않는다.

## 문서와 지침 읽기

| 작업 | 현재 프로젝트 자료 | 읽을 지침 |
|---|---|---|
| 탐구 시작·범위/목표 갱신 | `topology.md`, 있으면 `research/index.md` | [Topology](stages/topology.md) |
| 실제 조사·실험 | Topology 관련 목표, index, 현재 질문·직접 의존하는 R 문서 | [Research](stages/research.md) |
| 접근법·사례 발견 | 현재 연구의 중립 질문·환경·열린 선택 | Research가 연결하는 [Discovery](stages/discovery.md) |
| 외부 원문·화면 검증 | 현재 비교/주장의 근거 공백 | [Web Evidence Loop](stages/web-evidence-loop.md) |
| 코드·데이터·테스트 확보 | 현재 R 질문과 실험 기준 | [Lab](stages/lab.md) |

프로젝트 기준 위치는 `.elenchus/`다. `topology.md`는 목적·기능·연구 질문·달성 조건·현재 판단을, `research/index.md`와 `R###`는 연구별 근거·재료·판정을 담는다. 실험 재료는 `lab/R###/`에 둔다. 관련 없는 과거 연구·데이터·환경을 일괄 읽지 않는다. 문서만 필요하면 실행 환경이나 전체 로그를 로드하지 않는다.

## 공통 진행 원칙

### 목적과 달성 조건

Topology에 현재 목표, 필요한 재료·입출력, 실제 제약, 연구 질문·달성 조건과 조사·실험 방향을 잡는다. 그 준비가 되면 Research를 수행한다. 조사해야 알 수 있는 사항은 열린 질문으로 두고, 모든 미래 제품 선택을 먼저 정하도록 요구하지 않는다.

복수 해법이 가능한 연구에는 실제 웹 탐색과 서로 다른 질문을 맡은 탐색 subagent 두 명이 기본이다. [Research subagent](stages/research.md#research-subagent)의 좁은 사실 확인·도구 미지원 예외를 적용하며 생략을 수행으로 보고하지 않는다. 웹과 실험을 왕복하고, 익숙한 후보의 검증에만 머물지 않는다.

### 질문과 합의

조회 가능한 코드·문서·환경 사실은 먼저 확인한다. 사용자에게 물을 때는 후속 판단을 크게 바꾸는 목적·기능·입출력·제약의 질문 하나를 고르고, 이유·대안·권고를 사용자가 이해할 결과로 설명한다. 기능 내부의 가역적 구현 선택을 질문으로 늘리지 않는다.

명확한 답은 반영 내용을 알리고 이어간다. 새로운 해석이나 충돌이 있을 때만 짧게 재진술해 확인한다. 결정은 `사용자 결정 | 에이전트 제안 | 확인된 사실 | 미확인`을 구분한다. 사용자가 정한 요구·비용·데이터 의미를 기술적 편의로 바꾸지 않는다. 후보·예시를 필수 제약으로 승격하지 않는다.

같은 목적의 추가 질문·실패 원인·대체 접근은 메인이 Topology에 반영하고 Research를 계속하거나 새 R을 연다. 사용자 목적·중요한 제약·큰 비용·접근 범위가 바뀔 때만 해당 변경을 합의한다. 달성 조건을 낮춰 실패를 숨기지 않는다.

### 노력과 결과

실제 시행착오와 재현 가능한 결과에 노력을 쓴다. 조사량·문서 길이·agent 수 자체는 품질이 아니다. 실패하면 가설·접근을 갱신하고, 진전 없는 같은 호출을 반복하지 않는다. 의미 있는 다음 행동이 있고 합의 범위 안이면 계속한다. 접근 제한이나 필요한 사용자 결정이 실제 차단이면 근거와 재개 조건을 남긴다.

추론과 탐색 깊이는 모델·effort·도구 환경에 영향을 받는다. 이번 계열의 기준 평가는 Astra/xhigh다. 중간 effort에서 깊이가 부족했다는 사용자 관찰을 설정 선택에 참고하되, 다른 모델의 성능을 보장하거나 모델·effort를 자동 변경하지 않는다.

## 결과 전달과 종료

활성 연구 목표별로 답·재료·실행/테스트 결과·미검증을 대조한다. 실행 불가능성을 충분한 근거로 확인한 연구도 유효한 결론일 수 있지만 기능 구현 성공과 구분한다. 필요한 연구가 남으면 이어가고, 제외·연기는 사용자의 결정과 영향을 보존한다.

마지막에는 확보한 재료와 실행 방법, 중요한 제약·실패 경험, 남은 범위와 이후 제작자의 재량을 한 번 정리해 검토받는다. 사용자가 이미 결과 기준에 따른 종료까지 맡겼으면 같은 승인을 다시 요구하지 않는다. 내부 R마다 결론 승인을 반복하거나 전체 제품 UX·Build 계획 확정을 종료 조건으로 요구하지 않는다.

유효한 최종 확인 또는 사전 위임에 따라 첫 줄을 `[Elenchus · 완료]`로 바꾸고 끝낸다. 이후 일반 요청은 표식 없이 수행한다. 종합 제품화 요청이 세션 도중 오면 현재 연구 재료와 공백을 정리해 세션 종료/범위 전환을 명확히 하고 일반 작업으로 이어간다. 기능 재료 구현을 제품화 요청으로 오인해 막지 않는다.

Pro를 포함한 다른 제작자에게 넘기는 handoff는 선택 사항이다. 요청되면 목적·확정 제약·코드·데이터·테스트·실패 경험·열린 선택을 묶고 실제 공개/전달 범위는 그 요청에 따른다. handoff 준비만으로 자동 업로드하거나 Pro 사용을 강제하지 않는다. 기준 자료는 각 R에서 참조하며 별도 필수 인계 단계를 만들지 않는다.
