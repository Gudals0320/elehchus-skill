# Execution 단계

## 정체성

`execution.md`는 Idea의 모든 행동·출력·실패 동작·성공 기준을 Phase와 Build에 연결하고, 사용자가 각 Build의 결과와 Approve를 이해·합의한 뒤 전체 계획을 닫는다.

실제 구현은 시작하지 않는다. 실행 포인터, 개발 진행 상태와 개발 중 자동 재설계도 기록하지 않는다.

계획 계층은 `Phase → Build` 두 단계만 사용한다. Phase는 하나의 계획 범위를 묶고 Build는 사용자가 결과를 확인하고 Approve하는 최소 단위다. Feature를 독립 계층·번호·문서 단위로 만들지 않으며 사용자가 Feature라고 표현한 내용은 범위에 따라 Phase 또는 Build의 이름과 범위에 포함한다.

## 시작 문서

확정된 `idea.md`, 존재하는 `research/index.md`와 현재 Execution에 영향을 주는 확정 `R###` 파일을 읽고 `./.elenchus/execution.md`를 만든다. 관련 없는 Research 파일과 기존 Lab은 자동으로 읽지 않는다. 각 결론이 사례 탐색, 문서 확인, 직접 관찰, 실제 실험 중 무엇에 근거하는지 확인한다. 검증 계획의 합의를 실제 검증 성공으로 해석하지 않는다.

```markdown
# Execution: {주제}

- 상태: 작성 중
- 기준: idea.md{, research/R###-neutral-topic.md}

## Idea 커버리지

| Idea 행동·출력·실패·성공 기준 | Phase | Build |
|---|---|---|

## 전체 Phase·Build 순서
## 사용자 결정
## 에이전트 제안
## 구현 위임
## 제외
## 미확인·충돌
```

## Phase와 Build 번호

`idea.md`는 프로젝트 전체의 누적 의도 계약으로 사용하고 Research 근거는 `research/index.md`와 실제 사용한 확정 `R###` 파일을 참조한다. Phase별 문서 사본이나 별도 `contract.md`를 만들지 않는다. 모든 Phase와 Build는 하나의 `execution.md`에 기록한다.

- Phase 제목은 `### Phase #N — 이름`, Build 제목은 해당 Phase 아래의 `#### Build #N — 이름` 형식을 사용한다.
- Phase 헤더 없이 `### Build #N` 형식만 있는 기존 문서는 전체를 Phase #1로 간주한다. 새 Phase를 추가하며 문서를 수정할 때 기존 Build의 내용·순서·번호를 바꾸지 않고 `### Phase #1 — 기존 계획` 헤더 아래로 옮기며 Build 제목의 깊이만 `####`로 조정한다.
- 기존 `Phase → Feature → Build` 문서를 다시 열면 Feature 헤더를 제거하고 하위 Build를 같은 Phase 바로 아래로 올린다. Build 번호와 순서는 유지하고 Feature의 이름·설명·결정 근거는 각 하위 Build의 이름, 범위 또는 설계 근거에 보존한다. Build가 없는 Feature는 내용에 따라 Phase나 새 Build 후보로 제시하고 사용자 결정 없이 변환하지 않는다.
- 기존 Phase를 수정할지 새 Phase를 추가할지 모호하면 차이를 설명하고 사용자에게 하나를 선택받는다. 이미 계획한 결과를 보완·수정하면 기존 Phase를 열고, 확정 계획 이후 새로운 결과나 범위를 추가하면 새 Phase를 만든다.
- 확정된 계획을 다시 열면 문서 상태를 `작성 중`으로 바꾼다. 기존 Phase를 수정할 때는 영향받는 Build만 `미확인`으로 되돌리고, 새 Phase를 추가할 때는 기존 Phase의 합의 상태를 유지한다.
- 새 Phase 번호는 문서에 기록된 가장 큰 Phase 번호의 다음 번호다. 평면 문서만 있으면 다음 Phase는 Phase #2다.
- 새 Build 번호는 활성·폐기 이력을 포함해 `execution.md`의 Build 제목에 기록된 가장 큰 번호의 다음 번호다. Build가 하나도 없을 때만 Build #1부터 시작한다.
- Phase와 Build 번호는 안정적인 ID다. 이동·재배열해도 바꾸지 않고 삭제된 번호도 다시 사용하지 않는다.
- Build를 분리하면 기존 목적과 Approve를 가장 직접 유지하는 Build 하나가 번호를 유지하고 추가 Build에 새 번호를 부여한다. 어느 Build가 기존 목적을 유지하는지 모호하면 사용자에게 확인한다. 병합하면 대상 중 가장 작은 Build 번호를 유지하고 나머지는 폐기 이력으로 옮긴다.
- 삭제되거나 병합에 흡수된 Build는 `## 분리·병합·삭제·재배열한 Build` 아래에 `#### Build #N — 이름 (폐기)` 제목, 처리 방식, 이유와 대표 Build를 남겨 번호 계산에서 계속 발견되게 한다. 폐기 Build에는 활성 Build의 전체 필드와 합의 상태를 요구하지 않는다.

## 전체 Phase·Build 초안

Idea를 문장별로 읽고 다음과 같이 연결한다.

1. 사용자의 시작 행동을 첫 Build에 연결한다.
2. 출력과 실패 동작을 처음 관찰할 수 있는 Build에 연결한다.
3. 각 성공 기준을 사용자가 판정할 Build에 연결한다.
4. 선행 능력과 외부 조건을 앞 Build 또는 선행 조건에 연결한다.
5. 연결되지 않은 Idea 문장이 있으면 Build를 추가하거나 범위를 수정한다.
6. Idea나 선행 조건에 연결되지 않는 Build는 활성 계획에서 제외하고 폐기 이력으로 옮긴다.

모든 Build를 같은 깊이로 작성하고 각 Build를 하나의 Phase에만 둔다.

```text
Phase #N — 이름

Phase 목적:
이 Phase가 기존 계획에 추가하거나 수정하는 결과

Build #N — 이름

합의 상태: 미확인 | 합의 완료

목적:
이 Build가 가능하게 할 사용자 행동 또는 시험할 전제

Idea 연결:
담당하는 Idea 문장

선행 조건:
먼저 확인해야 하는 Build와 외부 조건

범위:
이번 Build에서 만들거나 조사할 것

제외:
이번 Build에서 하지 않을 것

산출물:
사용자가 실행·열람·비교할 파일, 화면, 명령 결과 또는 분석 결과

AI 완료:
구현자가 코드·테스트·파일 생성을 끝냈다고 판정할 조건

사용자 행동:
산출물을 확인하기 위해 사용자가 직접 할 일

관찰 결과:
사용자가 눈·귀·수치로 확인할 결과

Approve:
성공과 실패를 구분하는 관찰 조건

설계 근거:
사용자 결정·증거·전제와 선택 출처
```

뒤 Phase와 Build도 이름과 목적만 남기지 않는다. 필드를 작성할 수 없으면 사실을 조사하거나 사용자 결정을 받은 뒤 Execution을 확정한다.

## 전체 지도 공격

### Idea 커버리지

- 모든 행동·출력·실패 동작·성공 기준이 Phase와 Build에 연결되는가
- 같은 Idea 문장을 여러 활성 Build가 중복 구현하는가
- Idea나 선행 조건에 연결되지 않는 활성 Build가 있는가
- 문서 순서상 마지막 활성 Build의 Approve가 Idea의 최종 성공을 판정하는가

### Phase 경계

- 모든 활성 Build가 정확히 하나의 Phase에 속하는가
- Phase 목적이 포함된 Build의 사용자 결과를 설명하는가
- 모든 활성 Phase에 하나 이상의 활성 Build가 있는가
- 기존 결과의 보완과 새로운 범위 추가가 같은 Phase에 섞였는가
- 앞 Phase의 결과나 Approve를 전제로 하는 관계가 드러나는가
- Feature가 Phase와 Build 사이의 별도 계층으로 만들어지지 않았는가

### 개별 Build

- 목적이 사용자 행동 하나 또는 전제 하나로 설명되는가
- 서로 다른 목적이 한 Build에 섞였는가
- 같은 사용자 결과를 불필요하게 여러 Build로 나눴는가
- 사용자가 산출물을 직접 실행·열람·비교할 수 있는가
- AI 완료와 사용자 Approve가 분리되는가
- Approve가 성공과 실패를 다른 관찰로 구분하는가
- 구현자가 사용자 행동·출력·실패를 새로 결정해야 하는가

### Build 경계

- 선행 조건이 실제로 앞 Build 결과를 요구하는가
- 순서를 바꾸면 폐기되는 작업이 줄어드는가
- 앞 Build Approve 없이 뒤 Build를 시작할 수 있는가
- 두 Build를 합치면 사용자 확인 행동이 둘 이상 섞이는가
- Build 사이에 Idea 행동이 빠졌는가

### 전체 순서

- 틀렸을 때 여러 Build를 폐기하는 전제를 먼저 시험하는가
- 탐색에서 확인한 재사용 해법·적용 제약·실패 경험이 범위와 순서에 반영됐는가
- 미완료 사례 비교를 뒤 Build에 넘기는 것만으로 Research를 완료 처리하지 않았는가
- 우리 환경에서만 검증할 전제를 그 전제에 의존하는 제작·통합보다 먼저 시험하는가
- 확인하지 않은 능력 위에 UI·통합·패키징 Build가 놓였는가
- 사용자 결과를 처음 볼 때까지 내부 코드 Build만 이어지는가
- 모든 Build가 같은 깊이로 작성됐는가
- 구현자가 제품 결정을 내려야 하는 미확인 항목이 남아 있는가

## Build별 합의 루프

전체 Phase·Build 초안을 먼저 만든 뒤 새로 작성되었거나 영향받은 가장 이른 Build부터 문서 순서대로 합의한다. 최초 계획처럼 기존 Build가 없을 때만 Build #1부터 시작한다.

후속 Build의 미해결 전제가 앞선 Build도 바꾸면 [공통 질문 선택 규칙](../SKILL.md#2-다음-질문-선택)에 따라 그 전제와 영향을 먼저 설명하고 선행 관계·문서 순서를 조정한다. 번호와 유효한 합의는 보존하며, 중요한 질문을 먼저 다뤘다는 이유로 후속 Build 전체를 합의 완료로 바꾸지 않는다.

1. Build의 목적·범위·산출물·사용자 행동·Approve를 한 번에 보여 준다.
2. 비개발자가 판단할 수 있도록 기술 구조보다 실제 결과 차이를 먼저 설명한다.
3. Build의 `목표 | 제약 | 성공 기준 | 맥락` 등급을 평가한다.
4. 공통 질문 선택 규칙으로 현재 Build의 미해결 차원에 대해 질문 하나를 한다.
5. 선택이 필요하면 현재 상황, 결과 차이, 얻는 것·잃는 것, 맞는 조건과 권장 근거를 본문에 제공한다.
6. `유지 | 축소 | 연기 | 분리 | 병합 | 제거 | 만들지 않기`를 실제 후보로 검토한다.
7. 미해결이 없으면 전체 현재 Build에 대해 `합의 완료 | 수정 | 분리 | 병합`을 받는다. 이미 전체 현재 내용을 보여 주었고 그 내용에 대한 명확한 합의를 받았다면 같은 내용을 다시 승인받지 않는다.

기본은 개별 합의이며, 합의가 끝나기 전에 다음 Build를 확정하지 않는다. 아래 조건을 모두 충족할 때만 저위험 Build를 한 묶음으로 확인할 수 있다.

- 사용자가 해당 범위에서 묶음 확인 방식을 허용했고 각 Build의 전체 현재 내용을 보았다. 허용한 방식을 매번 다시 선택하게 하지 않는다.
- 각 Build가 독립적이며 서로 다른 제품 선택이 남아 있지 않다. ID가 다르다는 사실만으로 독립성을 판단하지 않는다.
- 비용·데이터·권한·파괴적 변경·범위 확대·사용자가 위임하지 않은 중요한 제품 선택이 포함되지 않는다. 이런 항목은 개별 확인한다.

묶음에서는 하나의 확인 질문으로 표시한 Build들만 합의한다. 질문 안에 별도 선택 여러 개를 숨기지 않는다. 제목만 보여 준 항목, 보이지 않은 Build, 나중에 바뀐 내용이나 구현·도구 실행을 포함하지 않는다. 사용자가 개별 확인으로 바꾸면 즉시 따른다.

합의 범위를 구분할 필요가 있으면 해당 Build에 제시한 내용·변경 요약과 사용자 응답의 위치를 함께 남긴다. 별도 상태 파일은 만들지 않는다. 요약 뒤 재개할 때 범위를 복원할 근거가 없으면 확인하며, 과거의 `좋아`나 문서의 합의 표식만으로 현재 내용에 대한 승인을 추정하지 않는다.

Phase나 Build를 수정·분리·병합·삭제·재배열하면 직접 바뀐 항목과 그 전제·출력에 의존하는 Build만 `미확인`으로 되돌리고 Idea 커버리지, Phase 경계와 전체 순서를 다시 검사한다. 묶음 중 하나가 바뀌어도 독립적인 나머지 합의는 보존한다. 공유 전제가 바뀌면 관련 항목을 함께 재검토한다. 번호는 바꾸거나 재사용하지 않는다.

## 결정 출처와 범위 변화

각 Phase와 Build 선택에 [공통 출처·변경 규칙](../SKILL.md#사용자-의도와-에이전트-제안)을 적용한다. 사용자 경험을 바꾸지 않는 구현 세부는 구현 위임으로 남긴다.

## Closure audit

모든 활성 Build가 `합의 완료`가 된 뒤 다음을 다시 검사한다.

- 모든 Idea 문장이 Phase와 Build에 연결된다.
- 실제 사용한 Research가 확정 `R###` 파일과 연결되고 Verdict의 영향이 해당 Phase·Build에 반영되었다.
- 필요한 탐색의 완료와 남은 실험을 구분했다. 사용자가 생략·연기한 탐색은 그 결정과 영향을 기록했고, 수행된 것으로 계산하지 않았다.
- 모든 활성 Phase와 Build, 폐기 이력과 각 경계를 검사했다.
- 모든 활성 Build의 네 차원이 `확정`이다.
- 사용자 경험을 바꾸는 미확인과 충돌이 없다.
- 에이전트 제안과 사용자 결정이 구분된다.
- 구현자가 제품 행동을 대신 정할 항목이 없다.
- 모든 활성 Build의 산출물·사용자 행동·관찰 결과·Approve가 연결된다.
- 모든 Phase와 Build 번호가 고유하며 폐기 번호를 포함해 재사용되지 않았다.
- Feature가 독립 계층으로 남아 있지 않다.

공백이 발견되면 해당 Build의 합의 상태를 `미확인`으로 바꾸고 Build별 합의 루프로 돌아간다.

## 최종 restate gate

Closure가 통과하면 다음을 한 번에 보여 준다.

- Idea의 한 문장 목표
- 모든 Phase의 목적과 각 Phase에 속한 Build의 전역 번호·선행 관계
- 각 Build에서 사용자가 직접 확인할 행동
- 각 Build의 Approve
- 사용자 요청에서 추가·삭제·단순화된 내용

그 뒤 묻는다.

```text
이 계획만 읽은 구현자와 사용자가 같은 완성 상태를 이해할 수 있습니까?

확정 | Phase 수정 | Build 수정 | 빠진 범위 | 전체 재검토
```

수정이 생기면 Idea 커버리지, Phase 경계, Build별 합의와 closure audit를 다시 수행한다.

## 종료 차단 조건

- Idea 커버리지, 모든 Phase 경계, 개별 Build, 모든 Build 경계와 전체 순서를 검사하지 않았다.
- Idea 문장에 연결되지 않은 활성 Build 또는 활성 Build에 연결되지 않은 Idea 문장이 있다.
- Phase에 속하지 않거나 둘 이상의 Phase에 속한 활성 Build가 있다.
- 활성 Build가 없는 Phase가 있다.
- 모든 활성 Build의 전체 필드가 작성되지 않았다.
- 합의 상태가 `미확인`인 활성 Build가 있다.
- 네 차원 중 `충돌 | 미확인 | 부분확정`인 활성 Build가 있다.
- 사용자 산출물이나 확인 행동이 없는 활성 Build가 있다.
- 활성 Build의 AI 완료와 사용자 Approve가 분리되지 않았다.
- 에이전트 제안이 사용자 결정으로 오인되어 있다.
- 사용자 경험을 바꾸는 구현 결정이 위임되어 있다.
- Research 참조가 단일 legacy `research.md`, 존재하지 않는 파일 또는 처리되지 않은 `결론 보류` 질문을 가리킨다.
- Phase나 Build 번호가 중복·재사용되었거나 Feature가 독립 계층으로 남아 있다.
- 최종 restate gate가 통과하지 않았다.

## 문서 구조

```markdown
# Execution: {제목}

- 상태: 확정

## 한 문장 목표

#### Build #1 ... Build #N
- 합의 상태: 합의 완료
- 목적
- Idea 연결
- 선행 조건
- 범위
- 제외
- 산출물
- AI 완료
```

사용자가 최종 확정하면 상태를 `확정`으로 바꾸고 전체 Phase, 활성 Build와 각 Approve를 요약한다. `SKILL.md`의 지속 상태 계약에 따라 응답 첫 줄을 `[Elenchus · 완료]`로 바꾸고 이 응답으로 현재 Elenchus 세션을 끝낸다. 완료 응답에서는 구현을 시작하지 않으며 이후 요청은 같은 Codex 작업에서도 상태 표식 없이 일반 모드로 처리한다.

완료 뒤 Build 수정·재검토·범위 변경을 요청하더라도 자동으로 재진입하지 않는다. 현재 사용자 메시지에 `$elenchus` 또는 `skill:elenchus` 호출 토큰이 있을 때만 응답 첫 줄을 `[Elenchus · 진행 중]`으로 바꾸고 영향받는 Build의 합의 상태와 전체 커버리지를 다시 연다.
