# Lab — 실전적 재료 확보

## 역할

합의한 연구 질문에 답하도록 실제 기능을 구현·연결하고 반복 실행한다. 현재 환경과 라이브러리·외부 도구의 제약, 기대 입출력과 실제 결과의 차이, 실패 원인과 대안을 찾아 재사용할 코드·데이터·테스트를 남긴다.

제품 성립에 필요한 시행착오를 수행한다. 코드·실험 계획만 작성하고 실제 실행했다고 보고하지 않는다. 실제 불가 조건을 확인하는 것도 연구 결과이며 작동 기능 확보와는 판정을 나눈다.

## 작업장과 원본 보호

- 기본 작업장은 `.elenchus/lab/R###/`다. 기존 제품 코드·설정·원본 데이터는 읽기 전용으로 두고, 필요한 연결은 독립 코드나 격리된 프로젝트 사본에서 검증한다.
- 메인은 역할별 작업 경로와 파일 소유권을 정한다. agent에게 구현·테스트를 맡길 수 있으나 다른 작업자의 파일을 동시에 수정하지 않는다. 공동 재료는 통합 담당자가 확인해 반영한다.
- 별도 가상환경·의존성과 도구가 지원하는 캐시·임시 경로를 사용한다. 모든 출력을 억지로 한 폴더에 가두는 대신 실제 출력·import 부수 효과·원본 변경 가능성을 사전에 확인한다. 예상 밖 쓰기를 피할 수 없으면 복제본이나 다른 도구를 쓴다.
- 변경 전후 원본의 관련 파일·데이터 해시 또는 diff를 확인한다. 사후 불변 검사만으로 기술적 격리를 보장했다고 하지 않는다.
- 합의한 범위의 로컬 의존성 설치·복제본 수정·테스트는 진행할 수 있다. 새 계정·접근·유료 호출·외부 상태 변경·민감 데이터 사용은 기존 승인 범위를 확인하고 필요한 확대만 합의한다. 비밀키를 재료 묶음에 넣지 않는다.
- 생성한 재료·실패 기록은 종료 때 자동 삭제하지 않는다. 불필요한 거대 캐시·환경 자체를 재료로 포장하지 말고 재구성 방법을 제공한다.

## 실행 준비

각 실험에서 시험할 질문, 기대 입출력, 사용할 데이터/환경, 채택·실패·보류 조건과 비교 방법을 R 또는 재료의 짧은 실행 안내에 적는다. 자료로 확인해야 할 수치는 임의의 성공 기준으로 고정하지 않는다. 예상 시간·비용·중단/복구 조건은 실제 실행 위험에 맞춘다.

관련 기존 코드·데이터를 읽고 라이브러리·OS·버전·외부 계약의 차이를 확인한다. 외부 도구 호출 전에 실제 필요한 인자·입력과 사용 조건을 확인하며, 제한이 예상된다는 이유만으로 동작 불가를 단정하지 않는다.

## 시행착오 루프

1. 현재 질문에 답할 기능·테스트를 만든다. 필요하면 수집→저장→처리→조회처럼 기술 경로를 연결한다.
2. 실제 입력으로 실행하고 출력·오류·부분 성공·재실행 동작을 관찰한다. 기준선과 비교할 수 있도록 환경·버전·입력 출처를 기록한다.
3. 실패나 기대 차이를 재현하고 원인 가설을 세운다. 라이브러리·환경 제약이 원인이면 [Discovery](discovery.md)로 사례·대체 방법을 다시 조사한다.
4. 의미 있는 가설·수정·대안이 있고 합의 범위 안이면 계속 시도한다. 같은 명령의 반복을 연구 진전으로 계산하지 않는다.
5. 확인된 실패 조건과 수정 후 동작을 테스트로 남긴다. 외부 의존이 변할 때는 확보한 응답을 조건·날짜와 함께 fixture로 보존해 오프라인 재현도 가능하게 한다.
6. 달성 조건별로 실제 통과·실패·미검증을 판정하고 R과 Topology의 다음 질문을 갱신한다.

실제 관찰한 실패와 테스트를 위해 주입한 실패를 구분한다. 모의 API·가짜 데이터의 테스트 통과를 실제 서비스 연결 성공으로 바꾸지 않는다. 반대로 외부 서비스의 일시적 실패를 기능 자체의 불가능성으로 일반화하지 않는다.

## 인터페이스와 재료의 수준

CLI·스크립트·테스트·진단 화면·시각 데모를 목적에 맞게 자유롭게 쓴다. 기능 연결이나 화면이 있다는 이유로 제품화라고 보지 않는다. 판단 대상은 연구 질문과 기능의 동작이며, 최종 제품의 화면 구성·전체 동선·중심 개념을 후속 제작자의 요구사항으로 고정하지 않는다.

기능 검증에 필요한 만큼 견고하게 구현한다. 이후 제작자는 재료를 재사용·감싸기·수정·교체할 수 있다. 보존해야 할 사용자 요구·데이터 의미·외부 계약과, 임시 함수명·폴더·스키마·UI 선택을 구분한다. 테스트도 의미 있는 동작을 보장해야 하며 임시 구조까지 불변 계약으로 만들지 않는다.

## 전달할 재료

질문에 필요한 항목만 준비한다.

- 실행 가능한 코드와 주요 진입점, 의존성·버전·설치/실행 명령.
- 실제 데이터의 필요한 사본·대표 샘플·스키마·각 필드의 의미와 출처·사용 조건.
- 테스트·fixture, 대표 입력/출력, 검증한 정상·실패·재실행 조건.
- 시행착오: 실제 장애·시도한 수정/대안·해결 여부, 아직 검증하지 못한 범위.
- 재료를 다시 실행하는 방법과 외부 연결 없이 확인할 수 있는 부분.
- 재사용 조건·임시 설계와, 이후 제작자가 별도로 판단할 제품화 사항.

대화 이력 없이 안내와 실제 전달할 묶음만으로 대표 경로를 실행할 수 있는지 확인한다. 가능하면 다른 agent가 새 위치에 펼친 작업장에서 재현한다. 같은 작업장에 남은 우연한 캐시·전역 의존성·절대 경로에만 기대지 않는다. 비교할 때 기능 결과·파일 내용의 불변 조건과 복사 후 달라질 수 있는 파일 시각 등 환경별 진단값을 구분한다. 진단값은 숨기지 않으며, 그 값이 연구의 실제 입력 의미라면 필요한 보존 조건을 명시한다. 실험 데이터가 없으면 재현할 수 없는 경우 필요한 데이터를 명시하고 실행 성공을 주장하지 않는다.

R의 결론은 Lab 디렉터리 없이도 이해할 수 있게 쓰되, 재현에는 어떤 재료가 필요한지 연결한다. 코드와 원본 로그를 보고서에 복사하지 않는다. 유용한 재료는 현재 연구나 명시적으로 관련된 후속 질문에서 재사용하며, 관계없는 과거 Lab을 자동으로 모두 읽지 않는다.

## 선택적 handoff

요청되면 Topology의 목적·확정 제약, 관련 코드·데이터·테스트·실행 방법, 실패·미검증과 열린 선택을 전달용으로 정리한다. 기준 커밋 또는 파일 해시와 미커밋 변경 범위를 적는다. 필요한 자료만 포함하고 인증정보·불필요한 개인 데이터를 제외한다.

재료의 임시 구조를 최종 제품 설계로 보존할 의무는 없다. Pro 또는 다른 제작자가 종합 사용자 경험과 제품 구조를 재구성할 수 있음을 명시한다. 전달 묶음 생성이 외부 전송 승인은 아니며 실제 업로드·공유는 사용자 요청 범위에서만 수행한다.
