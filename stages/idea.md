# Idea 단계

## 정체성

`idea.md`는 문제와 해결 방향을 실제 사용자 경험 계약으로 변환한다. 별도 `contract.md`를 만들지 않는다.

Idea가 확정되면 구현자는 사용자에게 보이는 행동·출력·실패·비용·권한·데이터 처리와 성공 기준을 새로 정하지 않아야 한다.

## 시작 문서

`./.elenchus/idea.md`가 없으면 topology 확인 전 다음 내용만 만든다.

```markdown
# Idea: {주제}

- 상태: 작성 중
- 시작 요청: {사용자의 요청}

## Topology
## 명료도
## 확인된 사실
## 사용자 결정
## 에이전트 제안
## 구현 위임
## 제외
## 미확인·충돌
```

## Topology gate

첫 질문 전에 현재 요청과 repo에서 다음 목록을 제안한다.

```text
산출물
사용 표면
외부 연동
제약
```

각 항목에 `활성 | 보류`를 표시하고 근거가 된 사용자 문장 또는 repo 경로를 붙인다. 사용자가 `맞음 | 추가·삭제 | 병합·분리 | 보류`를 선택하기 전에는 세부 인터뷰를 시작하지 않는다.

## 공격 표면

모든 활성 구성요소를 다음 영역에서 검사한다.

```text
문제와 관찰:
실제로 겪은 사건, 반복 빈도, 현재 해결 방법, 손실

사람과 책임:
시작하는 사람, 결과를 쓰는 사람, 비용을 내는 사람,
오류를 확인하는 사람, 최종 결정을 내리는 사람

원하는 변화:
사용자가 새로 할 수 있어야 하는 행동과 관찰할 결과

시작 조건과 입력:
언제 시작하며 어떤 형식·크기·출처의 입력을 받는가

정상 흐름:
사용자 행동, 시스템 반응, 다음 행동, 종료 시점

부분 성공과 빈 결과:
일부 입력만 처리됨, 일부 결과만 생성됨, 결과 없음, 지연

실패와 복구:
실패 표시, 원인, 재시도, 수정, 취소, 이전 상태 보존

출력:
형태, 포함 정보, 근거, 저장·복사·공유, 결과 소유자

오류 비용:
잘못된 결과, 누락, 중복, 지연이 만드는 손실

권한과 데이터:
수집, 접근, 저장, 공유, 삭제, 보관 기간, 공개 범위

교환 관계:
정확도·속도·비용, 자동화·사용자 확인, 편의·개인정보

지원 범위:
지원하는 사용자·환경·입력과 지원하지 않는 경우

대안과 단순화:
현재 구조 유지, 작은 버전, 연기, 미정의, 계층 제거, 만들지 않기

성공 기준:
사용자가 직접 실행할 행동과 성공·실패를 구분할 관찰
```

각 항목을 `확인된 사실 | 사용자 결정 | 에이전트 제안 | 구현 위임 | 제외 | 미확인 | 충돌`로 분류한다.

## 명료도 갱신

각 활성 구성요소의 목표·제약·성공 기준·맥락을 평가한다.

- 사용자 행동과 결과가 한 문장으로 이어지지 않으면 목표는 `미확인` 또는 `부분확정`이다.
- 범위·비용·권한·데이터·제외에 사용자 선택이 남으면 제약은 닫지 않는다.
- 사용자가 성공과 실패를 실행·관찰로 구분하지 못하면 성공 기준은 닫지 않는다.
- Brownfield repo와 새 흐름의 연결이 확인되지 않으면 맥락은 닫지 않는다.
- 모순, 회피성 답변, 범위 확장이나 새 구성요소는 해당 등급을 내린다.

## 질문 규칙

- 기능 목록보다 전제, 대안과 사용자가 겪을 결과 차이를 묻는다.
- 선택 전에 비개발자가 판단할 수 있는 결정 설명을 제공한다.
- 에이전트가 기능을 제안하면 원래 요청과의 차이와 유지·축소·연기·제거·만들지 않기를 함께 보여 준다.
- 구현자가 정할 수 있는 내부 구조는 질문하지 않는다.

## 종료 차단 조건

다음 중 하나가 남아 있으면 closure audit를 통과시키지 않는다.

- Topology에 사용자 확인이 없다.
- 활성 구성요소 중 네 차원이 모두 확정되지 않은 항목이 있다.
- 공격 표면에 분류되지 않은 영역이 있다.
- 사용자 경험을 바꾸는 미확인이나 충돌이 있다.
- 부분 성공·빈 결과·실패·복구 중 적용되는 경우가 분류되지 않았다.
- 비용·권한·데이터·교환 관계에서 사용자 결정이 남아 있다.
- 지원 범위와 제외 범위를 구분할 수 없다.
- 성공과 실패를 사용자 행동으로 구분할 수 없다.
- 에이전트 제안이 사용자 결정으로 오인되어 있다.
- 구현자가 사용자 대신 제품 행동을 정해야 한다.

## Topology coverage audit와 restate

Closure audit 전에 topology coverage audit를 따로 수행한다.

- 모든 활성 구성요소가 공격 표면의 적용 항목에 연결되는가
- 보류한 구성요소가 확정 범위에 섞이지 않았는가
- 새 답으로 생긴 산출물·사용 표면·외부 연동·제약이 topology에 추가됐는가
- 병합·분리한 구성요소의 책임과 성공 기준이 겹치거나 빠지지 않았는가

Topology coverage audit와 closure audit가 모두 통과하면 모든 활성 구성요소를 포함하는 한 문장 목표를 보여 주고 `확정 | 문구 수정 | 빠진 범위`를 받는다. 수정이 생기면 topology와 네 차원을 다시 평가한다.

## 문서 구조

```markdown
# Idea: {제목}

- 상태: 확정

## 한 문장 목표
## Topology
## 구성요소별 명료도
## 관찰한 문제와 현재 행동
## 사용자·책임·사용 상황
## 시작 조건과 입력
## 정상 사용자 흐름
## 부분 성공과 빈 결과
## 실패·복구·취소
## 출력과 근거
## 오류 비용
## 권한·데이터·보관·공유
## 교환 관계와 사용자 선택
## 지원 범위와 제외
## 성공 판정 행동
## 확인된 사실
## 사용자 결정
## 에이전트 제안과 승인 여부
## 구현 위임
## 대체된 결정
## 보류
```
