# Research 단계

## 정체성

Research는 Idea와 Execution을 바꿀 수 있는 불확실성을 저장소 사실, 외부 근거와 조건부 Lab 관찰로 줄이고 Verdict를 만든다. 자료 수집 자체나 제품 구현이 목적이 아니다.

`idea.md`는 프로젝트 전체의 의도 계약이고 Research는 독립된 조사 질문별 파일로 분리한다. 실험이 필요해도 제품 코드·설정·manifest·lockfile은 변경하지 않는다.

## 진입과 생략

Idea closure 뒤 다음 중 하나가 있으면 Research를 제안한다.

- 외부 서비스·API·가격·법·지원 상태가 실행 계획을 바꿀 수 있음
- procedure·방법론·라이브러리 선택이 비용·성능·UX나 Build 순서를 바꿀 수 있음
- 선행 사례나 반대 사례가 방향 선택을 바꿀 수 있음
- 실제 저장소 구조나 현재 동작이 문서상 전제와 다를 수 있음
- 데이터·하드웨어·성능·API 응답을 관찰해야 결론을 낼 수 있음
- Idea의 전제가 출처 없는 추정에 의존함

질문 본문에서 조사할 불확실성, 영향을 받는 Idea 문장·Phase·Build, 생략할 때 남는 위험을 설명하고 사용자가 `Research 진행 | 생략`을 선택하게 한다. `web | mixed | data` 모드는 묻지 않는다.

Research를 생략해도 미확인 사실을 해결된 것으로 바꾸지 않는다.

- 사용자 경험·비용·지원 범위·실패 동작·Build 순서를 바꿀 수 있으면 관련 범위를 제외·연기하거나 검증 Build를 추가해야 Execution closure가 가능하다.
- 사용자 결과와 무관한 기술 세부만 근거와 위험을 기록하고 구현 위임으로 넘길 수 있다.
- 생략한 질문, 위험과 처리 방법을 `idea.md`의 보류 또는 `execution.md`의 제외·검증 Build·구현 위임에 남긴다.

## 파일과 ID

프로젝트 루트에서 다음 구조를 사용한다.

```text
./.elenchus/
├─ idea.md
├─ research/
│  ├─ index.md
│  ├─ R001-neutral-topic.md
│  └─ R002-neutral-topic.md
├─ lab/
│  ├─ R001/
│  └─ R002/
└─ execution.md
```

Research 하나는 독립적인 결정 질문 하나를 다룬다.

- ID는 `R`과 세 자리 숫자를 사용한다. 새 ID는 index와 파일명에서 찾은 가장 큰 번호의 다음 번호이며 삭제한 번호를 재사용하지 않는다.
- 파일명은 `R###-neutral-topic.md` 형식이다. slug는 특정 라이브러리나 선호 후보가 아니라 중립 질문을 짧게 나타낸다.
- `research/index.md`에는 `ID | 중립 질문 | 상태 | 영향 | 파일`만 둔다. 후보 기술, 권장안과 상세 Verdict는 적지 않는다.
- 파일 상태는 `작성 중 | 확정 | 중단됨`을 사용한다. `결론 가능 | 결론 보류`는 Verdict 판정으로만 사용한다.
- 영향은 `Phase 후보 | Phase #N | Build #N` 또는 그 조합을 기록한다. Execution이 확정되면 실제 Phase·Build 연결로 갱신한다.

### 기존 `research.md` 이전

기존 `./.elenchus/research.md`는 단순히 프로젝트를 열거나 읽을 때 변경하지 않는다. 새 Research를 시작해 문서를 수정할 때 다음을 수행한다.

1. `./.elenchus/research/`를 만들고 기존 내용을 보존한 채 Research 파일로 이동한다.
2. research 디렉터리가 없으면 `R001-legacy.md`를 사용한다.
3. research 디렉터리나 index가 이미 있으면 가장 큰 기존 ID 다음 번호를 사용하며 파일을 덮어쓰지 않는다.
4. `research/index.md`에 중립 질문, 기존 상태, 영향과 새 경로를 기록한다. 기존 문서에서 중립 질문을 알 수 없으면 `기존 Research`라고 적고 내용을 추정하지 않는다.
5. `execution.md`와 다른 `.elenchus` 문서의 기존 `research.md` 참조를 새 파일 경로로 갱신한다.
6. 이전 완료 뒤 새 Research에는 다음 ID를 부여한다.

## Repository 기준선

Idea의 확정 내용을 intake로 사용하고 기술 후보를 탐색하기 전에 현재 질문과 관련된 저장소 사실을 읽기 전용으로 확인한다.

- 관련 파일·심볼·설정·테스트와 현재 동작을 확인한다.
- 관찰한 사실과 해석을 분리해 Research 파일에 기록한다.
- neutral brief의 입력·출력·사용자 경험·제약을 바꿀 수 있는 사실을 우선한다.
- Repository가 없거나 현재 질문과 무관하면 확인을 생략하고 이유를 기록한다.
- 제품 파일을 수정하거나 Lab 실험을 수행하지 않는다.

## Neutral brief

Repository 기준선을 기록한 뒤 Idea의 확정 내용과 객관적인 저장소·환경 사실을 다음 구조로 줄인다.

```text
중립 질문
입력
출력
사용자 경험
성공 조건
실패 조건
확정 제약
객관적인 저장소·환경 사실
미해결 질문
```

사용자가 언급한 procedure·API·라이브러리·서비스는 `필수 제약 | 현재 환경 | 후보 | 예시`로 분류한다.

- 필수 제약과 현재 환경만 neutral brief의 조건으로 사용한다.
- 후보와 예시는 확정 방향처럼 쓰지 않고 후보 비교 전제에서도 제거한다.
- 분류가 불명확하고 결과를 바꿀 수 있으면 사용자에게 확인한다.
- Repository 기준선이나 사용자 답으로 입력·출력·사용자 경험·성공·실패 조건·제약이 바뀌면 neutral brief를 즉시 갱신한다.

## 독립 solution explorer

메인 Elenchus 세션은 Repository 기준선과 neutral brief가 일치하는지 다시 확인한 뒤, 다음 중 하나가 성립하면 독립 solution explorer subagent가 결론의 신뢰도를 높일지 판단하고 사용자에게 먼저 제안한다.

- procedure·아키텍처·API·라이브러리 선택이 Execution을 크게 바꿀 수 있음
- 가능한 접근법이 여러 개이고 현재 대화가 한 후보에 치우쳐 있음
- 사용자가 특정 기술을 언급했지만 필수 제약인지 확정되지 않음
- 외부 생태계와 실제 사용 사례를 폭넓게 비교해야 함
- 이전 대화 맥락을 제거한 독립 탐색이 앵커링을 줄일 수 있음

저장소 사실 하나, 이미 선택한 후보의 국소 검증, 사용자 결과를 바꾸지 않는 작은 구현 세부처럼 독립 컨텍스트의 이점이 없으면 제안하지 않는다.

제안에는 다음을 한 번에 보여 준다.

```text
독립 Research 제안

필요한 이유
Subagent에 전달할 neutral brief
전달하지 않을 후보·가정
받을 결과

Subagent 호출 | 현재 세션에서 조사 | Brief 수정
```

- 사용자가 `Subagent 호출`을 선택한 경우에만 새 agent를 만든다.
- `현재 세션에서 조사`를 선택하면 같은 Research에서 동일한 제안을 반복하지 않는다.
- `Brief 수정`을 선택하면 사용자가 수정한 내용을 다시 보여 주고 승인받기 전에는 호출하지 않는다.
- Subagent 승인 뒤 Repository 사실이나 입력·출력·사용자 경험·성공·실패 조건·제약이 달라지면 기존 승인을 확대하지 않는다. 수정한 brief를 다시 보여 주고 재승인받은 뒤 호출한다.

### 호출 계약

- 새 subagent는 대화 이력 상속을 끈 `fork_turns="none"`으로 만들고 승인된 neutral brief만 제공한다. 이 격리를 지원할 수 없으면 호출하지 않고 현재 세션 조사로 대체한다.
- neutral brief에는 입력·출력·사용자 경험·성공·실패 조건·확정 제약·객관적인 저장소와 환경 사실·미해결 질문만 넣는다.
- subagent는 저장소를 읽기 전용으로 조사하고 외부 근거를 사용해 solution space를 넓힌다. 파일을 만들거나 변경하지 않고 Lab을 실행하지 않는다.
- subagent가 다른 agent를 만들거나 작업을 재위임하지 못하게 요청한다.
- 사용자의 후보를 지지하거나 공격하는 critic·hater 역할을 주지 않는다.
- Research 파일 하나당 기본 subagent는 하나다. 추가 호출이 필요하면 이유와 새 brief를 제시하고 별도 사용자 승인을 받는다.
- 호출이 실패하거나 결과가 부족하면 메인 세션이 보완하며 자동 재시도하거나 두 번째 agent를 호출하지 않는다.

Subagent 요청은 다음 결과를 요구한다.

```text
문제의 중립적 재정의
탐색한 solution space
유력한 procedure와 구현 전략
API·라이브러리·서비스 후보 비교
권장 방향과 근거
제약과 trade-off
제외한 방향과 이유
Lab에서 검증할 주장
남은 불확실성
출처
```

### 결과 정제

메인 세션은 subagent 원문이나 장황한 후보 목록을 파일로 보존하지 않는다. 다음 의미만 Research 파일에 다시 작성한다.

- 승인된 neutral brief
- 비교한 접근법의 범주
- 실제 판정에 남은 후보명과 핵심 차이
- 채택·제외 근거
- 권장 방향과 신뢰도
- Lab 검증이 필요한 주장
- 실제 판단에 사용한 출처
- 사용자 결정

Subagent 결과는 Verdict가 아니라 증거 입력이다. 메인 세션이 Idea와 저장소 사실에 대조하고 사용자 결과를 바꾸는 선택은 사용자에게 확인한다.

## 증거 계획

사용자에게 조사 모드를 선택하게 하지 않고 다음 증거원을 각각 `필요 | 생략`으로 판정한다.

```markdown
| 증거원 | 상태 | 이유 | 바뀔 수 있는 결정 |
|---|---|---|---|
| Repository | 필요 |  |  |
| Independent exploration | 필요 |  |  |
| External evidence | 필요 |  |  |
| Lab | 생략 |  |  |
```

- Repository가 없거나 현재 질문과 무관하면 생략할 수 있다.
- solution space가 좁고 현재 대화의 앵커링 위험이 없으면 Independent exploration을 생략할 수 있다. Subagent를 제안했지만 사용자가 현재 세션 조사를 선택하면 `생략`과 사용자 결정을 기록하고 메인 세션의 폭넓은 탐색을 External evidence에서 수행한다.
- 외부 사실이나 solution space가 결론을 바꾸지 않으면 External evidence를 생략할 수 있다.
- 실제 관찰이 Verdict나 Execution을 바꿀 수 있을 때만 Lab을 사용한다.
- 증거원을 생략한 이유가 없으면 Research closure를 통과하지 않는다.

## 증거 루프

1. 현재 질문과 관련된 Repository 기준선을 읽기 전용으로 확인한다.
2. 기준선과 Idea intake로 neutral brief를 확정한다.
3. 시험할 주장과 반증 조건을 적는다.
4. 독립 탐색 필요성을 판단하고 필요하면 사용자에게 subagent를 제안한다.
5. 승인된 독립 탐색과 External evidence를 수집한다.
6. Lab이 필요한 주장을 분리하고 예상 방향과 채택·폐기 기준을 먼저 적는다.
7. 결과, 반대 근거와 적용 한계를 갱신한다.
8. 결과가 Idea와 충돌하면 사용자에게 변경 선택을 받는다.
9. 다음 근거가 Verdict를 바꿀 수 있는지 다시 판단한다.

### External evidence

- 기술 사실은 공식 문서와 원문 연구를 우선한다.
- 가격, 지원 범위와 유지 상태에는 확인 날짜를 붙인다.
- 현재 주장과 반대되는 자료를 찾는다.
- 자료의 사용자·언어·데이터·하드웨어·기간이 현재 상황과 같은지 비교한다.
- 실제 판정에 사용한 후보명과 출처 링크는 남긴다.
- subagent가 제시한 결정적 사실과 출처는 메인 세션이 직접 확인하고 적용 범위를 다시 판단한다.

## Lab

Lab은 문서와 저장소 분석만으로 판정할 수 없고 실제 관찰이 Verdict나 Execution을 바꿀 때만 메인 Elenchus 세션이 사용한다.

### 격리 경계

- 모든 실험 코드·fixture·mock·응답·로그·출력·캐시·임시 파일·가상환경과 의존성은 `./.elenchus/lab/R###/` 안에만 만든다.
- 제품 코드·설정·manifest·lockfile과 Lab 밖의 프로젝트 파일은 읽기 전용이다.
- 제품 코드를 직접 수정하지 않고 읽기 전용으로 import하거나 필요한 최소 부분을 Lab으로 복제한다.
- 도구가 Lab 밖에 캐시·bytecode·출력을 만들 수 있으면 출력 위치를 Lab으로 재지정하거나 생성을 끈다. 격리를 보장할 수 없으면 실행하지 않고 이유와 필요한 사용자 결정을 기록한다.
- 인증정보와 원본 개인정보를 Lab에 저장하지 않는다. 필요한 실제 데이터는 최소화·비식별화하고 권한 범위를 넘지 않는다.

### 실행 전 계약

각 실험 전에 다음을 Research 파일에 적는다.

```text
시험할 주장
실행이 필요한 이유
예상 방향
채택 기준
폐기·실패 기준
범위와 예상 비용·시간
```

다음 조건을 모두 만족하는 작은 실험은 별도 승인 없이 실행할 수 있다.

- Lab 밖을 변경하지 않음
- 외부 서비스의 상태를 변경하지 않음
- 유료 호출, 새 계정·권한과 민감정보 저장이 없음
- 실행 범위와 시간이 작고 중단해도 제품과 사용자 데이터에 영향이 없음

유료 호출, 외부 생성·수정·삭제, 새 인증·권한, 민감한 실제 데이터, 장시간·대규모 실행 또는 격리 불가능성이 있으면 실행 직전에 사용자 확인을 받는다.

### 보존과 의미

- Research가 확정·중단·취소되어도 Lab을 자동 삭제하지 않는다. 사용자가 언제든 삭제할 수 있는 폐기 가능한 작업장으로 간주한다.
- 이후 Research는 기존 Lab을 자동으로 읽거나 재사용하지 않는다. 사용자가 명시적으로 요청하거나 현재 검증에 반드시 필요한 경우에만 확인한다.
- Lab 코드·원본 응답·전체 로그·상세 실행 명령과 우연히 사용한 구현 구조를 Research 파일에 복사하지 않는다.
- Research 파일에는 시험한 주장, 관찰, 조건·한계, 판정과 Idea·Execution에 미친 영향만 남긴다.
- Verdict는 Lab 디렉터리가 없어도 이해되고 적용될 수 있어야 한다. Lab 코드를 제품 구현의 출발점으로 지정하지 않는다.

실행 상태는 다음을 사용한다.

```text
기준선
채택
폐기
실패
검증 실패
제외
```

측정값이 좋아져도 검증 실패, 범위 밖 변경이나 측정 편법이 있으면 채택하지 않는다.

## 내부 검토 관점

- researcher: 출처, 반대 자료와 적용 범위를 확인한다.
- contrarian: 반대 결과가 사실일 때 Verdict가 바뀌는지 본다.
- simplifier: 추가 조사 없이 결론 가능한지, 조사 범위를 줄일 수 있는지 본다.
- architect: 근거가 Idea나 Execution의 구성요소·책임·연동을 바꾸는지 본다.

contrarian은 메인 세션의 내부 관점이며 별도 critic 역할이나 독립 산출물로 만들지 않는다.

## Verdict

```text
판정: 결론 가능 | 결론 보류
근거
반대 근거
후보와 핵심 차이
채택·제외 근거
한계
신뢰도: 높음 | 중간 | 낮음
Idea에서 바꿀 내용
Execution에서 바꿀 Phase·Build
```

- 근거가 부족하면 결론을 강제하지 않고 `결론 보류`로 둔다.
- 반대 근거와 제외한 실행을 숨기지 않는다.
- 결론 보류가 사용자 결과나 Execution을 바꾸면 Research를 계속하거나 범위를 제외·연기하거나 검증 Build를 만든다.
- 사용자 결과와 무관한 기술 세부만 사용자 동의 후 구현 위임으로 보낼 수 있다.

## 종료 차단 조건

- neutral brief의 입력·출력·사용자 경험·성공·실패 조건·제약 중 필요한 항목이 비어 있다.
- 사용자가 언급한 기술을 제약·환경·후보·예시로 분류하지 않았다.
- 증거원별 필요·생략과 이유가 없다.
- subagent 필요성을 판단하지 않았거나 제안에 대한 사용자 결정이 없다.
- 승인된 subagent 결과를 메인 세션이 검증·정제하지 않았거나 한 Research에서 추가 승인 없이 둘 이상 호출했다.
- 시험할 주장과 반증 조건이 연결되지 않는다.
- 사용한 사실에 출처나 확인 날짜가 없다.
- 반대 자료를 찾지 않았고 검색 범위도 적지 않았다.
- 실행한 Lab의 기준선·측정 방향·판정 기준이나 격리 확인이 없다.
- Idea와 충돌한 근거에 대한 사용자 결정이 없다.
- Verdict에 근거·반대 근거·한계·신뢰도 중 하나가 없다.
- 결론 보류가 사용자 결과나 Execution을 바꾸는데 제외·연기·검증 Build 중 다음 행동이 없다.
- index의 상태·영향·파일이 실제 Research 파일과 일치하지 않는다.
