# Research 단계

## 정체성

Research는 필요한 해법을 발견·비교하고 그 적용 가능성을 검증해 Idea와 Execution의 선택 근거를 만든다. 조사 목적은 `탐색·벤치마킹`과 `검증·실험`으로 구분한다. Web·Repository·Browser·Lab은 증거 수단이며 모든 조사에서 모두 사용할 필요는 없다. 자료 수집량이나 제품 구현이 성과를 대신하지 않는다.

`idea.md`는 프로젝트 전체의 의도 계약이고 Research는 독립된 조사 질문별 파일로 분리한다. 실험이 필요해도 제품 코드·설정·manifest·lockfile은 변경하지 않는다.

## 진입과 생략

다음 중 하나가 있으면 필요한 Research를 판단한다. 사례를 봐야 선택할 수 있는 질문은 Idea closure 전에 조사한다.

- 외부 서비스·API·가격·법·지원 상태가 실행 계획을 바꿀 수 있음
- procedure·방법론·라이브러리 선택이 비용·성능·UX나 Build 순서를 바꿀 수 있음
- 사용자가 레퍼런스·벤치마킹을 요청했거나 선행 사례·인접 분야·반대 사례가 방향 선택을 바꿀 수 있음
- 실제 사례 없이 시각·상호작용을 결정하거나, 잘못 선택하면 여러 후속 작업을 다시 해야 하는 전제가 있음
- 실제 저장소 구조나 현재 동작이 문서상 전제와 다를 수 있음
- 데이터·하드웨어·성능·API 응답을 관찰해야 결론을 낼 수 있음
- Idea의 전제가 출처 없는 추정에 의존함

명시적으로 요청하거나 이미 합의한 조사는 목적·범위를 알리고 진행한다. 새로운 조사 범위는 불확실성, 영향을 받는 선택과 생략 위험을 설명해 `Research 진행 | 생략`을 선택받는다. 이미 결정한 범위와 내부 역할 분담을 반복 승인받지 않는다. 사용자에게 `web | mixed | data`나 새 조사 모드를 선택하게 하지 않는다.

접근법·사례 발견이 필요하면 [탐색·벤치마킹](discovery.md)을 읽고 그 수행·완료 기준을 적용한다. 단일 사실 확인에는 이를 로딩하지 않는다. 하나의 질문에서 탐색과 검증이 모두 필요하면 목적별 산출물과 판정 범위를 나눈다. 웹 탐색만으로도 독립적인 결론을 낼 수 있으며 Lab 실행 여부로 연구 가치를 판정하지 않는다.

Research를 생략해도 미확인 사실을 해결된 것으로 바꾸지 않는다.

- 사용자 경험·비용·지원 범위·실패 동작·Build 순서를 바꿀 수 있으면 관련 범위를 제외·연기하거나 검증 Build를 추가해야 Execution closure가 가능하다.
- 사용자 결과와 무관한 기술 세부만 근거와 위험을 기록하고 구현 위임으로 넘길 수 있다.
- 생략한 질문, 위험과 처리 방법을 `idea.md`의 보류 또는 `execution.md`의 제외·검증 Build·구현 위임에 남긴다.
- 생략·연기 합의나 검증 Build 등록을 탐색 수행 완료로 바꾸지 않는다. 요청된 탐색의 범위를 줄일 때는 사용자 결정을 기록한다.

## 파일과 ID

프로젝트 루트에서 다음 구조를 사용한다.

```text
./.elenchus/
├─ idea.md
├─ research/
│  ├─ index.md
│  ├─ R001-neutral-topic.md
│  └─ R002-neutral-topic.md
├─ lab/
│  ├─ R001/
│  └─ R002/
└─ execution.md
```

Research 하나는 독립적인 결정 질문 하나를 다룬다.

- ID는 `R`과 세 자리 숫자를 사용한다. 새 ID는 index와 파일명에서 찾은 가장 큰 번호의 다음 번호이며 삭제한 번호를 재사용하지 않는다.
- 파일명은 `R###-neutral-topic.md` 형식이다. slug는 특정 라이브러리나 선호 후보가 아니라 중립 질문을 짧게 나타낸다.
- `research/index.md`에는 `ID | 중립 질문 | 상태 | 영향 | 파일`만 둔다. 후보 기술, 권장안과 상세 Verdict는 적지 않는다.
- 파일 상태는 `작성 중 | 확정 | 중단됨`을 사용한다. `결론 가능 | 결론 보류`는 Verdict 판정으로만 사용한다.
- 영향은 `Phase 후보 | Phase #N | Build #N` 또는 그 조합을 기록한다. Execution이 확정되면 실제 Phase·Build 연결로 갱신한다.
- 기존 문서는 읽기만 했다는 이유로 재작성하지 않는다. 현재 질문을 수정할 때만 필요한 조사 목적·관찰 수준·남은 공백을 보완한다. 기존 상태·ID·참조와 변경 없는 합의는 유지한다.

### 기존 `research.md` 이전

기존 `./.elenchus/research.md`는 단순히 프로젝트를 열거나 읽을 때 변경하지 않는다. 새 Research를 시작해 문서를 수정할 때 다음을 수행한다.

1. `./.elenchus/research/`를 만들고 기존 내용을 보존한 채 Research 파일로 이동한다.
2. research 디렉터리가 없으면 `R001-legacy.md`를 사용한다.
3. research 디렉터리나 index가 이미 있으면 가장 큰 기존 ID 다음 번호를 사용하며 파일을 덮어쓰지 않는다.
4. `research/index.md`에 중립 질문, 기존 상태, 영향과 새 경로를 기록한다. 기존 문서에서 중립 질문을 알 수 없으면 `기존 Research`라고 적고 내용을 추정하지 않는다.
5. `execution.md`와 다른 `.elenchus` 문서의 기존 `research.md` 참조를 새 파일 경로로 갱신한다.
6. 이전 완료 뒤 새 Research에는 다음 ID를 부여한다.

## Repository 기준선

현재 Idea와 유효한 사용자 요청의 확정 제약·열린 선택을 intake로 사용하고, 후보 탐색 전에 관련 저장소 사실을 읽기 전용으로 확인한다. Idea 전체가 확정돼야 하는 것은 아니다.

- 관련 파일·심볼·설정·테스트와 현재 동작을 확인한다.
- 관찰한 사실과 해석을 분리해 Research 파일에 기록한다.
- neutral brief의 입력·출력·사용자 경험·제약을 바꿀 수 있는 사실을 우선한다.
- Repository가 없거나 현재 질문과 무관하면 확인을 생략하고 이유를 기록한다.
- 제품 파일을 수정하거나 Lab 실험을 수행하지 않는다.

## Neutral brief

Repository 기준선을 기록한 뒤 사용자 목적·확정 제약·열린 선택과 객관적인 저장소·환경 사실을 다음 구조로 줄인다. 아직 자료를 봐야 알 수 있는 성공 기준은 미해결로 두며 탐색 전에 임의 확정하지 않는다.

```text
중립 질문
입력
출력
사용자 경험
성공 조건
실패 조건
확정 제약
객관적인 저장소·환경 사실
미해결 질문
```

사용자가 언급한 procedure·API·라이브러리·서비스는 `필수 제약 | 현재 환경 | 후보 | 예시`로 분류한다.

- 필수 제약과 현재 환경만 neutral brief의 조건으로 사용한다.
- 후보와 예시는 확정 방향처럼 쓰지 않는다. 독립 탐색 brief의 조건에서는 제거하고 검증 작업에는 후보라는 분류와 함께 전달한다.
- 분류가 불명확하고 결과를 바꿀 수 있으면 사용자에게 확인한다.
- Repository 기준선이나 사용자 답으로 입력·출력·사용자 경험·성공·실패 조건·제약이 바뀌면 neutral brief를 즉시 갱신한다.

## Research subagent

합의된 조사 범위 안에서 독립적인 질문을 나눌 이점이 있고 도구가 지원되면 subagent를 활용한다. 사례와 구현 접근을 함께 찾아야 하거나 중요한 근거가 충돌할 때 역할을 분담한다. 단일 사실 확인·작은 국소 판단에는 불필요한 agent를 만들지 않는다. 역할과 조사할 질문을 알리되 내부 호출마다 같은 사용 승인을 반복하지 않는다.

| 역할 | 입력 | 반환할 결과 |
|---|---|---|
| 사례 탐색 | 목적·확정 제약·열린 선택·관련 원래 사용자 표현 | 직접 유사·인접 사례, 접근 범주, 비교할 장면·동작과 근거 |
| 구현 탐색 | 같은 중립 brief와 객관적인 환경 사실 | 구현 전략, 공개 코드·개발기·실패 경험, 재사용 조건·비용 |
| 집중 검증 | 확인할 후보·주장·충돌·관련 근거 | 확인·반박 근거, 직접 확인 범위와 남은 공백 |

### 위임과 후속 조사

- 탐색은 가능하면 대화 이력 없이 필요한 brief만 전달한다. 지원하는 도구의 실제 인자를 확인한다. `fork_turns="none"`은 그 기능을 제공하는 도구의 예다. 메인의 선호 후보·결론은 독립 탐색의 전제로 전달하지 않는다. 검증 역할에는 대상 후보·주장을 숨기지 않는다.
- 기존 목적·접근·투입 범위 안의 질문 구체화와 후속 조사는 메인이 판단하며 기존 agent를 우선 활용한다. 추가 agent는 새로 분리할 질문이 있을 때만 만든다. 인원·호출·검색 횟수를 품질 기준으로 고정하지 않는다.
- 새 조사 목적, 중요한 제약 변경, 큰 비용·접근 범위 확대는 변경 내용을 합의한다. 사용자에게 현재 세션만으로 조사하라는 지시가 있으면 따르고 재제안하지 않는다. 실제 호스트·상위 지침의 승인 요구는 유지한다.
- 호출 실패나 부족한 결과는 원인·남은 질문을 확인해 같은 범위의 후속 조사 또는 메인 보완으로 처리한다. 진전 없는 같은 호출을 반복하거나 권한 거절을 자동 확대하지 않는다. 완료할 수 없으면 공백과 다음 행동을 남긴다.
- subagent는 맡은 공개·읽기 전용 조사만 수행한다. 제품 파일 변경·Lab 실행·다른 agent로 재위임·브라우저 제어를 맡기지 않는다. 메인이 공개 시각 관찰·병렬 작업과 최종 결론을 관리한다.

### 지원 조건과 실제 권한

맥락의 독립성과 파일·도구 권한은 별도로 확인한다. 가능한 좁은 권한·도구 제한을 사용하고 불필요한 저장소·계정 정보는 brief에 넣지 않는다. 읽기 전용 강제가 없는 일반 공개 조사 경로도 호스트와 사용자 범위가 허용하면 사용할 수 있으나, 지시상 제한을 기술적 격리로 보고하지 않는다. 별도 격리가 필수인 데이터·코드·환경에서는 그 조건을 충족하지 못하면 실행하지 않는다.

무이력 생성이 불가능하면 독립성의 한계를 밝히고 메인에서 조사한다. 도구 부재·접근 제한으로 위임이 불가능해도 탐색 자체가 완료된 것은 아니다. 가능한 대체 조사를 수행하고 필수 근거가 없으면 보류한다. Lab과 사용자 로그인 관찰의 경계는 각각의 계약을 그대로 따른다.

### 결과 통합

agent는 직접 관찰·자료의 설명·추론·미확인을 구분하고, 결정에 필요한 원문 위치·적용 조건·실패 경험·남은 공백을 반환한다. 메인은 결과에서 같은 원문을 합치고 선택을 바꾸는 중요한 근거를 직접 확인한다. 여러 agent의 동의를 독립 출처의 수로 계산하지 않는다.

현재 `R###`에는 역할·범위·지원 한계, 접근 범주·핵심 후보 차이, 확인한 근거와 적용 판단, 남은 검증을 정제해 남긴다. 전체 agent 대화·장황한 검색 기록을 복사하지 않는다. 출처 추적에 필요한 원문 위치는 보존한다. 최종 비교와 완료 판정은 메인의 책임이며 사용자 결과를 바꾸는 새 선택은 사용자에게 확인한다.

이미 Idea에 있는 제약·사용자 결정을 각 R###의 긴 표로 다시 복사하지 말고 관련 위치를 참조한다. 같은 질문의 사례 비교와 그 후보 검증은 한 문서에 모을 수 있다. 단일 사실이면 필요한 근거·적용 범위·판정만 남긴다. 문서 항목의 존재를 보이기 위한 반복 작성보다 사용자가 검토할 비교 결과를 우선한다.

## 증거 계획

사용자에게 조사 모드를 선택하게 하지 않고 다음 증거원을 각각 `필요 | 생략`으로 판정한다.

```markdown
| 증거원 | 상태 | 이유 | 바뀔 수 있는 결정 |
|---|---|---|---|
| Repository | 필요 |  |  |
| Independent exploration | 필요 |  |  |
| External evidence | 필요 |  |  |
| Browser Evidence | 생략 |  |  |
| Lab | 생략 |  |  |
```

- Repository가 없거나 현재 질문과 무관하면 생략할 수 있다.
- 독립적인 질문 분담의 이점이 없거나 사용자가 메인 조사만 원하면 Independent exploration을 생략하고 이유를 남긴다. 필요한 탐색은 메인의 External evidence에서 수행한다. 도구 미지원이면 그 한계를 구분한다.
- 외부 사실이나 solution space가 결론을 바꾸지 않으면 External evidence를 생략할 수 있다.
- 공개 화면·JavaScript 데모는 External evidence의 공개 관찰 경로로 확인한다. Browser Evidence는 사용자 로그인·개인화·현재 권한의 관찰로 별도 판정하며, 그 환경만 확인할 질문은 External evidence를 생략할 수 있다.
- 실제 관찰이 Verdict나 Execution을 바꿀 수 있을 때만 Lab을 사용한다.
- 증거원을 생략한 이유가 없으면 Research closure를 통과하지 않는다.

## 실행 환경 확인

Lab·subagent·Browser를 사용할 때 해당 경로에 필요한 기능과 현재 도구 스키마를 먼저 확인한다. 호스트 이름만으로 지원을 선언하지 않는다. 환경이 같고 확인이 유효하면 반복 승인이나 같은 조사를 요구하지 않는다.

| 경로 | 확인할 조건 | 확인 불가·미지원 시 |
|---|---|---|
| Lab | 허용 쓰기 경로, import·캐시·임시 파일·의존성의 출력 위치, 시간·외부 부수 효과 | 읽기 전용 분석·통제된 mock 또는 검증 연기 |
| 독립 탐색 | 무이력 입력 지원, 허용 도구·실제 권한과 지시상 제한의 차이, 조사 범위 | 위 호출 계약에 따라 대체하고 독립성·실행 한계를 기록 |
| 공개 Browser 관찰 | 메인의 별도 조사 탭·공개 자료 범위, 렌더링·관찰 도구 지원 | 다른 공개 자료 또는 미확인 범위 기록 |
| 사용자 Browser Evidence | 정확한 지정 탭 식별, 현재 연결/권한, 비영구적 관찰인지 | 재지정·사용자 수동 확인·공개 근거 또는 보류 |

필요한 확인만 현재 `R###`의 증거 계획에 남긴다: 호스트·버전·OS·확인 날짜, 제공 도구/스키마, 지침상의 범위, 호스트가 실제 강제하는 권한, 확인 방법과 `사용 가능 | 미지원/차단 | 미검증`. 단순 파일 diff, 모델의 지침 준수, 호스트의 강제 차단은 서로 다른 증거다.

호스트가 제공하는 좁은 쓰기 경계·제한된 도구를 사용하고 실제 조건을 기록한다. 해당 경로의 필수 제약을 충족하지 못하면 실행하지 않는다. 일반 공개 조사와 격리가 필수인 실험은 위 계약으로 구분한다. 출력 위치 재지정은 전체 파일 접근 차단과 같지 않다. 권한 거절·연결 실패·미지원 인자를 이유로 자동 권한 확대·재위임·무한 재시도를 하지 않는다.

대체 경로는 원래 증거와 같은 강도로 취급하지 않는다. 실제 관찰 여부, 적용 범위와 남은 공백을 Verdict에 반영하며 필수 근거가 남으면 결론을 보류한다.

## 증거 루프

저장소에서 확인할 수 있는 사실을 먼저 살핀 뒤에도 대상 식별 정보·필수 자료·실행 기능/권한이 없어 조사를 시작할 수 없으면, 확인한 범위·제약, 근거 공백, 미지원 사유·가능한 대안과 다음 질문만 짧게 남긴다. 아직 실행하지 못한 조사에 빈 표와 전체 보고서 틀을 채우지 않는다. 상태는 `작성 중`, Verdict는 `결론 보류`이며 조사 완료로 계산하지 않는다. 자료를 수집·비교할 수 있게 되면 아래 증거 루프와 해당 조사 깊이를 적용한다.

1. 관련 Repository 기준선과 현재 사용자 목적·제약·열린 선택을 확인한다.
2. 필요한 조사 목적을 정한다. 탐색이면 Discovery의 접근 범주·사례 발견부터, 검증이면 시험할 주장·반증 조건부터 시작한다.
3. 독립적인 질문 분담의 이점과 지원 조건을 판단해 필요한 역할을 맡긴다.
4. External evidence를 수집한다. 발견한 후보의 중요한 주장을 검증하고 접근 범주와 근거 공백을 갱신한다.
5. 필요한 공개 화면·영상은 실제로 관찰한다. 로그인·개인화 Browser Evidence는 지정 탭·Claim 범위에서 메인이 관찰한다.
6. Lab이 필요한 주장은 예상 방향·채택·폐기 기준을 적고 조건부 실험한다.
7. 관찰·반대 근거·적용 한계를 종합해 현재 사용자 선택으로 돌려준다. Idea와 충돌하면 변경 범위를 확인한다.
8. 탐색을 포함한 조사에는 다섯 완료 기준을, 수행한 검증에는 해당 검증 기준을 적용한다. 단일 사실 확인에 탐색 기준을 추가하지 않는다. 좁은 질문을 닫은 사실로 필요한 미탐색 범위를 숨기지 않는다.

External evidence나 Browser Evidence가 `필요`이면 조사 전에 [Web Evidence Loop](web-evidence-loop.md)의 공통 절차·조사 깊이·Web closure와 사용하는 증거원 섹션을 읽어 적용한다. 공개 자료만 필요하면 Browser 상세 계약을, Browser-only면 공개 접근 상세를 미리 로딩하지 않아도 된다. 새 증거원이 필요해질 때 해당 섹션을 읽는다. 별도 사용자 선택 모드는 만들지 않는다.

### External evidence

[Web Evidence Loop](web-evidence-loop.md)의 조사 깊이·본문 검증·접근 기록·gap loop와 Web closure를 따른다. subagent가 제시한 결정적 사실과 출처도 메인 세션이 직접 확인해 적용 범위를 판단한다.

### Browser Evidence

[Web Evidence Loop의 Browser 계약](web-evidence-loop.md#browser-evidence)에 따라 메인 세션이 사용자가 지정한 탭·Claim만 관찰한다. 승인·관찰 경계·탭 보존·민감정보·실패 처리와 Web closure는 그 문서에서 관리한다. External evidence를 생략했어도 Browser-only 근거로 Web closure를 완결할 수 있다.

## Lab

Lab은 문서와 저장소 분석만으로 판정할 수 없고 실제 관찰이 Verdict나 Execution을 바꿀 때만 메인 Elenchus 세션이 사용한다.

### 격리 경계

- 모든 실험 코드·fixture·mock·응답·로그·출력·캐시·임시 파일·가상환경과 의존성은 `./.elenchus/lab/R###/` 안에만 만든다.
- 제품 코드·설정·manifest·lockfile과 Lab 밖의 프로젝트 파일은 읽기 전용이다.
- 제품 코드를 직접 수정하지 않고 읽기 전용으로 import하거나 필요한 최소 부분을 Lab으로 복제한다.
- 도구가 Lab 밖에 캐시·bytecode·출력을 만들 수 있으면 출력 위치를 Lab으로 재지정하거나 생성을 끈다. 격리를 보장할 수 없으면 실행하지 않고 이유와 필요한 사용자 결정을 기록한다.
- Python은 필요에 따라 `-B` 또는 `PYTHONDONTWRITEBYTECODE=1`로 bytecode 생성을 끈다. 도구별 임시·캐시 경로는 실제 지원 설정으로 Lab 안에 지정한다. 제품 import의 부수 효과를 모르면 먼저 소스를 확인하거나 필요한 부분만 복제한다. 사전/사후 diff는 이상 탐지이며 예방적 격리의 증명으로 대신하지 않는다.
- 인증정보와 원본 개인정보를 Lab에 저장하지 않는다. 필요한 실제 데이터는 최소화·비식별화하고 권한 범위를 넘지 않는다.

### 실행 전 계약

각 실험 전에 다음을 Research 파일에 적는다.

```text
시험할 주장
실행이 필요한 이유
예상 방향
채택 기준
폐기·실패 기준
범위와 예상 비용·시간
```

다음 조건을 모두 만족하는 작은 실험은 별도 승인 없이 실행할 수 있다.

- Lab 밖을 변경하지 않음
- 외부 서비스의 상태를 변경하지 않음
- 유료 호출, 새 계정·권한과 민감정보 저장이 없음
- 실행 범위와 시간이 작고 중단해도 제품과 사용자 데이터에 영향이 없음

유료 호출, 외부 생성·수정·삭제, 새 인증·권한, 민감한 실제 데이터, 장시간·대규모 실행은 기존 승인 범위를 확인하고 새로 필요한 범위만 실행 직전에 확인한다. 격리 불가능성은 승인으로 해소되지 않는다. 해당 실험을 실행하지 않고 가능한 대안과 다음 결정을 제시한다.

### 보존과 의미

- Research가 확정·중단·취소되어도 Lab을 자동 삭제하지 않는다. 사용자가 언제든 삭제할 수 있는 폐기 가능한 작업장으로 간주한다.
- 이후 Research는 기존 Lab을 자동으로 읽거나 재사용하지 않는다. 사용자가 명시적으로 요청하거나 현재 검증에 반드시 필요한 경우에만 확인한다.
- Lab 코드·원본 응답·전체 로그·상세 실행 명령과 우연히 사용한 구현 구조를 Research 파일에 복사하지 않는다.
- Research 파일에는 시험한 주장, 관찰, 조건·한계, 판정과 Idea·Execution에 미친 영향만 남긴다.
- Verdict는 Lab 디렉터리가 없어도 이해되고 적용될 수 있어야 한다. Lab 코드를 제품 구현의 출발점으로 지정하지 않는다.

실행 상태는 다음을 사용한다.

```text
기준선
채택
폐기
실패
검증 실패
제외
```

측정값이 좋아져도 검증 실패, 범위 밖 변경이나 측정 편법이 있으면 채택하지 않는다.

## 내부 검토 관점

[공통 질문 선택의 내부 관점](../SKILL.md#2-다음-질문-선택)을 Verdict에 적용한다. 출처·반대 자료·적용 범위, 추가 조사가 결론을 바꿀 가능성, Idea·Execution의 경계와 순서에 미치는 영향을 검사한다.

## Verdict

```text
판정: 결론 가능 | 결론 보류
근거
반대 근거
후보와 핵심 차이
채택·제외 근거
한계
신뢰도: 높음 | 중간 | 낮음
Idea에서 바꿀 내용
Execution에서 바꿀 Phase·Build
```

- 탐색과 검증의 판정 범위를 밝힌다. 계획 합의를 관찰·실험 성공으로 해석하지 않는다. 근거가 부족하면 결론을 강제하지 않고 `결론 보류`로 둔다.
- 반대 근거와 제외한 실행을 숨기지 않는다.
- 결론 보류가 사용자 결과나 Execution을 바꾸면 Research를 계속하거나 범위를 제외·연기하거나 검증 Build를 만든다.
- 사용자 결과와 무관한 기술 세부만 사용자 동의 후 구현 위임으로 보낼 수 있다.

## 종료 차단 조건

- neutral brief의 입력·출력·사용자 경험·성공·실패 조건·제약 중 필요한 항목이 비어 있다.
- 사용자가 언급한 기술을 제약·환경·후보·예시로 분류하지 않았다.
- 증거원별 필요·생략과 이유가 없다.
- 위임이 조사 합의·호스트의 허용 범위를 넘었거나 역할·지원 한계와 대체 조사 범위를 숨겼다.
- subagent의 결정적 근거를 메인이 확인하지 않았거나 agent 간 중복 원문을 독립 근거로 계산했다.
- 필요한 탐색이 Discovery의 다섯 완료 조건을 충족하지 않았다. 생략·연기 합의 또는 검증 Build 등록을 탐색 수행 완료로 계산했다.
- 검증할 핵심 주장과 반증 조건이 연결되지 않는다. 탐색 초기의 열린 질문 자체에 확정 주장을 요구하지 않는다.
- 사용한 사실에 출처·Browser 관찰 또는 확인 날짜가 없다.
- 전체 기록에서 반대 자료를 찾지 않았고 검색 범위도 적지 않았거나, 간소화 기록에서 반대·실패 점검의 생략 이유가 없다.
- External evidence나 Browser Evidence가 필요한데 선택한 깊이의 주장·원문·관찰 범위·반대 근거·판정·공백을 추적할 수 없거나 Web closure를 통과하지 않았다. 별도 표가 없다는 사실만으로 차단하지 않는다.
- 접근 실패 자료에 시도한 공개 대체 경로, terminal reason 또는 남은 관련 경로의 처리 이유가 없다.
- 필수 Browser Evidence에 사용자 승인 범위가 없거나 관찰 불가·연결 중단 뒤 다음 행동이 없다.
- Verdict 영향이 큰 `근거 부족` Claim이 남았는데 Lab, 범위 제외·연기 또는 검증 Build로 연결하지 않았다.
- 실행한 Lab의 기준선·측정 방향·판정 기준이나 격리 확인이 없다.
- Idea와 충돌한 근거에 대한 사용자 결정이 없다.
- Verdict에 근거·반대 근거·한계·신뢰도 중 하나가 없다.
- 결론 보류가 사용자 결과나 Execution을 바꾸는데 제외·연기·검증 Build 중 다음 행동이 없다.
- index의 상태·영향·파일이 실제 Research 파일과 일치하지 않는다.

## Research 파일 구조

아래는 최소 기록 예시다. 필요한 의미를 한 문단·표로 합치고 수행하지 않은 증거원의 빈 섹션은 만들지 않는다. 복잡한 조사만 지원 문서의 세부 항목을 확장한다.

```markdown
# Research R###: {중립 주제}

- 상태: 작성 중 | 확정 | 중단됨
- 기준: ../idea.md의 관련 결정
- 확인 날짜: {날짜}
- 영향: Phase 후보 | Phase #N | Build #N

## 질문·목적·범위
목적·열린 선택·확정 제약의 참조, 관련 저장소 사실, 기술 언급의 분류.
필요한 증거원·생략 이유와 사용한 위임의 역할·실제 지원 한계.

## 비교와 근거
탐색이면 Discovery 비교표. 검증이면 주장·원문·관찰·적용 범위·반대 근거·판정·남은 공백.
같은 근거를 여러 표로 복사하지 않는다. 출처·원문 위치와 관찰 수준은 추적 가능하게 유지한다.

## 결론과 다음 행동
목적별 판정, 채택·제외·유지·보류 근거, 한계·신뢰도.
필요한 완료 기준의 근거, 사용자 결정·미승인 제안, Idea·Execution에 미치는 영향.
실제 실행한 Lab의 관찰·조건·한계 또는 아직 필요한 실험과 검증 시점.
```
