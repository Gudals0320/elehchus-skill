# Research

## 목적과 연구의 단위

Topology의 목표에 필요한 해법을 넓게 발견·비교하고, 기능을 실제로 구현·연결·실험해 재사용할 재료와 확인된 지식을 확보한다. 탐색·벤치마킹, 환경·계약 확인, 구현·실험·통합 검증을 질문에 맞게 결합한다. Web·Repository·Browser·Lab은 수단이며 사용자에게 조사 모드 선택을 요구하지 않는다.

독립적인 결정 질문 하나를 R 문서 하나로 다룬다. 같은 질문의 후속 조사·실패·재실행은 그 R에 이어가고, 별개의 질문이 생기면 새 R과 발생 이유를 Topology에 연결한다. 한 번 정한 계획 때문에 중요한 새 질문을 무시하지 않는다.

실제 기능 재료를 요구받았다면 설명·실험 계획만으로 완료하지 않는다. 웹 비교만으로 답할 수 있는 질문에는 형식적 코드를 만들지 않는다. 재료의 가치는 실행·적용 가능성과 증거로 판단한다.

## 진입과 범위

현재 Topology의 목적·기능·기대 입출력·달성 조건·환경·허용 범위를 읽는다. 자료로 알아낼 수 있는 사실은 먼저 확인한다. 후보가 아직 없으면 열린 질문에서 [Discovery](discovery.md)를 시작한다. 실제 기능의 입출력과 환경 제약을 확인할 때는 [Lab](lab.md)을 적용한다.

합의된 목적 안의 질문 구체화, 실패 원인 조사, 대안·후속 실험과 역할 배정은 메인이 수행하고 알린다. 중요한 목적·제약 또는 큰 비용·접근 범위 변경만 다시 합의한다. 미응답을 기능 축소나 새 권한의 승인으로 바꾸지 않는다.

## 파일과 ID

```text
.elenchus/
├─ topology.md
├─ research/
│  ├─ index.md
│  └─ R001-neutral-topic.md
└─ lab/
   └─ R001/
```

- R ID는 index·파일에서 가장 큰 번호 다음의 `R###`로 부여하고 삭제 번호를 재사용하지 않는다. slug는 선호 라이브러리 대신 중립 질문을 나타낸다.
- index는 `ID | 중립 질문 | 상태 | 영향 | 파일`만 유지한다. 영향은 관련 기능·Topology 목표·의존 질문이며 실제 결과·후보 비교는 R에 둔다.
- 문서 상태 `작성 중 | 확정 | 중단됨`과 Verdict `결론 가능 | 결론 보류`를 구분한다. `확정`은 기록된 범위의 연구 결론이며 미승인 제품 선택이나 모든 코드의 완성을 뜻하지 않는다.
- 원문·실행 로그 전체를 Topology나 index에 복사하지 않는다. 관련 근거·재료의 경로와 재현 방법을 연결한다.
- 기존 R과 프로젝트 문서는 읽기만 했다는 이유로 변환하지 않는다. 실제 수정하는 질문의 새 Topology 연결만 보완한다.

기존 단일 `research.md`를 수정해야 한다면 원문을 보존한 채 다음 빈 R에 내용을 복사하고 index·현재 Topology에서 새 위치를 참조한다. 옛 문서와 기존 참조를 무단 삭제·일괄 재작성하지 않는다. 상충하는 두 기록을 독립 근거로 세지 않으며 현재 기록의 출처를 명시한다.

## Repository와 중립 brief

관련 소스·설정·의존성·테스트·환경을 읽어 기준선을 확인한다. 저장소가 없거나 질문과 무관하면 짧게 이유를 남긴다. 실제 코드의 결과인지 문서상 기대인지 구분한다.

공유할 brief는 목적·중립 질문, 필요한 입출력과 데이터 의미, 확정 제약, 객관적인 환경 사실, 달성/실패 조건, 열린 선택으로 제한한다. 독립 탐색자에게 메인의 선호 결론을 전제하지 않는다. 사용자가 언급한 기술의 필수 제약·현재 환경·후보·예시 분류를 유지한다. 후보 검증 역할에는 검증할 대상과 반증 질문을 명시한다.

## Research subagent

**복수 해법이 가능한 비단순 Research에는 실제 웹 탐색과 서로 다른 질문을 맡은 탐색 subagent 두 명을 기본으로 사용한다.** 먼저 목적·역할을 알리고 범위 내 호출·재호출 승인을 반복하지 않는다. 이 기본은 탐색을 메인의 익숙한 후보에 가두지 않기 위한 수행 규칙이며 인원 수 자체가 품질 점수는 아니다.

| 기본 분담 | 질문·반환할 결과 |
|---|---|
| 기존 해법·구현 사례 | 직접적인 해법, 실제 코드·유지 상태·계약, 적용 비용과 근거 |
| 대체 접근·인접 분야·실패 경험 | 다른 문제 분해/구현 방식, 재사용 가능한 인접 해법, 실패·제약·반증 근거 |

- 시작은 가능하면 필요한 brief만 받은 새 맥락으로 한다. 지원 도구에서 `fork_turns="none"` 같은 실제 인자를 확인하며, 단지 중립적인 문장을 쓴 것을 맥락 격리라고 부르지 않는다.
- 관련 실패나 새 단서가 나오면 기존 agent에 후속 질문을 주거나 역할을 바꾼다. 분리할 업무와 여유 도구/동시 실행 슬롯이 있을 때 추가 agent를 쓴다. 제한된 슬롯에서는 순차 실행할 수 있다.
- 구현·라이브러리 비교·테스트 작성/실행·공개 브라우저 관찰도 맡길 수 있다. 쓰기 작업에는 [Lab](lab.md)의 작업장·파일 소유권·입력 보호 범위를 전달한다. 다른 작업자의 파일을 동시에 수정하지 않는다.
- 메인은 역할·작업장·동시 실행 수와 후속 질문을 조정한다. 결론을 바꾸는 원문과 실제 실행 결과를 재확인하고 중복 원천을 합친다. agent의 동의나 보고만으로 독립 근거·실행 성공을 선언하지 않는다.
- 위임된 브라우저 관찰도 실제 도구 지원과 접근 범위를 확인한다. 공개 자료 조사 합의를 사용자 로그인 환경의 권한으로 확대하지 않는다.

### 간소화와 미지원

단일 API 지원 여부·좁은 저장소 사실처럼 대안을 발견할 필요가 없는 질문에는 메인이 필요한 근거만 확인한다. 간소화 이유를 짧게 남기며, 여러 선택이 걸린 연구를 단일 사실 질문으로 잘라 독립 탐색을 생략하지 않는다.

위임 도구가 없거나 사용자가 메인 단독 조사를 명시하면 그 한계와 메인이 조사한 범주를 기록한다. 무이력 생성만 불가능한 경우에는 필요한 범위의 brief와 실제 맥락 한계를 밝히고 사용 가능한 위임을 활용할 수 있다. 기술적 격리가 필요한 민감한 작업의 접근 조건은 별도로 지킨다. 위임 부재·한 agent 실패를 수행 완료로 계산하지 않는다.

## 실행 환경 확인

필요한 경로의 도구·권한·출력 위치를 실제로 확인한다. 호스트 이름만으로 지원/미지원을 단정하지 않는다. 이미 확인한 같은 환경·승인 범위는 재사용한다.

- Web: 실제 검색·본문 확보와 공개 대체 경로.
- Browser: 관찰 대상과 세션·탭, 공개 자료 또는 사용자가 지정한 로그인 환경.
- Subagent: 사용 가능한 생성·후속 전달·파일/도구 권한과 맥락 독립성.
- Lab: 독립 작업장·복제할 원본·의존성·캐시·외부 부수 효과·재현 조건.

출력 후 diff는 변경 탐지이며 사전 격리의 증명이 아니다. 부족한 기능·권한이 있으면 가능한 대안을 확인하고, 필수 근거가 막히면 그 부분을 보류한다.

## 증거 루프

1. 목적·입출력·달성 조건과 기준선에서 아직 모르는 질문을 고른다.
2. [Discovery](discovery.md)로 직접 해법·대체 방식·인접 분야·실패 경험을 탐색한다. 유력 후보의 출처·버전·코드·관찰은 [Web Evidence](web-evidence-loop.md)로 확인한다.
3. 실제 실행이 필요한 주장에는 예상 결과·실패 조건·비교 방법을 정하고 [Lab](lab.md)에서 구현·연결·실험한다.
4. 기대와 실제 결과의 차이, 오류·환경 제약을 기록한다. 동작을 바꿀 수 있는 실패이면 관련 사례·대체 구현을 웹에서 다시 찾아 후속 실험으로 연결한다.
5. 같은 질문은 가설·접근을 갱신해 계속하고, 독립 질문은 다음 R과 Topology에 연결한다. 실패를 숨기거나 같은 명령을 근거 없이 반복하지 않는다.
6. 근거·코드·데이터·테스트를 재현 가능하게 정리하고 목적별로 결론을 판정한다. 해결된 점과 아직 바뀔 수 있는 점을 Topology에 반영한다.

조사 자체를 시작할 필수 자료·기능·권한이 없으면 확인한 조건, 가능한 대안, 필요한 사용자 결정·재개 조건만 남긴다. 빈 전체 보고서나 아직 없는 테스트 결과를 채우지 않는다.

## 재료와 결론

R에는 질문·달성 조건, 서로 다른 접근의 비교, 직접 근거·실행 증거, 사용한 역할과 실제 한계, 재료 위치·실행 방법, 실패 경험·미검증과 다음 행동을 남긴다. 비교표가 이 정보를 담으면 근거 표를 반복 생성하지 않는다.

탐색과 구현·검증이 함께 있으면 각각의 판정 범위를 구분한다. 외부 설명을 우리 환경의 실행 성공으로, 테스트 통과를 전체 실제 데이터·성능·제품 적합성으로 확대하지 않는다. 부정적인 결과도 질문에 충분한 답이면 결론 가능할 수 있다. 요청한 작동 기능을 만들지 못했다면 그 목표는 미달성으로 남긴다.

### 종료 판단

- 탐색은 [Discovery의 다섯 기준](discovery.md#완료-판정)을 확인한다. 빠진 중요한 범주나 편중된 원천이 있으면 추가 조사한다.
- 기능 재료는 달성 조건에 대응하는 실제 코드·데이터·테스트·재현 절차로 확인한다. 계획만 만든 것은 실제 검증이 아니다.
- 실패·제약·미검증·모의 처리를 구분한다. 당초 조건 변경과 그 근거를 추적한다.
- 같은 목적의 중요한 공백은 계속 조사한다. 접근 제한·사용자 제외·연기로 끝내면 충분한 조사 종료와 구분하고 영향을 남긴다.
- Pro 전달, 미래 구현 계획 등록, 화면 선택 보류만으로 미완료 연구를 완료 처리하지 않는다.
- 각 R의 결론은 메인이 근거로 정리한다. 사용자 목적·새 선택을 바꿔야 할 때만 그 쟁점을 확인하며 결론 승인 질문을 매번 반복하지 않는다.
- 세션 전체의 전달·종료는 [공통 규칙](../SKILL.md#결과-전달과-종료)을 따른다.

## 기록 예시

```markdown
# Research R001: {중립 질문}
- 상태: 작성 중 | 확정 | 중단됨
- 기준: ../topology.md의 관련 목표
- 영향: {기능·연구 질문}
- 확인 환경/날짜: {실제 조건}

## 질문·목적·달성 조건
## 접근 비교·원문·관찰·실행과 실패 경험
## 재료·재현 방법
## 결론·한계·추가 질문
판정: 결론 가능 | 결론 보류
```

전체 agent 대화·원본 응답·실행 로그를 R에 복사하지 않는다. 검토자가 관련 증거와 재료를 찾을 경로는 유지한다. 확정된 외부 제약·데이터 의미와 임시 구현의 모양을 구분해 다음 제작자의 재량을 보존한다.
