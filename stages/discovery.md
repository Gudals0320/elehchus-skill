# 탐색·벤치마킹

## 목적과 적용

관련 문제를 이미 풀어본 사례와 접근법을 발견하고 실제 근거로 비교해, 사용자가 자신의 조건에 맞는 방향을 선택하도록 돕는다. 재사용할 해법과 피할 실패 경험을 함께 제시한다. 아직 비교 후보가 없는 상태의 발견도 이 작업의 책임이다.

[Research](research.md)의 조사 목적에 탐색·벤치마킹이 포함될 때만 읽는다. 요청된 레퍼런스, 낯선 분야의 여러 접근, 사례가 필요한 시각·상호작용, 재작업 비용이 큰 전제를 다룬다. 단일 API 지원 여부처럼 후보 발견이 필요 없는 사실 확인은 기존 Web Evidence의 간소화 경로를 사용한다.

## 탐색에서 적용까지

1. 현재 문제·확정 제약·열린 선택과 조사 범위를 정한다. 이미 알고 있는 해법을 정답으로 넣거나 모든 미정 제품 선택을 먼저 확정하지 않는다.
2. 해결 방식이 달라질 수 있는 접근 범주를 찾는다. 직접 유사 사례와 문제 일부를 해결한 인접 분야를 함께 살핀다. 관련성이 없는 분야까지 의무적으로 늘리지 않는다.
3. 발견한 용어·프로젝트·개발자·참고 링크를 따라 후보와 검색어를 갱신한다. 유력한 대안과 반대·실패 사례를 비교하고 같은 원문의 재인용을 합친다.
4. 후보를 실제 판단에 필요한 깊이로 확인한다. 자료 확보·본문 검증·공개 대체 경로는 [Web Evidence Loop](web-evidence-loop.md)를 사용한다. 발견한 후보의 중요한 주장을 그때 Claim으로 구체화한다.
5. 우리 조건에서 가져올 요소, 필요한 변경, 적용하기 어려운 부분과 비용을 비교한다. 기존 선택을 유지하는 결론도 근거가 충분하면 유효하다.
6. 남은 공백 중 선택을 바꿀 가능성이 큰 것을 다음 조사 대상으로 삼는다. 우리 환경에서만 확인할 수 있는 주장에는 실험 조건과 검증 시점을 연결한다.

검색 묶음 뒤 접근 범주와 남은 공백을 갱신한다. 알려진 후보의 Claim을 모두 채웠다는 이유로 발견 범위까지 충분하다고 판단하지 않는다. 더 조사하면 다른 선택을 할 만한 관련 범주가 남아 있는지 확인한다. 검색량·출처 수·보고서 길이·agent 수의 할당량을 만들지 않는다.

## 근거와 관찰 수준

| 판단 대상 | 직접 확인할 대상 | 과장하지 않을 범위 |
|---|---|---|
| 형태·배치·가독성 | 실제 화면·이미지·공개 데모의 관련 장면 | 소개 문구·이미지 URL만 확보했다면 시각 관찰이 아님 |
| 움직임·속도·연속 사용 | 영상의 관련 구간 또는 동작하는 데모 | 정지 이미지·자막은 움직임이나 대기 시간의 관찰이 아님 |
| 구현 전략·재사용 | 관련 코드·기술 설명·작성자의 개발기 | API 존재는 우리 구현의 정확성·성능을 보장하지 않음 |
| 실패·운영 경험 | 원 작성자의 이슈·후기·회고와 조건 | 개별 사례를 모든 사용자·버전에 일반화하지 않음 |

관찰한 장면·동작과 원문 위치를 남기고 `직접 관찰 | 자료의 설명 | 추론 | 미확인`을 구분한다. 코드·에셋 재사용을 제안하면 사용 조건과 수정 부담을 확인한다. 시각 자료를 못 보거나 영상 재생이 지원되지 않으면 다른 공개 자료를 찾거나 해당 판단을 미확인으로 남긴다. 자료가 없는 부분을 상상으로 채우지 않는다.

공개 화면은 승인된 조사 범위에서 메인이 별도 조사 탭으로 관찰할 수 있다. 사용자 로그인·개인화 탭과의 경계는 Web Evidence의 Browser 계약을 따른다. 시각 자료 보존이 필요하면 기존 저장 승인·경로 규칙을 사용한다.

## 비교 산출물

별도 장문 보고서 대신 현재 `R###`에 아래 의미를 남긴다. 관련 내용을 한 표·문단으로 합칠 수 있다.

| 접근법·대표 사례 | 실제 근거·관찰 수준 | 해결 방식과 차이 | 우리 조건의 적용·제약·비용 | 채택·제외·보류와 이유 |
|---|---|---|---|---|

- 조사한 접근 범주, 제외하거나 확인하지 못한 범주와 이유.
- 사용자에게 보여 줄 비교 자료. 시각적 선택은 실제 사례를 나란히 볼 수 있게 원문·관련 장면을 제시한다. 확보한 자료가 판단을 지원하지 못하면 선택의 한계를 설명한다.
- 기존 방향을 유지하거나 바꿀 근거, 새 제안과 사용자 결정의 구분.
- 후속 조사·실험·Build가 답할 질문과, 그 전제를 사용하는 작업보다 먼저 검증할 조건.

## 완료 판정

메인이 다음 다섯 조건을 각각 근거와 함께 확인한다.

1. **접근법 비교:** 주요 해결 방식과 선택 조건의 차이가 드러난다. 유력 대안이 하나라면 조사 범위와 그 이유를 설명한다.
2. **적합한 직접 근거:** 결정에 필요한 대상과 원문을 실제로 확인했다. 직접 관찰·자료 설명·추론·미확인을 섞지 않는다.
3. **적용 가능성:** 가져올 요소, 필요한 변경, 적용 비용·제약이 구체적이다.
4. **결정 영향:** 채택·제외·보류 또는 기존 선택 유지의 근거를 사용자에게 제공했다. 사용자의 미응답을 새 제품 선택의 합의로 바꾸지 않는다.
5. **타당한 종료:** 선택을 바꿀 중요한 미탐색 공백이 없으며 추가 조사의 효용이 낮은 이유를 설명한다. 남은 우리 환경의 실험은 별도로 연결한다.

웹 사례의 비교를 마쳤어도 우리 제품의 성공은 아직 미검증일 수 있다. 반대로 미완료한 사례 비교를 `구현하면서 확인`으로 넘기는 것은 탐색 완료가 아니다. 접근 제한·예산·사용자 중단 때문에 끝내면 충분한 탐색 완료와 구분해 `결론 보류`와 남은 범위·다음 행동을 남긴다. 사용자가 탐색을 생략·연기한 경우에도 수행 완료로 계산하지 않는다.

탐색과 검증을 한 `R###`에서 함께 수행하면 목적별 판정 범위를 나눈다. 문서의 `확정`은 그 범위의 결론 합의이며, 미실행 관찰·실험까지 성공했다는 뜻이 아니다. 별개의 결정 질문이 생길 때만 다음 `R###`로 분리한다.
